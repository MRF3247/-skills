# SciLink 小红书图文成稿（dbs 编排版 v1.0）

一句话：**素材 → dbs 定结构与标题 → Kimi 新闻口吻成稿 → 脚本机检 → AI 味与风险复检 → 落盘（可选写回飞书）**。全流程可复现，不靠手感。

产出规格固定：正文 ≤1000 字（含标点、含 tag），tag 恰好 6 个，**末两位固定 `#刀客轻研` `#SciLink`**（品牌词＋产品词），标题 ≤20 字。

## When to Use

- 用户给长文 / 飞书文档 / 论文 / 新闻，要一篇小红书图文正文
- 用户说「AI 味太重」「改成新闻报道口吻」「重写小红书」「按批注改」
- 一条稿已完成，要落盘 + 附事实核对表 + 评论区置顶出处

不适用：封面出图（用 `scilink-ref-style-poster`）、B 站口播稿、公众号长文。

## dbs 分工（别串岗）

| 阶段 | 主 Skill | 它负责 | 本 Skill 负责 |
|---|---|---|---|
| 结构 | `dbs-content` | 形式匹配 + 五维诊断，产出结构判断 | 落成 5 段大纲 + 砍料清单 |
| 标题 | `dbs-xhs-title` | 75 条公式库匹配，给候选标题 | 筛到 ≤20 字、贴主题、给 Top3 |
| 写稿 | —（Kimi） | — | 按 prompt 骨架出正文 |
| AI 味 | `dbs-ai-check` | 逐处标 AI 指纹 | 按报告回改并复跑机检 |
| 发布 | `dbs-content-risk-check` | 平台机审 / 医疗类目 / 导流 / 绝对化 | 定 tag、定评论区出处、落盘 |

**硬规则**：

1. **`dbs-content` 只做诊断和结构，不代写**（它自述「你不帮人写内容，你帮人诊断内容该怎么做」）。把写正文派给它 = 拿到一份诊断报告交差。
2. **`dbs-xhs-title` 只是公式匹配器**。每条候选标题必须能溯源到公式编号 + 原始爆款 + 为什么选，自由发挥视为没用工具。
3. 用户说「调用 dbs」时先跑 `dbs/scripts/check-update.sh`（有输出才把更新提醒放回复末尾）。

## 流程

### Step 0 · 取素材，先做事实骨架

读原稿（飞书长文：`lark-cli docs +fetch --doc "<URL>" --as user --doc-format markdown`），把可用事实按编号列成表：时间、主体、机构、动作、数字、出处。数字照抄，不换算、不四舍五入、不加「近 / 约」。

**先查这条选题写过没有**：拿到的是 record 链接时，先看该记录的 `润色正文` 是否已有云文档 URL。非空 = 已写过，直接告知用户并把表里未写稿的候选（按话题度排）列给他挑，**不要重写一篇重复的**（用户可能只是把旧链接又贴了一次）。

**先定研究类型，再动笔**：「综述 / 原始研究 / 二次分析（多队列数据再分析）/ RCT / 观察性 / 会议摘要」必须先判定并写进 ⚠️ 首句。判据：有自己样本与方法、产出新结论 = 原始研究；在既有数据集上重做分析 = 二次分析；只在梳理文献 = 综述。搞不清就看 Methods 第一段与 `pubType`，不要默认写「观察性」。

**完成判据**：正文里每一个数字都能在这张表里找到同值同语境的一行。

### Step 1 · `dbs-content` 出结构

按它的 Phase 2（形式匹配）+ Phase 3（五维诊断）跑，只取结构结论：五段职责 + 该砍掉哪些素材。

经验顺序：「硬事实与量级 → 机制/拆词 → 为什么会发生 → 怎么被发现 → 下游代价」。离读者最远的素材（导师连带责任、机构历史撤稿率）先砍。

**完成判据**：每段能用一句话说清讲什么；砍掉的素材写成一行清单。

### Step 2 · `dbs-xhs-title` 出标题

3–5 条候选，覆盖至少 3 类触发器；每条标公式编号 + 原始爆款 + 一句话理由；末尾给 Top3。硬约束：≤20 字（含标点）、留悬念但不许让读者看不出讲的是什么事。

**新闻事件类选题的坑**：公式库里 #1/#7 那类悬念公式套上去会跑偏——用户会因为「标题不贴主题」直接打回。改用 #26 数字锚定 + #24 人群限定（例：「印度学者造假被查，41 篇论文撤稿」）。

**标题要吃「中国团队 / 全球首个」这类重磅身份**（用户 2026-10 原话：「这不是中国团队吗，看看有没有什么『首个』啊、很重磅的 title，受众是吃这些的」）：中国团队牵头、全球首个、多少国多少中心——只要网站上能找到出处（报告人原话、厂商新闻稿、机构官网），**标题和首段就要把它说出来**；只写数据不写身份 = 「没灵性」。查证方法：去搜报告人姓名 + 机构 + 研究代号，再看厂商 PR 里有没有 first-in-class / first global phase 3 这类措辞；**别自己造“首个”**，造了就是绝对化风险。

**完成判据**：Top1 可直接发；每条候选都能指回公式编号。

### Step 3 · Kimi 写正文

1. `cp <skill_dir>/templates/kimi-prompt.md /tmp/p.md`，填 `{{}}`：事实清单、五段职责、字数、6 个 tag（末两位 `#刀客轻研` `#SciLink`）。
2. `terminal(command="python3 <skill_dir>/scripts/kimi_write.py /tmp/p.md --out /tmp/draft.md", timeout=300)`

**完成判据**：`/tmp/draft.md` 有正文段落 + 最后一行 6 个 tag。

### Step 3.5 · 装回本账号房式（Kimi 交的是裸稿）

Kimi 按「无 emoji、无小标题、不许劝读者」的禁令写出来是一串裸段落，直接发出去和内容物料库其它条不像。成稿前手工装框，结构固定：

```
{一句主题句：这条讲什么、为什么现在讲}

{背景段：谁 / 何时 / 什么设计 / 什么数据源}

{一句主题引导，例：这六条是一条临床路径——诊断→一线→风险评估→二线→症状→移植后}

▫️ {要点，一条一行，写成完整句而不是冒号+名词堆}

{机制 / 为什么发生 / 怎么被应对，每段一个意思}

⚠️ {口径与截止时间：数据来自哪几家机构、截至哪天、各方统计口径是否一致}

#tag ×6（前 4 个是内容词，末两位固定 #刀客轻研 #SciLink）
```

硬约束：**数据块与正文段不许复述同一批数字**。数据块先把数字列全，正文只写背景、机制、应对、最新进展；写完把「同一数字第二次出现」的整句删掉，否则读起来像一件事说了两遍（实测能削掉 60–80 字且信息不减）。

**Kimi 裸稿会自我重复**：同一条限制（开放标签、随访时长、数据未成熟）常在末段和收尾各写一遍，两句话意思几乎相同。装框时合并成 ⚠️ 里的一处，不要把两句都搬进成稿——用户会把它当成凑字。

### Step 4 · 机检（不许跳）

`terminal(command="python3 <skill_dir>/scripts/xhs_check.py /tmp/draft.md --title \"<标题>\"", timeout=60)`

FAIL 的处理顺序：

1. 字数超 → 回灌 Kimi「压到 880 字以内，优先砍细节不砍事实」。
2. 命中 A 档句式 → 把具体句 + 改法回灌 Kimi 重写整段；**不要手动删两个字凑数**（会写出断句）。
3. tag / 标题不合规 → 直接改，这两项不需要模型判断。

**完成判据**：退出码 0，输出 `→ PASS`。

### Step 5 · `dbs-ai-check` + `dbs-content-risk-check` 复检

- `dbs-ai-check`：按文本顺序逐处看报告，重点看脚本抓不到的两项——**段段收金句**、**整段可删而信息不减**。
- `dbs-content-risk-check`：正文不能有外链（出处放评论区置顶）、无医疗功效表述、无绝对化词、无导流。医学科研选题的 tag 避开 `#医学科普` `#健康科普` 与病名科室词。

**完成判据**：两份报告无未处理项，或已写明为什么保留。

### Step 5b · 用户写了批注时（两轮以上很常见）

1. **先出整改方案，别直接改**：用户批注后的标准提问是「你告诉我你准备怎么改」。回复格式：逐条对应（原文 → 改法），能写出改后句子就直接写，并说明连带影响（字数变化、哪些部分不动）。他回「确认/改吧」再动手。
2. 改完：重跑 `xhs_check.py` → 回读文档 → 逐条 `drive +resolve-comment`，并在本地成稿末尾记「批注处理记录」。
3. 同一篇常被批 2–3 轮，每轮只动被点的部分；标题、封面、图片、出处、DS 初稿节默认不动（除非点名）。

### Step 6 · 事实核对表

正文说法 ↔ 原文出处，一行一条，放交付文件末尾。

**完成判据**：不存在「正文有、原文无」的行。

### Step 7 · 落盘 +（可选）写回飞书

- 本地成稿：`~/Documents/Hermes/小红书成稿/YYYY-MM-DD_<短标题>.md`，含标题候选（带公式溯源）、正文、事实核对表、评论区置顶出处。交付时用 `MEDIA:<绝对路径>`。
- 写回飞书：按 `references/feishu-writeback.md`，写完必须 `+fetch` 回读验证。

### Step 8 · 子文档与表格链接（物料库固定口径）

0. **会议／事件专题的文档名要带前缀**：用户口径「ESMO2026｜」这类前缀打在标题最前（全角竖线 `｜`，不是 `|`）。新建时一次写对：`--title 'ESMO2026｜<内容标题>'`；已建好的用 `lark-cli drive +update-title --url <wiki URL> --title 'ESMO2026｜…' --as user`（`--type wiki` 传 node token 也行，node 与 doc 标题会同步）。没有 `wiki +node-rename` 这个命令，别找。

1. **文档建在「资讯内容选题库」下**：`lark-cli wiki +node-create --parent-node-token DTcUwQwEBi1bTWkSdN9c09Kbnnf --obj-type docx --title '<内容标题>'`。
1. **文档固定结构（用户 2026-10 最终定，顺序不得变）**：

```
<title>ESMO2026｜<内容标题></title>
# 封面与截图      ← 四栏并排：封面（无文案）/封面（带文案）/P2/P3；下方引用块放参考图（小图~420px）
# 封面文案
主标：<专题名，成组专题才有；普通单条不写>
副标：<这一条的具体文案>
# 图文标题
<标题正文>
# 正文
<逐句一段的正文>
# 出处
# 附：DS 初稿
```

   - **封面与截图放最前面**（用户 2026-10 口径：先让审稿人看到图，再读文案），原来放后面的做法作废。
   - 封面文案单独成一节，`主标`/`副标` 各占一行；主标按需（ESMO 2026专题这类成组专题才写）。
   - 参考图一律以引用块 + 小图（宽约 420px）形式放在四图 grid 下方，不占大图。
   - 顶部 blockquote 不再放封面文案。标题用户会自己改：回填前先 `docs +fetch` 取当前值，以文档为准。

1b. **元信息用引用块，不混排成正文**：`生图引擎：…`、`说明：原文页 403…` 这类不是给读者看的话，用 `<blockquote>…</blockquote>`。
2. **表格「润色正文」列只放云文档链接，而且是纯 URL**（用户 2026-10 口径：「对，贴云文档链接」）：`fldHZF29L7 = https://my.feishu.cn/wiki/<node_token>`。**不要**把成稿正文写进这一列，也不要写成 `[标题](url)`（text 字段塞 markdown 会读回 None）。
3. `DS建议正文`（`fldqTWRrDy`）仍放 DS 初稿文字；两列分工不要串。
4. **存量记录一并改**：用户说「上一篇稿子贴的是原文也要换成链接」时，把旧稿的 `润色正文` 也改成它的云文档 URL，不要只改新的一条。
5. **子文档排序**：用户要求「子文档按从新到旧的顺序从上往下排」。实测飞书 wiki 子节点顺序＝创建时间升序（新建追加在末尾），OpenAPI **没有排序参数**：`wiki +move` 只能换父节点；`PATCH nodes/<token> {"position":0}` 回 404；`POST /open-apis/wiki/v2/spaces/<sid>/nodes/<token>/move` 带 `{"position":0}` **返回 `ok: true` 但顺序不变**——接口的 ok 不代表排序生效，别拿它当成功凭据。所以：新建后如实汇报「新文档在末尾，需 UI 拖到最上面」，并提议可选的逆序重建（会换链接、要回填表格，不推荐默认做）。

### Step 9 · 批注返工（先给方案，再动手）

用户会在同一篇稿上**多轮**批注，而且往往是「你告诉我你准备怎么改」——这是**只出方案、不改文档**的指令，不是让我直接开改。固定节奏：

1. `lark-cli drive +list-comments --url <URL> --solved-status all` 读全部未解决批注（`--solved-status all` 才看得到状态），逐条抄成「原文 → 意见」。
2. **回一份整改方案**，每条三段：原文怎么写的 → 改成什么 → **具体改写示例**（直接把新句子写出来，让用户看字感，别只描述思路）。
3. 末尾写「连带影响」：字数会怎么变、机检要不要重跑、标题/封面/图/出处哪块不动、DS 初稿那节改不改。
4. 等用户说「确认」再动手；改完 `xhs_check.py` 跑一遍、`docs +fetch` 回读、再 `drive +resolve-comment` 逐条标已解决。

**每次返工都要重跑机检**：展开句子（电报体→自然语言）几乎一定撞黑名单（实例：把「换来的瘙痒改善」展开后触发硬造动词「换来」），FAIL 要就地重写那句，不要为了过检删事实。

**改稿不动的东西**：标题、封面文案、已出的图、出处段、`附：DS 初稿` 那一节（初稿是留档，用户批的是成稿）。真要同步改初稿，先问。**例外：批注本身就是点在标题/封面文案上的（如「这个标题很没灵性，应该围绕中国团队重写」），当轮就以批注为准改，并同步表格里的 `图文建议标题`／`封面建议文案`**——不要把「默认不动」误读成「批了也不改」。

### Step 10 · 自审（用户说「看一下我的文案和封面有什么需要改进的」）

这是 **只出审查意见、不改文档** 的指令。按四组组织，每条都要带「依据的规则 + 具体改写后的句子」：

| 组 | 查什么 |
|---|---|
| **A 必改** | 违反硬规则：元叙述标签（0e）、电报体（0c）、小学生句式（0k）、数字与正文重复（Step 3.5）、数量词与条目数不符（0i） |
| **B 建议改** | 能更好但不违规：续行缩进、方法段过长、团队句位置、研究类型写得不准 |
| **C 封面** | 文案是否平庸/与标题同义（0l、0l-2）、画面元素是否与主题错位、单行文案是否已下移、色板 Δ |
| **D 一致性** | 文档 vs 表格字段是否被手改过、旧稿是否还停在旧规范（▫️ 缩进、文案位置、📌 钩子） |

末尾给一句执行建议（「A 全改 + B 全改 + C2 改画面，C1 你挑文案」），等用户点头再动手。

**回填前先 diff**：用户会在文档里直接手改标题（例：加上了「疼痛研究｜」前缀）与正文。改写或回填表格前，先 `docs +fetch` 取当前值、与表格字段逐列比对，**以文档里的手改版为准**，不要用本地旧稿覆盖他的编辑。

## 文档排版（手机阅读优先）

写飞书 docx 时正文不能一段一大块，按手机屏幕拆行：

1. **段与段之间空一行**：段落之间插一个只含全角空格 `　`（U+3000）的 `<p>`。空 `<p></p>` 虽能存活，但全角空格段在手机端更稳（实测不会被客户端合并）。
2. **每一行都是独立的 `<p>`，不缩进，也不再靠 `<br/>` 分行**：用户会把文档正文直接复制到小红书，实测 `<p>` 里的 `<br/>` 软换行在粘贴时会**全部丢掉、挤成一段**（用户 2026-10 原话：「换行消失了，全都挤到一段里」）。拆分点：先按空行分块，每块内按行拆，行内按 `。！？` 拆句（**`；` 不拆**，否则一个分号就把 ⚠️ 段塞断），每句一个 `<p>`。`▫️` 条目各自一个 `<p>` 且顶格。
   > 代价：文档里行间距比原来大、看着更散，但这是为了「复制即发」的保真度付的代价，用户已确认接受。验收：`docs +fetch --doc-format markdown` 里每句/每行之间应有空行（即 `\n\n`），且 `　　` 出现次数＝ 0。
3. 生成 XML 的固定写法：

```python
def body_xml(text, spacer="　"):
    """每句/每行一个 <p>：小红书粘贴时不丢换行（软换行 <br/> 会丢）。"""
    blocks = [b.strip() for b in re.split(r"\n\s*\n", text.strip()) if b.strip()]
    out = []
    for bi, b in enumerate(blocks):
        for line in b.split("\n"):
            line = line.strip()
            if not line:
                continue
            if line.startswith("▫️"):       # 每个 ▫️ 是一个独立段落
                out.append("<p>" + html.escape(line) + "</p>")
                continue
            for s in [x.strip() for x in re.split(r'(?<=[。！？])', line) if x.strip()]:
                out.append("<p>" + html.escape(s) + "</p>")   # 注意：；不拆
        if bi != len(blocks) - 1:
            out.append(f"<p>{spacer}</p>")
    return "\n".join(out)
```

> 坑：衹按句子切不按行切，`▫️` 列表会被并成一行（因为它们行尾没句号）。两层都拆才能保住列表形状。
>
> 坑 2（用户 2026-10 连纠两次）：早期用「段首是 ▫️ 则后续全部缩进」的布尔量，**每个 ▫️ 条目都被当成上一条的续行缩进**；改成按行判断后仍留着「续句缩两个全角空格」，用户直接指出「这里不要莫名其妙多几个空格」。最终口径：**一律不缩进、每句一个 `<p>`**（见本节第 2 条），段间只留一个全角空格段。验收：回读 markdown 里 `　　` 出现次数必须为 0，且句与句之间有空行。

4. `正文` 与 `附：DS 初稿` 两节都用这个函数；`出处`、`图文标题` 不用。
5. 回读验收：`docs +fetch --doc-format markdown` 里**每句/每行之间都要有空行**（`<p>` 分段的结果），`\u3000` 只出现在段间空行段，`　　` 出现次数为 0。如果看到「行尾两个空格＋换行」，说明又退回 `<br/>` 软换行了——那种写法复制到小红书会并成一段，直接判失败。

## 写作铁律

0. **不写 `📌` 开头钩子**（用户 2026-10 明确口径：「没必要每条文案都加这个」）。正文第一句直接上事实——机构＋时间＋数据。参考旧稿里的 `📌 一行钩子` 一律不要照搬。
0b. **`▫️` 数据块里的每一条必须指向同一个主题**。实测被批：「前两条是疫情进展，第三条 MMR 保护效力跟疫情进展有什么关系」。拆法：数据块只放「同一件事的几个数」，不同维度的数字（疫苗保护效力、政策口径）拿出去写进段落。
0c. **禁电报体**（用户原话：「不要为了少写字而少写字」「神经一样的六条推荐，推荐什么了」）。列表每条写成自然语言的完整句：什么人／什么情况／做什么／能得到什么。错：`▫️ AMA 阴性但临床怀疑 PBC：加查 sp100 与 gp210 抗体`；对：`如果患者临床很像 PBC，但抗线粒体抗体（AMA）查出来是阴性，指南建议再查 sp100 和 gp210 两种抗体，一部分患者因此不用做肝活检`。
0d. **列表前面必须有一句主题引导**：告诉读者这几条是什么、按什么逻辑排（例：这六条是一条临床路径——诊断→一线→风险评估→二线→症状→移植后）。裸列表直接甩 = 读者不知道在看什么。
0e. **禁元叙述标签**：「两条术语白话：」「下面解释两个术语」这种交代写法的句子一律删（用户原话「脱裤子放屁」），术语首现就地跟解释。
0f. **比喻写完整、说人话**：写「可以类比为这个病的『指纹』」，不许压成「像这病的『指纹』」；惜字如金到丢人味 = 返工。**但常识词不加比喻**（见铁律 4b）——写之前先问一句：这个词医生真的需要解释吗。
0g. **外部推荐里的「对照臂」和限定语不许压缩**：把指南的 `recommend using UDCA compared with no treatment` 压成「用 UDCA 而不是不治疗」，读者会以为临床上真有个「不治疗」方案（用户直接反问「原先的治疗方案到底是怎么建议的」）。写法分三档，按顺序试：① **首选整句删掉对照语**，只留结论——「指南把熊去氧胆酸（UDCA）列为初诊患者的一线选择」；② 对照必须在文中交代时，用原文自己的措辞，**不许自造「对照组 / 比较臂」这类读者看不懂的同位词**（生造出来的是「这句话啥意思？读起来莫名其妙」）；③ 原文没定义的（对照里到底观不观察、对不对症处理）不许替它补。
0h. **一组并列项的标签用同一句式**：六条建议统一叫「诊断阶段 / 一线治疗 / 风险评估 / 二线用药 / 症状处理 / 移植之后」，不许混进「诊断这一段」这种口语变体（用户原话「改为『诊断阶段』不就行了？」）。写完把这一组标签横向扫一眼再交。
0i. **并列项先按「结论方向」分组，再落到类型**：写「四类疼痛」却把急性与术后合并列成三条，会被抓「说四种却列三条」。正确顺序：先分两组说方向（炎症越重、疼痛也越重 / 炎症越重、疼痛反而越轻），再往组里填疼痛类型，特例单独起段。这样读者先拿到规律，再看分类。数量词（四类/三种/六条）写完必须数一遍实际条目数。
0j. **转折处用「则／却」，但不做机械替换**（用户原话：「我不是要你把『就』全部换成『则』，而是要你在一些转折的地方用『则』『却』这些字」）。只在逻辑真的拐弯的句子用：方向**却**随状态而变 / 长期结局**却**更差 / 到了慢性阶段**则**可能失控 / 方向**则**可能相反。其余「就」保持口语本色。
0k. **句式别写成小学生作文**：`对临床的直接含义是 X`、`这种轻不是好消息`、`看起来像…在承担修复任务` 这类主谓宾平面句要改成人话，例：`因此临床上需要根据不同分期选择相应的抗炎手段`。写完每段读一遍，拗口或稚气的那句重写。
0l. **封面文案不能平庸**：`X和Y 关系会反转` 这种平铺直叙会被打回（「这个文案太普通了，真的是 dbs 写的吗？」）。封面必须带立场/反差/数字，按 `dbs-xhs-title` 给 3–5 个带公式编号的候选让用户挑，Top1 先出图。
0l-2. **封面文案不得与标题同义**：两者分工是「标题让人对号入座，封面让人愣一下」。标题是「炎症越重，未必越痛」时，封面就不能写「炎症越高疼痛未必越重」，要换成「同样的炎症 两种相反的痛」这类反差句——同义重写等于浪费一个位置，用户会直接换掉。改封面前先把新文案与标题并排读一遍。
0m. **团队/机构只在真有名气时点一句**（用户口径：「比较著名的你就提一下，不著名就算了」）：首段一句话说清“哪家机构 + 谁领头”就够，例：「研究团队来自麦吉尔大学 Alan Edwards 疼痛研究中心，末位作者 Luda Diatchenko 是加拿大卓越研究主席」。不堆头衔、不写自我判断式形容词（「国际最集中团队之一」这类需删）。头衔必须可核（官网/机构页），核不到就不写。作者与单位另存到文档「出处」节，别塞进正文。
0n. **首句要有润滑，不能写成主谓宾电报句**（用户原话：「太干了，缺乏一些过渡措辞润滑」）：结论句必须带连接成分——`只需…就能…` / `把…拉到…` / `…却没有赢` / `没想到…`。反例：「进入维持阶段后加一个双抗，中位总生存从12.7个月延长到21.1个月。」正例：「进入维持阶段后，只需加一个双抗，就能把中位总生存从12.7个月延长到21.1个月。」
0o. **中文语序：主语做动作**（用户原话：「主语发布了谓语，不要写成xxx在xx公布这种被动物体放在前面的写法」）。反例：「3期XXX研究在欧洲肿瘤内科学会（ESMO）2026年会公布」；正例：「XXX研究团队在欧洲肿瘤内科学会（ESMO）2026年会上公布了这项3期试验的结果，论文同期发表在《…》」。主语是团队/作者，动词是公布了/报告了。
0p. **试验术语一律落地，而且必须落在首现处**：用户两轮批过同一件事——「这里才解释…前面就该备注了」、「又知道备注了，为什么备注不放在第一次出现的地方」。规则：**任何缩写/术语的第一次出现就带括号注释**，后面不再重复注释、只用缩写或「该药」。要落地的包括：`arm/臂` → `组`；`亚组` 前文没交代就改成「把患者按转移部位分组后…」；非劣效（＝要证明「不比标准差」而不是「更好」）、界值、数据成熟度、BICR（第三方影像团队判读）、ctDNA、pMMR、CRS、高表达。
0p-2. **括号里的检测参数也得白话**：`免疫组化3+且≥90%肿瘤细胞`、`FISH≥10拷贝` 这类不是解释而是黑话，要写成「免疫组化3+且≥90%肿瘤细胞（即染色最深、几乎全部肿瘤细胞都染上）」「FISH≥10拷贝（即每个细胞里该基因拷贝数≥10）」。
0p-3. **百分比不许裸露**：`数据成熟度53%` 这种写进 ▫️ 块会被问「53% 突然冒出来、没有前言后语」。做法：数据块里只写读者能读的限定语（`HR 0.68，随访尚未达预设事件数`），百分比的含义放到段末一句白话或 ⚠️ 里。
0q. **同一个东西只用一个称谓**：先说 DLL3 又改口「双抗」会被问「生怕别人知道你的主语到底是谁」——同一对象统一叫一个名字，或以「它」承接。比喻被否（如「门牌」）就换直说，不要换个比喻再试。
2d. **「具体癌种＋具体药名＋具体疗效数字」三件套是机审首要雷区**（用户 2026-10 拿小红书 AI 审意见回来，判定这是目前风险最高的一类）：三件套全齐时容易被判「医疗功效宣称」。降级三招，缺一不可：
  - **句式**：首句改成客观陈述——「试验组中位总生存为21.1个月，对照组为12.7个月」；**禁用强功效句**：`延长到 / 提高到 / 降低风险 / 只需…就能… / 多活 N 个月`。
  - **药名**：研究药只保留一次且写成「一种双特异性抗体（Tarlatamab）」；对照药只用类别（「免疫检查点抑制剂」），不点具体名。
  - **导向句**：`支持成为新标准 / 指导临床决策 / 直接改变实践` → `为后续治疗策略的探索提供了参考`。
2e. **定位声明放在「数据块引导句」里，不要悬在首段末尾**：写成「研究公布的数据如下（本文仅作数据转述，不构成任何医疗建议）：」放在 ▫️ 块前一行；如果硬放在首段末尾，下一段往往还是背景，读者会觉得「下面并不是数据」。结尾那句「本文为科研文献解读…」照旧保留，两头都有。
2f. **封面不能写功效承诺**：`多活8个月`、`生存期翻倍` 这类把风险从正文搬到图上，等于白降级。封面只写反差或方向（例：「维持期 多了一个选项」），具体数字留正文。
0r. **看着像常识的临床词也要给判断依据**：`进展`、`耐药`、`缓解`、`可评估` 这些词医生熟、但读者不知道具体指什么。用户会直接问「就一个『进展』，怎么进展的？」。首现就地补一句标准口径：`治疗后肿瘤再次长大（影像上病灶增大或出现新病灶，医学上叫疾病进展）`；后文再用「进展」就不用重复。
0s. **写中文全称前先核权威指南，并回填依据**：用户会问「你确定一下是不是这个」。做法：用国家卫健委诊疗指南 / CSCO 指南核对（例：EGFR＝表皮生长因子受体（epidermal growth factor receptor），《原发性肺癌诊疗指南》与 CSCO 肺癌指南均如此写），核对结果与依据写进文档「出处」节；不确定就只写英文缩写，不硬编中文名。
2g. **「全球首个」「首次」「获益」「改善」一律不写（用户 2026-10 口径，比小红书 AI 的建议更保守）**：即使事实成立，「全球首个……总生存获益」叠加会被判夸大宣传/功效宣称。价值感改由**中国团队牵头 + 规模**承载（例：「由上海市胸科医院陆舜团队牵头，在 29 个国家的 230 家中心开展」）；`获益` → `数据方向一致`；`改善` 尽量落地成具体数字。标题里也不要「首个」，用「中国团队牵头」开场。
2i. **「选药 / 建议 / 质疑」框架是机审最高危（比三件套还危险）**：标题带「选哪个」「该做什么」「是浪费时间么」、正文写「谁好谁差」「正面PK」「摆在一起比」、反复用「新药」压对照组，机审会判为处方推荐／药品对比宣传或诊疗建议。这类选题一律拉回「数据解读」转述口径：
  - 标题去掉「选哪个 / 该做什么 / 是浪费时间么」，用「头对头研究数据公布 / 结果解读 / 围术期研究数据公布」这类转述；
  - 删掉「谁好谁差一眼见分晓」；结论段改成客观陈述「试验组在…上的数值均高于对照组，结果供参考」，并补背景限定（开放标签、对照组组成）；
  - 「新药」统一改「试验组药物」或直接写药名，不再反复强调新旧；
  - 「正面PK／摆在一起比」换成中性的「头对头／直接对比」。
2h. **病程词用「发生进展」而非「长大/叫疾病进展」**：用户口径是写「治疗后发生进展（影像上病灶增大或出现新病灶）」，动词短语更自然、也更像临床表达。
2j. **试验结果报道必须有收口结论段**：骨架固定「旧困境 → 新试验 → 数据 → 注意点 → 所以这意味着什么」，缺收口 = 读者要自己拼结论（Kimi 审核原话「文章从头到尾没有说出结论」）。⚠️ 之后、定位声明之前，加一句「这项研究为<人群>补上了<某条路径/选项>；至于<悬而未决的终点>，还需更长随访或直接对照来回答」——把开头「过去只能直接切/直接手术」的旧困境和数据接成闭环。
2k. **数字自带结论，⚠️ 引用前文要有**：主要终点数字必须写 HR + P 值/是否达显著（否则「最容易被截图断章」，如 `HR 0.57，P=0.0002`）；⚠️ 段引用的任何数字（如三药组的 HR）前文数据块必须出现过，否则读者无法核对——要么补进数据块，要么删掉这条。
1. **新闻口吻**：主语写全（机构 + 认定 + 姓名 + 内容）；先事实后背景；外文机构名首现「中文全称（ABBR）」；引号只给机构原话；语气克制，不评价不感叹。
2. **收尾落在事实上**：最新进展 / 下一步动作 / 当事机构反应。不总结、不升华、不提问、不祝福、不派活给读者。
2b. **不写诊疗建议，全改成研究/指南转述**（平台机审口径，2026-10 小红书 AI 审核意见）：`临床上需要根据不同分期选择相应的抗炎手段`、`判断该不该用抗炎药`、`见到疼痛即压炎症`、`对XX科的直接用处是…` 这几类都会被判为接近诊疗建议。改法：`研究提示，抗炎策略或需根据疼痛分期调整`、`并非所有疼痛都应立即抗炎`、`该发现或为XX科后续研究提供参考`。保留事实与数字，只把“建议感/可用感”降下去。
2b-2. **药名 + 用药路径是最容易被判「药品推广」的组合**（指南类稿尤其）。两档口径，用户 2026-10 选的是更保守的 B：
  - 档 A：药名全留，但只集中出现一次、绝不与「推荐/建议用」相邻。
  - **档 B（默认）：一线主干药（如 UDCA）留名，同类新药合并成类别**（`两类 PPAR 激动剂` 而不写 elafibranor/seladelpar 具体名）、对症新药写「一种针对该症状的药物」。推荐主体改写为`指南提出可考虑…`，并补一句`具体选择需结合患者情况由医生判断`。
  - 标题/首段不强调「新药」：用官方口径（如 `首份以药物为重点的指南`），不用「首次纳入新药」这种自我表述。
2c. **医疗类稿结尾固定加一句定位声明**（在 ⚠️ 之后、tag 之前，单独一段）：`本文为科研文献解读，不构成任何医疗建议，具体诊疗请咨询专业医师。`——注意：早期口径是「不写免责声明」，后来用户拿小红书审核意见回来要求加；以 2026-10 这条为准，两者不再矛盾。加了之后重跑机检，总字数仍须 ≤1000。
3. **三档黑名单**见 `references/ai-slop-blacklist.md`：硬造动词、`真正…的是`、`比…多一…`、`不是…而是…` 高密度、套话、读者指令。
4. **术语/缩写的呈现顺序按“哪个更常用”定**（用户 2026-10 口径）：英文缩写更常用（PPAR、PBC、UDCA、HR、AUC、RCT）→ **英文在前、中文全称进括号**（`PPAR 类药物（过氧化物酶体增殖物激活受体激动剂）`）；中文更常用（糖化血红蛋白、肾小球滤过率）→ 中文在前、缩写进括号。不要用“也就是…”把两个写法串成一句。
4b. **常识词不配比喻**：`标志性抗体`、`一线用药`、`肝硬度` 这类本身含义已经在字面上的词，**不要再加“可以类比为…”**（用户原话：「这是废话，标志性抗体就是识别用的」）。比喻只给真的外行看不懂的概念（如全血 RNA 测序 = 看细胞此刻在干什么活）。
5. **tag 六个六位配比**（2026-10 用户口径）：热点大词 / 精准核心词 / 受众词 / 垂类词 + **末两位固定品牌词 `#刀客轻研`、产品词 `#SciLink`**；同义大词不同时打。只给 5 个会被 `xhs_check.py` 判 FAIL。
6. **字数**按「含标点、含空格、不含换行」的实测值报给用户，不许估。

## Pitfalls

- **中文引号一律用「」不用""**（用户 2026-10 明确：所有要加双引号的地方都用「」，保持格式一致；已写死进 skill）。
- **`block_insert_after` 的中文内容一定要用 `@file` 传**：在 shell 里把中文 `json.dumps(...).replace('"',"'")` 拼进 `--content`，会被当成字面量 `\u25ab\ufe0f` 写进文档（实测整行变成乱码转义）。正确做法：写 `/tmp/x.xml`，`--content @/tmp/x.xml`；写完 `docs +fetch` 回读看有没有 `\u`。
- **给图片块加评论**（注明生图参考图）：`drive +add-comment --doc <token> --type docx --block-id <img块ID> --content @comment.json`；elements 只支持 `text`/`mention_user`/`link`（写 `text_run` 会报 unsupported type）。图片块 ID 从 `docs +fetch --detail with-ids` 取。
- **`docs +update --content @file` 会把「同名旧文件」当成新内容静默写进去**：回写多轮时如果文件名与记录 ID 的对应关系乱了（例：三条新稿的 XML 仍叫 `moio.xml` / `clarity.xml`，而正文实际在 `reczz….xml` 里），接口照样回 `ok:true`，文档却还是旧版本。做法：① 文件统一用 **record_id** 命名，不用语义化简称；② 每次写完 `docs +fetch` 回读，用一句**只属于新版的标志句**（如「并没有带来预想的收益」）做断言；③ 列表类文档再查 `　　▫️` 出现次数＝ 0。
- **Moonshot 端点 `429 engine_overloaded_error` 会连成一片**（实测 2026-10：`api.moonshot.cn` 连续 4 次退避重试全失败，5 条稿 6 分钟只出 1 条）。不要把重试次数调高或循环等待：换通道——`api.kimi.com/coding/v1`（key 取 `~/Documents/Hermes/APIs/kimicode API.rtf`，model `k3-256k`，`temperature` 只能=1，`max_tokens` 给 6000）实测同时段稳定；再不行才退 GLM coding 端点。写稿 prompt 可以直接复用，不用改模板。
- **Kimi k3 系列是思考模型**：不关 thinking 会把 token 全烧在 reasoning 上，`content` 返回空字符串。`kimi_write.py` 默认带 `thinking={"type":"disabled"}`。
- **`kimi-k3` 只接受 temperature=1**，传 0.85 直接 400。脚本默认不传 temperature。
- **`kimi-code` CLI 的 OAuth 会失效**（`The provided authorization grant is invalid`），别修，直接用 Moonshot API Key。
- **空格算字**：正文里「2026 年 9 月」的空格平台也计数，别用去掉空格的 len 低估。
- **`block_replace` 会让被替换块的批注失效**：用户标注意见时，先本地存稿、把批注逐条落实，再整体替换。
- **`docs +update --command overwrite` 只用于「新文档首次成稿」**：此时文档里没有配图和批注，整篇覆盖最省事（`--doc-format xml` 还能一次带排版）。**已有配图／批注的文档禁止 overwrite**——会连图带评论一起清掉，改用 `str_replace` / `block_*`。写完一律 `docs +fetch` 回读定成败，不看接口的 `ok`。
- **「疫情同步推进」这类动词是 AI 味重灾区**：疫情、病例不能「推进」（用户原话「哪枱这种说法的」）；过渡句用「再看看其它州：」这种白得不能再白的写法。“好在接种量也在上升，”比“接种量也在上升。”带信息。
- **用户写批注后的两件事**：①批注要用 `lark-cli drive +list-comments --url <URL> --solved-status all` 读（`docs +fetch` 现在**不再**回 `reference_map.comments`，fetch 里找不到批注不等于没批注）；②改完用 `drive +resolve-comment --comment-id` 逐条标已解决，别让批注挂在旧 block 上变成幽灵。
- **`润色正文` 列放云文档纯 URL，不放正文文字**（用户 2026-10 口径）。DS 稿仍进 `DS建议正文`，两者不要串。
- **原文页 403 时 P2 怎么拍**：gastrojournal / 学协会官网经常 403，先 curl 看状态码，能 200 就走 `scilink-ref-style-poster/scripts/shot_offline.py`（curl HTML → 本地 headless 渲染 → 裁 3:4），并在文档里注明「原文页 403，P2 采用官方新闻页」。
- **物料库文档的「附：DS 初稿」不许拿 Kimi 原稿顶替**：那类文档是「DS 初稿 + Kimi 润色」双列结构——`正文` 节放润色稿、`附：DS 初稿` 节放 DS 稿。只用 Kimi 出一条稿、把未整理版塞进「DS 初稿」节，会被用户当场抓出来问「正文其实是不是 DS 初稿？」。正确顺序：先按房式自写 DS 初稿（主题句 + ▫️ 数据块 + ⚠️ 边界 + 6 个 tag + 定位声明，不加 📌）→ 再把初稿喂 Kimi 只做润色（事实、数字、人名机构白名单不变，禁新增事实）→ 表内 `DS建议正文` 存初稿、`润色正文` 存润色稿。
- **指南/清单类稿件最容易一口气踩三个坑**：①把六条推荐当清单子甩出去不给主题引导；②每条用电报体（冒号＋名词），为了控字数把解释砍光；③把原文的对照语（compared with no treatment）压成「而不是不治疗」这类临床上不存在的方案。写完先问三句：这几条是什么关系？每条读者能看懂吗？每个「而不是」能回原文对上吗？
- **字数不是第一优先级**：平台上限 1000，但用户真正反感的是「为了少写字而少写字」。指南类目标 850–950 字，压缩对象是无信息量的修饰（有多高 / 这件事 / 一份），不是解释与比喻。
- **写回后必须列表回读验证，不信接口的 ok**：改完节点位置/记录字段，用 `wiki +node-list --parent-node-token <父>`（返回里是 `data.nodes`，不是 `items`）或 `base +record-get` 回读实际值。凡是「API 说成功但列表没变」的地方，以回读为准；无法回读验证的变更不要向用户报完成。
- **`xhs_check.py` 的两条非问题别追**：`缩写首现未带中文名` 是 INFO，中文全称就写在同行括号里（`MMR（麻疹、腮腺炎、风疹联合疫苗）`）时属误报，不要为它重写句子；`emoji 分类标记` 的 WARN 也来自本账号房式允许的 `⚠️` 口径行。只看 FAIL，WARN 逐条判断后可以在交付说明里写明保留理由。
- **规范更新后旧稿要回归对齐**：本 skill 是活规则（禁用 📌、▫️ 续行缩进、单行文案下移、段间空行都是后来加的）。写完新稿后把同目录最近几篇当成一批看，**上一批可能还停在旧规范**，审查时当成必提项，别让同一个账号两种排版。
- **研究类型别含混过关**：只写「观察性研究」会漏掉「二次分析 / 多队列再分析」这类关键信息；写前先定类型、写进 ⚠️ 首句，用户会直接问「这是综述还是啥」。
