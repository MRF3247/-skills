# IEP 哲学百科逐段中英对照翻译工程

## 项目概况
- 目标：把 `/Users/Jin/Documents/Obsidian Vault/哲学百科/IEP词条/原文存档/*.md`（共 890 篇）**原地**改造成逐段中英对照版：每段英文原文之后紧跟一行引用块译文，译文由 GLM 5.3 Flash 完成。
- 完成标记（统计进度用）：文件含字符串「全部中文译文由 GLM 5.3 Flash 翻译」。
- 原件备份：`/Users/Jin/.hermes/cache/scratch/iep-backups/`（与原文件同名）。⚠️ scratch 目录闲置内容可能被系统清理，勿当长期保险；若文件被污染需要还原，先确认备份仍在。
- 恢复进度：用 execute_code 按完成标记统计 done/todo，未完成的按文件名字母序取下一批（每批 4 篇并行，用户授权连续推进不停问）。

## 派发契约（delegate_task，每批 4 篇，role=leaf）
每篇任务的硬性规则（直接复用）：
1. **原文一字不动**：按行号程序化插入；译文行必须**包成单元素列表再 extend**（直接 extend(str) 会逐字符展开爆稿）；译文插在原文**之后**不是之前。
2. 换行符二进制检测（CRLF/LF）原样保持；成品无双重 \r；总行数 ≈ 原行数+插入数（防爆稿检查）。
3. frontmatter（结束 --- 之前）插 3 行 YAML：`translator: GLM 5.3 Flash`、`translation_date: 2026-10-26`、`translation_format: 逐段中英对照…`；无 frontmatter 的短文在文件开头新建。
4. 首 H1 后插折叠译注 callout（`> [!info]- 译注（点此展开）`，含 10–25 条术语对照 + 人名对照）；正题 H2 后插「**译**：中文标题（English）」；目录末项后插「> **译**（目录）：」译块（`### Table of Contents` 标题本身不加译行）；每个正文段后插单行「> **译**：完整中文翻译」；##/###/#### 标题后各插译行；纯公式行、代码、`<!-- -->` 占位不译，承载内容的公式/表格/图后插紧凑「> **译**（表）/（图）/（式）」块；参考文献条目保留原文并在节标题译行后加「> 注：…保留原文…」；文末作者块后插「**译**：」+姓名/邮箱/大学/国家中文版。
5. 术语用学界通行译法、首次出现括注英文原文；人名通行中文译名；中文弯引号“”。源文的拼写/语法笔误按原意翻译、不改源文，不要在回报里逐条报笔误（每批都会遇到，报了也不改）。
6. **写回必须一次完成**：先在内存组装完整成品、自验全过再写入，绝不写半成品；备份已存在则不覆盖。
7. 写回后自验并打印：原非空行数＝保留数（子序列逐行比对）、插入行数、「> **译**」行数、「**译**」行数、无双重 \r、抽查 5 个译行前一行是原文行。
8. read_file 可能截断超长行/超长文件，必须用 execute_code 分段补读；读完全文再译，禁止跳段压缩。超长文件（>100KB）在契约中明确要求 T1…T10+ 分批翻译字典、30+ 次调用。

## 拆段方案 v2（省 token 50-70%；>30KB 的文件用这套）
旧方案（整篇一个子代理背着全文+已写译文滚雪球）一篇烧 70-100 万 token，九成耗在上下文重复发送。**选型**：≤30KB 的小文件直接用上方老契约整篇翻（上下文本就小，拆段反添组装开销）；>30KB 才用 v2。合同模板在 `templates/iep-v2-contract.md`、组装器在 `scripts/iep-v2-assemble.py`、spec/notes/parent-inserts 组装清单在 `references/iep-v2-checklist.md`（scratch 里的副本会被清理，以技能内文件为准，每次拷到当次管线目录使用）。v2 架构：
1. parent（主会话）机械切：按 ## 标题边界把文件切成 5-8 段（~40-60 行/段）；frontmatter/译注 callout/正题译/目录译块/导言短段由 parent 自己处理（几段话直接翻，不占额度）。
2. parent 预先定死全部标题译名表 + 全文统一术语表（10-40 条，从目录+领域知识写）+ 文末作者块中文行（姓名音译（英文）/邮箱/大学/国家）——作者块译文直接写进最后一段 spec 的 notes 让子代理照抄，parent 组装时不再补翻。
3. 每段派一个全新子代理，任务书只给三个文件指针：瘦身合同 contract.md（~1.2K 字）+ glossary.md + spec-N.json（行号区间/标题译名表/输出路径）；子代理只回传插入清单 JSON（[{after:行号, text:插入行}]），**不碰词条原文**。
4. 管线文件位置：`~/.hermes/cache/scratch/iep-sections/<篇名>/`（contract/glossary/spec-N/sec-N/parent-inserts.json）+ `~/.hermes/cache/scratch/iep-pipeline/assemble.py`（组装+校验电池：原非空行全保留且子序列、行数吻合、无双重CR、frontmatter、邻接抽查）。
5. 全部 sec JSON 结构校验过 → assemble() 一次写回 → 全量校验 → 对比备份核验。目录译块锚点=目录末项实际行号（脚本算，别猜）；导言短段、frontmatter、译注 callout、正题译由 parent 翻好写入 parent-inserts.json。

## 历史坑（必防）
- **作者行可能是无 # 前缀的普通文本行**：标题扫描用 `^#{2,4} `，裸写「Author Information」的行不会命中，切分后它会混进上一段或参考文献段。建 spec 前用文本内容（裸行本身 + 后随姓名/邮箱/学校/国家的行组）找作者块；命中后在最后一段的 spec.notes 里特判：该行后插「**译**：作者信息（Author Information）」，再随作者块中文行。作者块也可能是双作者（两组姓名/邮箱/大学/国家之间夹一个孤立 `and` 行）：中文行按人数成组、孤立 `and` 译「与」，全部写进最后一段 spec.notes，插入行数按人数扩展，别套单作者模板只插 5 行。
- **切分后先跑覆盖检查再派发**：全部 spec 的 [start,end] 排序后必须首尾相接（下一段 start = 上一段 end+1），再确认每个标题行都落在某段区间内——章节标题恰好落在两段边界时容易两头漏（§4 标题与其下导言段既不在前段也不在后段）。发现缝隙：≤10 行的小缝隙 parent 自己翻好塞进 parent-inserts.json（装配器自动归位）；大缝隙延长相邻段 spec 重派。无小节的长节（如几百行的单一大节）不必受“按标题边界”限制，可在空行处再切，区间同样要求无缝。
- **文献注释分两种粒度，spec.notes 里都要写死**：①条目行内部的描述子句一律不译；②独立成行的条目间散文注释句（如 “This volume contains…”）按库内惯例要译。只写笼统的「条目间的散文句照译」会被子代理泛化成①也译（发生过一次，组装前剔除 8 条）；两种情况都明确写死后，组装前仍按备份的参考文献行号区间把该区间内不该出现的「> **译**：」行再剔一遍。
- **干跑产物不得放在分段工作目录里**：曾有 2 个子代理误入 dryrun/ 子目录，把验证干跑当任务（一个白干，一个把干跑状态当成品回报）。测试产物放目录外或派发前删除。
- **并发≥4-6 触发 RPM 429**（「速率限制/控制请求频率」，区别于周/月额度用尽的 429 文案）：6 个段代理并行时 2 个被限流。并发控制在 ≤3；任务书加防限流指令「遇 429 用 execute_code time.sleep(90) 再重试，可反复等最多 15 分钟，不要放弃」。
- **子代理回报可能与磁盘不符**：有代理报告完全跑偏（把干跑状态当成品）但 sec 文件实际落盘正确；一律以磁盘校验（JSON 可解析、anchor 在区间、标题译行与定死表逐字一致、无占位残留）为准，别只信回报。
- **同一清单跨多个分段时，处理方式要在相关段的 spec.notes 里预先统一**（逐条译 or 紧凑表译）：不指定时相邻段会对同一枚举清单（如 75 法清单）采取不同粒度（头中段紧凑表译、尾段逐条译），成品风格分裂。
- 跨段术语首现括注允许少量重复/缺漏：并行段代理无法知道其他段是否已括注，抽检时不算错误，别为此返工。
- sec 文件里裸「**译**」行是文末作者块的规定空白标记行，校验时别当错误。
- **sec JSON 插入行可能内嵌 \n**（子代理把多行块塞进一个 text）：parent 校验时查 `"\n" in text`，有则拆成同 anchor 多条单行条目（保序）再组装，否则成品混入孤立 LF。组装后复核脚本加一项孤立 LF 计数（raw.replace("\r\n","").count("\n") 应为 0）。
- **切段注意覆盖缝隙**：切分区间必须首尾相接无缝（上一个 end+1 = 下一个 start，否则中间行无人译；卡托里亚迪斯篇曾漏 L196-201）。写 spec 后用脚本断言全区间连续且并集=正文区间。标题行/导言段若落在 parent 责任区，parent-inserts 要补齐。
- **TOC 项数 vs 标题数「差 1」先配对再下结论**：用 strip_num 剥编号后逐对匹配；Author Information 不进 TOC，手工数标题数容易把它误计入而虚报差 1。配对全对齐才把 TOC 块写进 parent-inserts。
- **parent 自写的术语表/标题译名表会被子代理逐字照抄**：表里一个错别字会原样落进所有段的成品（术语表派发前自己校读一遍；组装校验时对表内术语在成品里抽查实际写法，发现错字先改 glossary 再 patch 各 sec JSON，别让错字进成品）。
- **429 限额残稿**：GLM 5 小时限额中断时子代理可能已写入半成品（骨架完整但段译缺失，如 Autonomy 漏 129 段、Bergson 漏 33 段）。重派前必查文件是否含完成标记（污染）；污染则检查完整性，不全→从备份逐字节还原再重派；契约加「写回必须一次完成」。
- **顺序颠倒**：曾有子代理把译文插到原文前面（亚里士多德总论篇）→ 契约写死「译文插在原文之后」+ 抽查译行前一行必须是原文。
- **漏译段误报**：纯公式行（>60 字符的符号串）按规则本就不单独译，核验脚本报「漏译」先看是不是公式行；被压平成逐行文本的扁平化表格同理，整块一条表译即正确，别误判返工。
- **大文件爆稿**：曾有 extend(str) 逐字符展开成 15920 行 → 已入契约第 1 条。
- 子代理回报里的路径可能有笔误（如把「原文存档」写成「原件存档」），以磁盘实际文件为准核验。
- 自验断言本身也会假报 FAIL：CRLF 文件按 \n split 后每行带尾部 \r，用不带 \r 的字符串做成员/相等比较必失败；复核磁盘时 `l == '---\r'` 找 frontmatter 结束线会先命中开头那条（索引 0）。断言前先对目标行 repr 打印核对，再下 FAIL 结论，别把断言 bug 当成品 bug 返工。
