# 交互式文档协作写作（逐章定稿）

用户（中文运营/产品人群）常用工作流：要求代理创建一份方案/报告文档，**一章章写、逐章过**（"先从第一个章节来过"），用户在 Obsidian 里直接修改已生成的内容，然后说"我改好了，你读一下继续写"。

## 触发条件
- 用户说「一章章写」「一章章过」「我跟你一章章过」「先大纲后逐章」
- 用户说「我改过笔记了」「我改好了你读一下」「以我修改过的稿件为准」
- 场景：运营方案、内容策略、调研报告等长文档的协作定稿

## 核心规则（用户明确纠正过，违反会被投诉）
1. **续写前必读当前文件**：用 read_file（或 terminal cat 兜底）读取文档，对比自己上次写的内容，识别用户改动
2. **以用户改过的版本为基准**：只追加新章节，绝不覆盖/重写用户修改过的部分（用户原话："不然我改完了笔记你写新的部分又把我改过的盖掉了"）
3. **只追加，不重写整文件**：新章节用追加（terminal python append 或 patch 插入），不要 write_file 覆盖整个文档
4. **尊重用户的格式改动**：用户会重排表格（加空格对齐、改列名、改结构）、删小节、改措辞——续写时保持用户的新格式，不要"纠正"回自己的格式

## 步骤
1. 用户确认上一章 OK 后，先读文档当前内容（read_file；若报 binary 误判则用 `cat` 读，文件实际是 UTF-8 文本时 read_file 可能误判）
2. 识别用户改动点（对比上次写的版本），确认无冲突
3. 用 append/插入方式写入下一章，**只动新增部分**
4. 汇报：说明识别到的用户改动（证明读了）+ 新增章节内容要点
5. 每章写完停下等用户确认，不连续写多章

## 用户会在文档里留待办/任务
- 用户会直接在文档里加「待办」清单（如「留两个待办，等方案写完了要写 XX 报告」）——续写时**保留**这些待办（可放进附录的待办小节），方案完成后主动跟进执行
- 后续报告/分析产物用户可能要求**以附录形式追加到同一文档**（「直接更新到这个内容运营方案下面，以附录的形式呈现」）——追加 `## 附录 A/B`，不要另建文件

## Pitfalls
- **先确认协作模式再动笔**：用户说「帮我参谋/辅助我写」时≠代写——先给结构提案（章节+每章写法+运营主题/分线设计）让用户确认，再按确认的模式推进；不要上来就生成成稿（2026-09-23 用户纠正）
- **read_file 误判 binary**：Obsidian 编辑过的 .md 偶尔被 read_file 判为 binary（file 命令显示实际是 UTF-8）——用 `terminal cat` 或 `file` 命令确认后读取
- **删除/排除性操作用户会反悔**：用户在 B站对标工作流里先要求"剔除非科研选题"后要求"全部回滚还原"——删除前保留可回滚路径（移到独立文件夹而非 rm），删除/排除类操作先做备份或确认
- **用户改稿常删细节**：用户会把代理写的具体指标、前提说明、引言行删掉（"不要内容侧目标，我不知道定什么目标"）——续写时不要试图补回被删的内容
- **章节编号冲突**：插入新小节时注意编号重排（如插入 2.2 后原有 2.2 变 2.3），用正则提取章节标题验证顺序
- **表格列名/结构**：用户可能要求"新建一列整合"（如对标参考列）或删掉整节——按用户指令重构，保留其列结构
- **用户会重排表格格式**（改空格对齐/列宽）导致 patch 精确匹配失败（assert old in txt 崩）——用「定位起止位置（find 表头/下一个标题）+ 截取实际文本替换」替代精确字符串匹配；找不到就先 cat 读当前实际内容再构造 old

## 用户偏好（此类文档写作）
- 不要替用户定"目标"（内容侧目标、粉丝目标等）——用户会明确"不要内容侧目标"
- 受众/策略判断用户给结论，代理负责用数据支撑（评论区原话、账号数据）
- 文档放 医时知识库/内容增长/，frontmatter 用 date: + tags + related（wikilink 关联相关文档）
