# 超长素材：拆章节 → 并行子代理 → 机械组装

## When to use

单份素材长到**顺序读一遍就要吃掉几十万字符**，而用户要的是**多份结构化产物**（完整原文/逐字稿 + 分章摘要 + 可复用选题库/条目库/清单）。典型：4 小时公开课、整本书、几十份访谈、长报告合集。

不适用：素材本来就能一次读完（直接读）；或者只要一份摘要（顺序分块更快）。

## 核心原则

**父上下文只放「结构与指针」，不放正文。** 正文在子代理的文件里流转，父代理只做分组、契约、组装、核验。这样 20 万字符的素材也不会把主会话撑爆，且 10 个章节组能同时在跑。

## 流程

### 1. 先要结构，再切块

素材自己带的结构永远优先于你切的结构——它保证章节标题、时间轴、顺序都是「原作者的」，用户回原片/原书能对上。

- 视频：拿官方章节表（描述栏时间轴）→ `yt-dlp --skip-download --print "%(chapters)j" <url> > chapters.json`
- 书/长文档：拿目录（`##` 标题树、PDF outline、EPUB nav）
- 都没有：按固定长度切 N 段并在交付物里说明「段落为机械切分，非原文结构」

按结构把素材切成 `chapters/NN_*.txt` 之类的分节文件，**每节首行保留定位信息**（标题 + 起止时间戳 / 页码），后续所有产物都靠它回链。

切完立刻打印一张 **「文件名 → 首行标题」对照表**（`for f in chapters/*; do echo "$f | $(head -1 $f)"; done`）。派任务时路径和内容描述**都从这张表复制**，不要凭序号推断——序号一旦和内容错位，子代理会各自按内容纠正，产出比报错更难收拾。

### 2. 贪婪装箱分组（≤10 组）

`delegate_task` 单次并发上限是 10，所以组数就定在 ≤10，每组约等于「总字符数 ÷ 10」的 1.1–1.15 倍。顺序扫，超上限就开新组，**尾部小章节并入前一组**，不要留空组或单章节的尾巴组。

非连续章节可以放进同一组（组装时按编号重排即可），但同一组内的顺序要保持，便于子代理连贯理解。

### 3. 给子代理的契约（每个任务 context 自包含）

子代理**看不到本次对话**，所以每个任务的 context 必须重复给齐四块：

1. **背景**——素材是什么、受众是谁、产物给谁用、风格要求（术语要配大白话？情绪基调？）；
2. **文件清单**——绝对路径，标明「顺序即输出顺序」；
3. **输出格式**——照抄的模板（见 `templates/subagent-chapter-contract.md`），要求它不要加代码围栏/前后缀，便于机器合并；
4. **落盘与回报**——写到自己那一组的文件、**只回一行确认**（路径 + 覆盖哪几节 + 条数）。

硬规则一定写进 context（漏哪条就会收到哪类脏输出）：不许编造原文没有的内容，原文没讲清的写「原文未展开」；数字与专名以原文为准；每条产出必须能独立成篇。

### 4. 组装：一定会有格式漂移，按规则归一化

子代理的格式漂移是常态，不是意外。合并脚本至少要处理：

- **多重强调符号**（`1. ****标题**`）→ `re.sub(r'\*{4,}','**',s)` 再重写条目首部；
- **条目编号**→ 按节顺序重排成全局连号，用户才能按编号引用条目；
- **引文与源文本不一致**→ 若源素材本身无标点（自动字幕、OCR 稿），把子代理引文里「句号 + 空格 + 大写字母」还原成空格 + 小写（`re.sub(r'\.\s+([A-Z])', lambda m: ' ' + m.group(1).lower(), s)`）；
- **多值字段统计**→ 拆分分隔符时**全角斜杠一起拆**（`[/／、,，]`），否则同一标签被算成两个；
- **缺节检查**→ 期望节数 vs 实得节数，缺的立刻补齐重跑，别默默少一节交付。

### 5. 交付与核验

1. 纯文本产物优先**一次成型**：飞书用 `lark-cli docs +create --doc-format markdown --content "@./doc.md" --parent-token <wiki node_token>`（`@file` 只吃 cwd 相对路径）。多份文档先建父节点（`wiki +node-create`）再挂。
2. **回读核验才算完成**：`docs +fetch --doc <id> --doc-format markdown --as user --format json` → `data.document.content`，数标题数/条目数/字段数，与源文件对上。子代理自报的「已完成」不算证据；回读字符数略少于源文件（缩进归一化）属正常，**以结构计数为准**。
3. 本地留全量中间件（分节稿、每组产物、组装脚本、来源信息），脚本要能重跑。
4. 交付前清掉**过期中间件**（被替换的旧版本、旧脚本），否则用户回头核对时分不清哪份为准。

## 坑清单

- **分节文件名与「第 N 节」必须成对校验，不能凭序号推断**。把「第 7 节」的路径写成 `07.txt`、而 `07.txt` 实际是第 8 节的内容时，子代理读到不符不会报错，而是**自行按内容纠正**：lesson 字段填的是任务里那个错序号、page/time 却来自真实文件；更糟的是两个组会重复覆盖同一节（一个组按描述找、一个组按路径找），合并时还得重映射 + 去重。派任务前用对照表核对一遍，成本 10 秒。另外在契约里加一句「回报必须写清你实际读了哪几个文件（文件名）」，子代理自己纠正错位时就能在回报里暴露出来，不用等到合并时才发现。
- **字符串相似度去重只能清掉字面重复，抓不到同义改写**。两个组覆盖同一节时，同一知识点会写成两种措辞（「知网是综合性知识资源库」vs「知网是综合性中文库」，difflib 相似度只有 0.6 上下，字面去重放行）。字面去重后必须再按节喂 LLM 做一次语义归并（340→278 那一步）；归并 prompt 要写死「只合并讲同一件事的、独有信息一条不许丢、合并≠删除、事实数字专名不动」，否则它会顺手删条目。
- **子代理的自报不可信**：它说「9 章、39 条」可能是真的，也可能漏了一段没读。合并前用脚本数结构，交付后用回读再数一遍。
- **别把正文收进父上下文**：让子代理只回一行。一旦它把 2 万字摘要塞回 summary，父会话的收益就全没了。
- **组别太大反而更慢更差**：单组超过 ~3.5 万字符，输出容易被截断或敷衍。宁可多开一组。
- **组装脚本要幂等**：中途补跑某一组时，重跑组装脚本必须直接覆盖出正确结果，不要让用户手动拼。
- **「全片速览」单独一次调用**：让一个子代理只读汇总后的摘要写导览，别让 10 个子代理各写一段导览再去重。
- **产物的定位信息不能丢**：时间戳/页码/节标题是所有产物的回链锚点，任何归一化都不能删掉它们。
- **原地插入式改造（如逐段中英对照翻译）的三类翻车点**（IEP 词典 890 篇实战）：① Python `extend(译文字符串)` 会把字符串逐字符展开成几千行爆稿——译文必须包成单元素列表 `extend([line])`；② 插入顺序可能被写成「译前原后」——契约必须写死「译文插在原文之后，不是之前」，且父代理要程序化抽查「每个译行的前一行是非译行」；③ 契约自检必须含四项：原非空行 100% 按序保留（子序列比对）、frontmatter 插在结束 `---` 之前、无双重 `\r`、总行数 < 原×3+500（防爆稿）。
- **供应商 5 小时/每周限额把整批子代理打挂（HTTP 429）时的处置**：报错里带重置时间；重派前先程序化确认目标文件干净。多数情况子代理死在写盘前（无译文标记＋行数与备份一致＝干净）；**但也会死在写盘中——文件已有译注标记但段译块数远小于原段数＝骨架残稿**（frontmatter/作者块已写入、正文未译，IEP《自主性》实战）：先从备份还原（还原前验证备份无译注标记，还原后逐字节比对），再重派。备份目录同名复用时**已存在的备份不覆盖**（它就是原件）。限额重置后用**原文照抄的同一份契约**原样重派，并给契约追加两句：「备份已存在则不要覆盖」「写回必须一次完成：成品全部自验通过后才落盘，绝不允许写入半成品」——契约做得自包含就是为了这一天。
- **父代理核验的误报要先定性再动手**：「长原文段（>60 字符）后必须紧跟译行」这条检查会把纯公式行报成漏译（符号串超 60 字符，按规则本就不单独译、用紧凑译块处理）——先看上下文，前后散文句都已译就是豁免，别盲目返工。另外子代理回报里的文件路径可能有笔误（如「原文存档」写成「原件存档」），核验一律以磁盘上的真实文件为准，不信回报文本。
