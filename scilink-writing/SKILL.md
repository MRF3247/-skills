# SciLink 小红书图文成稿（dbs 编排版 v1.0）

> **对外名字：SciLink-writing，简称「writing skill」**（用户 2026-11 定，原名 `scilink-xhs-writing`）。目录与 `name:` 必须保持 ASCII 小写连字符（大写会让部分运行环境加载失败），所以文件标识写 `scilink-writing`；跟用户对话时用「SciLink-writing」。

一句话：**素材 → dbs 定结构与标题 → Kimi 新闻口吻成稿 → 脚本机检 → AI 味与风险复检 → 落盘（可选写回飞书）**。全流程可复现，不靠手感。

产出规格固定：正文 ≤1000 字（含标点、含 tag），tag 恰好 6 个，**末两位固定 `#刀客轻研` `#SciLink`**（品牌词＋产品词），标题 ≤20 字。

**字数预算先算好再动笔**：1000 的上限里，6 个 tag 约占 35 字、开头的括号定位声明占约 42 字（`（声明：本文为科研资讯解读，不构成任何医疗建议，具体诊疗请咨询专业医师。）`），所以**正文实际只能写到 920 字上下**。写完才发现 1024 字再往回压，会连砍四五轮、每轮都动到事实句（实测一篇从 1065 压到 1000 压了四遍）；正确顺序是先按 900 字设计骨架再写。

**默认三件套（2026-10 用户口径：不用再点名，每篇新稿都做）**：
1. 本地成稿 → `~/Documents/Hermes/小红书成稿/YYYY-MM-DD_<短标题>.md`
2. **建「资讯内容选题库」子文档 + 回填 `物料文档` 链接（必做，别跳过）**：每条从选题库挑的选题写的新稿，必须建一个云文档子文档，并把 `物料文档` 列回填成该文档 URL。用户 2026-10 强调过两次（「从选题库里挑的选题写的新稿子要作为选题库那个云文档的子文档放进去」「到底要我说几次」）——只填文字四列、不建子文档、不回填链接 = 没交稿。父节点与命令见 Step 8
3. 回填表格字段：**先 `base +field-list` 现查当前有哪些列，只填存在的列**——列会被用户增删（实测这张表已精简到只剩 9 列：内容标题/话题度/内容分类/原文发布日期/来源链接/DOI链接/获取方式/是否采用/物料文档，原先的「图文建议标题 / 封面建议文案 / DS建议正文 / 润色正文 / 系列」全部不存在）。照旧字段清单硬写会整批写不进去或写错列。`物料文档` 是必须回填的那一列。

用户只说「帮我写稿」「写一篇」时，这三件就是默认范围，**不要再问放到哪里**；只有生图是例外——用户不说生图就只出稿。

> **零空格铁律（用户 2026-10 第三次强调，已列为一票否决）**：正文里**任何句首、任何行首、任何段首都不允许有空格**，全角空格 `　`（U+3000）也算。唯一允许出现全角空格的地方是「段与段之间那一行单独的空行段」。软换行后的句子、`▫️` 条目的续句、引用原话——一律顶格。
>
> **无序列表铁律（同属一票否决）**：`▫️` 列表条目**各自一个独立 `<p>`、相邻排列，条与条之间不插 `　` 空行段**。两个错误写法都要避：① 条目全部合成一个 `<p>` 用 `<br/>` 换行——**复制到小红书时软换行会全部消失、挤成一段**；② 每条一个 `<p>` 但中间插空行段——视觉上多出空行。判定靠回读 XML：连续 `▫️` 段落之间不得出现 `<p>　</p>`，全文不得出现 `<br/>`。生成只能调 `scripts/body_xml.py`（唯一实现，自带 `--check`）。

## 内容形式 → 版式（Step 0 先看这一条）

选题库的 `内容形式` 字段（`fldms7NLUi`，六值）决定这篇该做成哪种图文。**开写前先读这个字段**，不同值的版式骨架完全不同；不要一套版式套所有选题。

| 内容形式 | 版式骨架 | 关键差异 |
|---|---|---|
| **原始论文** | 研究设计（人群/样本量/对照）→ 主要终点数据 → 结论 → 局限与边界 | 必须交代研究类型（RCT／观察性／基础／Meta）与发表状态；数字带效应量与 CI |
| **新闻资讯** | 发生了什么 → 关键数字 → 为什么现在 → 后续动作 | 不需要研究设计表；没有自有数据就不能写成「研究发现」 |
| **政策/监管** | 正文＝官网原文逐字照搬 → 出处（文号／成文日期／发布日／链接）→ 附：解读原文 → 附：条款或指标清单 → 附件 PDF 挂文末 | 唯一需要原件的类；**用户要的是照搬原文，不是自己重写解读**（见下方固定做法） |
| **综述/观点** | 核心论点 → 支撑证据 → 反方／边界 → 落点 | 不摆研究设计，讲「这一派在主张什么、证据到哪」 |
| **企业管线** | 阶段 → 数据性质（动物/未评议）→ 时间表 → 证据等级 | 合规最重：药名类别化、证据等级前置、DOI 留空 |
| **行业生态** | 大标题 + 关键引语 + 两三个数据点 + 共鸣落点 | 情绪节奏，不摆数据表；主体是「人」不是「试验」 |

选择原则：
- **一稿只用一套骨架**，不要论文的表格配新闻的叙事，写成四不像。
- **同一选题换了形式，版式跟着换**：「某药获批」写成新闻资讯就讲事件与影响，写成政策/监管就要贴官方公告截图。
- **企业管线和政策/监管是合规风险最高的两类**，写前先看本 skill 的 2b-4、2z-3 两条脱敏口径。

### 政策/监管类：照搬原文的固定做法

用户口径：「这个选题属于国家政策新闻，建议你直接照搬官网原文，然后这个解读是另一个链接的解读，那个链接里还有两个 pdf，你要放到这个文档里」。所以这类选题**不要自己写成解读稿**：

1. **正文逐字照搬，一个字不改**：红头文件的通知标题、文号、主送单位、正文各段、附件说明、落款、成文日期、信息公开形式全抄进 `# 正文`。仍交给 `scripts/body_xml.py` 拆句（手机阅读格式照旧），但**不改写、不缩写、不调语序**。
2. **解读另起一节、单独照搬**：解读几乎总是官网的另一篇（链接挂在通知页上），放 `# 附：政策解读原文`，按解读页自己的小标题分节（起草背景／主要特点／应用要求）。**不要把解读混进正文**——两篇不同来源，混写后就分不清哪句出自哪篇，审稿人无法溯源。
3. **附件 PDF 挂进文档本身，不只写链接**：`# 附：<指标/条款>清单` 一节由 PDF 正文逐条整理（每条只用 PDF 原话，不自行解读），PDF 原件用 `docs +media-insert --type file` 挂在文末（命令与回读断言见 `references/feishu-writeback.md` 第 5c 节）。交付时点明「清单是我整理的，只要原件就说一声我删」。
4. **交付时主动说明这一版是存档稿**：公文原文直接发小红书会像转发通知。要发平台得另写一版解读正文（变化在哪、谁的台账要改、怎么落），先问用户要不要，不要自己把照搬的原文改写成稿。
5. 表格照样回填 `内容形式`＝政策/监管、`物料文档`＝wiki URL，与其它选题一致。

### 资料／教材／干货包宣传图文的做法（非资讯类，单独一套）

用户给一本 PDF／教材／资料包，要「小红书版 + 公众号版」的宣传贴时，走这一套（截图配方与文档结构见 `references/pdf-material-promo.md`）：

1. **先把 PDF 变成可截的页**：文字型 PDF 的「图文并茂」页往往是矢量表格／流程图，不是栅格图——用 `page.get_text('blocks')` ＋ `page.get_drawings()['rect']` 求内容包围盒，`get_pixmap(matrix=Matrix(3,3), clip=bbox)` 按 3 倍渲染，裁掉页边与页码。**不要整页截图**（一半是空白），也不要用 `get_images()` 挑页（矢量页会被判成 0 张图）。
2. **选页两头都要**：结构页（封面、目录）＋ 钩子页（清单、错误对照表、框架图、流程箭头图）。用户的原话是「目录截图 + 比较图文并茂的页」，所以封面和目录必须有。
3. **同一篇文档分三节**：`一、素材截图`（grid 排图 + 一行图注点清每张是什么、在第几页）→ `二、小红书版本`（标题候选带公式溯源 / 正文 / 配图顺序）→ `三、公众号版本`（标题 / 正文，图插在段间，图数量是小红书的两三倍）→ `四、待确认`（引流落点、人称、还能加多少字）。
4. **两个版本不是同一篇改长短**：小红书 5 张图、661 字级别、每条 ▫️ 都带页码可核；公众号 9 张图、1000–1200 字，把坑展开成小节（选题／开题／统计／写作／一句话很现实的点），每节配一张对应截图。
5. **云文档落点：一律建在「资讯内容选题库」下**（父节点 `DTcUwQwEBi1bTWkSdN9c09Kbnnf`，与 Step 8 同一处），标题用 `教材宣传｜<书名>（小红书＋公众号双版）`。**不要另开「内容增长／选题&创作」之类的父节点**——用户的默认家就是选题库那个节点，放别处会被直接打回（原话「你放哪去了？放 XXX 子文档啊」）。**建错位置用搬的、不要重建**：`lark-cli wiki +move --node-token <node_token> --target-parent-token DTcUwQwEBi1bTWkSdN9c09Kbnnf --as user`（迁完用 `+node-list --page-all` 回读确认，链接不变、正文与图片都跟着走）。
6. **截图之外还要出「多页拼图＋中央压字」时走 `scilink-pic`**（选页规则、等比拼格、压字风格与居中几何验证都在那边；直接调它的 `scripts/collage_pages.py`，不要在本 skill 里手搓图片）。
7. **引流口径按平台分**：小红书正文不写外链也不写微信号，落点是「评论区留『<关键词>』」，二维码只出现在最后一张图；公众号可以正文末尾写「扫码加客服」并把封底二维码单独放一张。交付时把这条口径和「要不要换成网盘链接」一起列为待确认，别自己定。

8. **用户说「用 X 版」时，先 fetch 文档找有没有叫 X 的那一节，不要自己再生成一版**：用户会直接在文档末尾手加新节（如「五、小红书版本（Kimi 版·情绪向·合规修订）」）。先把全部 `<h1>` 列一遍再动手——不列就会重新跑一遍 Kimi、交出一份和用户已有稿重复的第二版。找到了就整节搬进目标位置（见第 9 条）。

9. **整节替换 / 合并 / 删除的固定动作**（正文段落常挂在 `<h2>` 下、不是 `<h1>` 的兄弟，所以按“标题到标题”取范围）：
   - **取节边界**：`docs +fetch --doc-format xml --detail with-ids` → `re.findall(r'<h1[^>]*id="([^"]+)"[^>]*>(.*?)</h1>')` 拿每个 h1 的 id；一节的最后一个块一般是它末尾那个 `<blockquote>`。
   - **替换整节**：`block_replace --start-block-id <该节 h1 id> --end-block-id <该节最后一个 blockquote id> --content @sec.xml`（`--content` 必须 `@file`，中文直传会写成转义乱码）。
   - **把用户新加的节并进目标节**：切出那一节的 XML（从它的 h1 到文末）→ `re.sub(r'\sid="[^"]+"','',seg)` 去掉 id（新块由服务端重分配）→ 改 h1 文案 → 用它 `block_replace` 目标节 → 再 `block_delete --start-block-id <旧 h1 id> --end-block-id -1` 删掉原节。**用户在该节里写的导流设计／配图建议／差异说明一句都别删**，那是他的判断记录。
   - 删完 `docs +fetch` 回读 h1 列表，确认没有重复节、没有残留空 grid。

10. **素材截图节的定稿排法：所有素材收进一行分栏，封面占第一栏**。用户口径是「所有素材都在一行，用分栏收纳；图注写在对应分栏里，不要写在外面」＋「封面在第一页」：一个 `<grid>`，N 张图就 N 个 `width-ratio="1/N"` 的 column，**第一栏永远是封面（拼图封面或书封）**；**图注写在各栏内部**（img 之后一段 `<p>`，如「目录·上」「三五三框架 P7」），栏外不再挂一条总图注。用户删图后会留下空 `<column></column>`，整节重写时一并清掉。**img 必须直接做 column 的子块且带 `width`**——包在 `<p>` 里会被推到栏右侧（「为什么每张图都靠右了」）、不带 width 会被列宽撑开约 7 倍；机制与回读断言见 `scilink-pic` 的「落飞书：图片块的硬属性」节。先按「封面单独一块 + 多行 3 列」交过的版本会被改回一行，下次直接一行。

12. **用户手删过的内容一律不许加回，改前先 fetch 现状**（原话「我删了不少东西，你别加回来了」「修订依据、说明等引用块都删掉」）。这类宣传文档他会反复精修：删图、删说明块、删小节、合并段落。固定动作：① 动手前 `docs +fetch --doc-format markdown` 和 `--doc-format xml` 各拉一份，按 `<h1>` 列出现存节名，**以现状为准重写**（不要拿自己上一版当底稿）；② 只改他点名的那一节，其余节不碰；③ 交付时**主动列一句「你已删的我没有加回」**，点名没恢复的项（素材说明引用块、修订依据、标题候选、导流设计、差异说明这类元信息块尤其容易被顺手写回去）。他自己留着没删的元信息块（导流设计、配图建议）则原样保留，那是他的判断记录。

11. **资料分享帖的标题口径是「无偿分享➡️《资料名》」，不是「N 个坑」**：用户会给成品标题让直接用，别再套 `dbs-xhs-title` 的坑位公式去覆盖它；同时**正文里的人设要与图一致**——Kimi 版常写「我自己整理的资料」，而封面用的是书封/目录截图，二者会穿帮，交付时点出这个冲突让他选（换封面 / 换口吻），不要自己替他改。tag 也可能不带 `#刀客轻研` `#SciLink`（他那版用的是 `#硕博生 #医学研究生 #研究生日常 #开题报告 #论文写作 #科研干货`）——**按用户的版保留**，只在交付里提一句与本 skill 默认口径不同。

## When to Use

- 用户给长文 / 飞书文档 / 论文 / 新闻，要一篇小红书图文正文
- 用户给 PDF／教材／资料包，要「宣传图文」：小红书版 ＋ 公众号图文版（见上一节与 `references/pdf-material-promo.md`）
- 用户说「AI 味太重」「改成新闻报道口吻」「重写小红书」「按批注改」
- 一条稿已完成，要落盘 + 附事实核对表 + 评论区置顶出处

不适用：封面出图（用 `scilink-pic`）、B 站口播稿、公众号长文。写完之后要出「新闻速读卡」时，**卡面内容回到英文原文逐段译，不是把本文正文搬上去**（见 `scilink-pic` 新闻速读卡栏目的首条规则）；两者长度不同是正常的，不要为了对齐稿件而少译。

| 写稿 | —（Kimi） | — | 按 prompt 骨架出正文 |
| AI 味 | `dbs-ai-check` | 逐处标 AI 指纹 | 按报告回改并复跑机检 |
| 发布 | `dbs-content-risk-check` | 平台机审 / 医疗类目 / 导流 / 绝对化 | 定 tag、定评论区出处、落盘 |

**硬规则**：

1. **`dbs-content` 只做诊断和结构，不代写**（它自述「你不帮人写内容，你帮人诊断内容该怎么做」）。把写正文派给它 = 拿到一份诊断报告交差。
2. **`dbs-xhs-title` 只是公式匹配器**。每条候选标题必须能溯源到公式编号 + 原始爆款 + 为什么选，自由发挥视为没用工具。
3. 用户说「调用 dbs」时先跑 `dbs/scripts/check-update.sh`（有输出才把更新提醒放回复末尾）。

## 流程

### Step 0 · 取素材，先做事实骨架

读原稿（飞书长文：`lark-cli docs +fetch --doc "<URL>" --as user --doc-format markdown`），把可用事实按编号列成表：时间、主体、机构、动作、数字、出处。数字照抄，不换算、不四舍五入、不加「近 / 约」。

**学会／机构／厂商新闻稿的正文常被导航淹没**：`web_extract` 抓 ESMO 这类站点，head 窗口里几乎全是菜单和页脚，正文在中段。拿到返回里的 `Full text saved to: <path>` 后用 `read_file` 或按**关键数字 grep**（`82.2`、`HR 0.58`、摘要号 `LBA1`）定位正文段，**不要按 head 内容判断「原文没有这段」**——那会让你把本来有出处的数字当成编造删掉，或反过来放过真没有的。

**付费墙论文只能拿到摘要时，取材按摘要措辞走**：`curl` 拿 Nature／NEJM／Lancet 的 DOI 落地页常回 200 且体积不小，但页面 `<h2>` 列表里只有 `Abstract`、`Access options`、`References`、`Author information`——**没有 `Introduction`／`Results`／`Methods` 就说明全文在订阅墙后、手上只有摘要**。此时：① 研究设计与局限**只能从摘要原话取**（摘要里的 `Modeled risk-enriched contexts yielded predictive values…` 就是「预测值来自模型、不是实测人群」的依据，`Prospective evaluation in consecutively enrolled real-world cohorts is required` 就是「未做前瞻连续入组」的依据——这两句正好够写「不足」节，**不要因为没 Methods 就跳过不足**）；② 表格 `获取方式` 填 `付费墙`；③ 交付时说明「正文数据全部出自摘要，Methods 细节未取到」，别让读者以为读过全文。

**先查这条选题写过没有**：拿到的是 record 链接时，先看该记录的 `润色正文` 是否已有云文档 URL。非空 = 已写过，直接告知用户并把表里未写稿的候选（按话题度排）列给他挑，**不要重写一篇重复的**（用户可能只是把旧链接又贴了一次）。

**先定研究类型，再动笔**：「综述 / 原始研究 / 二次分析（多队列数据再分析）/ RCT / 观察性 / 会议摘要」必须先判定并写进 ⚠️ 首句。判据：有自己样本与方法、产出新结论 = 原始研究；在既有数据集上重做分析 = 二次分析；只在梳理文献 = 综述。搞不清就看 Methods 第一段与 `pubType`，不要默认写「观察性」。

**交付时点名素材类型**——用户会直接问「这条资讯是论文吗？还是新闻？」。三类要在交付里说清，别让他自己在页面上找：① **同行评议原始论文**（页面有 `Article` 标记、`Peer review information`、`Version of record` → 可以说「研究团队发表了」，但研究设计照实说：横断面病例对照／RCT／队列随访，四种设计的白话区别与使用场景见 `references/study-design-primer.md`）；② **会议摘要／企业新闻稿**（无同行评议，写「据会议摘要」「据官方发布」）；③ **监管通告**（新闻口径）。判页面结构：有 Methods／Results／Data availability 是论文全文，只有 `Abstract` + `Access options` 是订阅论文（全文没拿到，见上一条）。

**完成判据**：正文里每一个数字都能在这张表里找到同值同语境的一行。

**骨架里没有的数字，一个都不许写进正文或标题**——尤其是金额、经费、用户量这类「听起来应该有」的数。随口给一个数（「花了十几亿美元」）没出处，用户一追问「到底多少钱」就只能当面收回。要写钱就按 `scilink-topic` §三·7 走：先查是否披露 → 查不到用行业基准算区间 → 标「估算」。

**但「标题挂了金额」这件事，用户的口径是标题党优先**（原话：「这种时候我要标题党，没有的事就不要声明」）：标题用「耗资几十亿」而正文写「花费公司未披露，按行业基准估算量级在几十亿」时，用户会把这句**整句删掉**——审稿人要的是标题的分量，不要自我拆台的括注。正确做法：① 按他的意思删，正文不再交代来源性质；② 在交付消息里单列一句风险提示（「标题的几十亿现在正文无支撑，评论区大概率被问」）；③ 同时给一条可回滚的补丁（⚠️ 段加半句「花费未公开，为按行业成本基准的估算」），让他需要时一句话就能加回去。**不要在他的文章里留防御性声明，也不要因为被他删了就反复劝。**

### Step 1 · `dbs-content` 出结构

按它的 Phase 2（形式匹配）+ Phase 3（五维诊断）跑，只取结构结论：五段职责 + 该砍掉哪些素材。

经验顺序：「硬事实与量级 → 机制/拆词 → 为什么会发生 → 怎么被发现 → 下游代价」。离读者最远的素材（导师连带责任、机构历史撤稿率）先砍。

**完成判据**：每段能用一句话说清讲什么；砍掉的素材写成一行清单。

### Step 1.5 · 选题评估（用户问「这个新闻要怎么选题」「先不写文稿」）

这是**只出角度方案、不写正文**的指令。四步：

1. **解 record 链接 → 拉字段**：`lark-cli base +url-resolve --url '<record URL>' --as user` 拿 `base_token` / `table_id` / `record_id`，再 `base +record-get`。先看 `物料文档`（或 `润色正文`）是否非空——非空就是写过，直接说、不重写。
2. **核原文素材**：DOI 能直连就 `curl -sL -A "Mozilla/5.0" <doi> -w '%{http_code}'` 拓落地页再剔标签取摘要；PubMed 走 Step 0 的 efetch。摘要拿不到就**直接说阻断**，不要凭标题编角度。
3. **产出四块**：
   - **素材盘点表**：事实 ｜ 数字 ｜ **口径提醒**（第三列是重点：标化率 vs 粗率、占亚洲 vs 占全球、模型估算 vs 实测、筛选/随机/亚组三层）
   - **2–3 个角度**：每个写「钩子 → 给谁看 → 支撑数据 → 风险 → 可写性」
   - **结论**：选哪个当主角度 + 哪个当对比段 + 五段骨架 + 三处易错口径
   - **末尾问一句**下一步（要不要跑标题），不要自己往下写稿
4. **主角度必须自带反差或规模冲击**（「占六成却在降」「东亚九成七在一个国家」「同一种病两种走向」）。只描述「某病负担重」「某研究发布」的角度一律算没钩子，不要拿它做推荐。

**用户回了「继续」**：默认按主角度跑完 Step 2→Step 8（含默认三件套），标题给 Top3 并**直接用 Top1 落稿**（别停下来等他挑），交付末尾列「待确认」让他换标题/封面文案。

### Step 2 · `dbs-xhs-title` 出标题

3–5 条候选，覆盖至少 3 类触发器；每条标公式编号 + 原始爆款 + 一句话理由；末尾给 Top3。硬约束：≤20 字（含标点）、留悬念但不许让读者看不出讲的是什么事。

**新闻事件类选题的坑**：公式库里 #1/#7 那类悬念公式套上去会跑偏——用户会因为「标题不贴主题」直接打回。改用 #26 数字锚定 + #24 人群限定（例：「印度学者造假被查，41 篇论文撤稿」）。

**标题要吃「中国团队 / 全球首个」这类重磅身份**（用户 2026-10 原话：「这不是中国团队吗，看看有没有什么『首个』啊、很重磅的 title，受众是吃这些的」）：中国团队牵头、全球首个、多少国多少中心——只要网站上能找到出处（报告人原话、厂商新闻稿、机构官网），**标题和首段就要把它说出来**；只写数据不写身份 = 「没灵性」。查证方法：去搜报告人姓名 + 机构 + 研究代号，再看厂商 PR 里有没有 first-in-class / first global phase 3 这类措辞；**别自己造“首个”**，造了就是绝对化风险。

**选题阶段已经被用户认可的那一句，优先当 Top1，别用公式另起一条**：Step 1.5 里写进「角度 A｜…」的那句话（通常是带冲击数字的事实句）如果用户回了「这个不错」「继续」，它就是标题定稿候选，`dbs-xhs-title` 只用来补充备选与溯源。用户会直接问「你前面不是给我拟了一个挺好的标题吗，为什么不用那个」——公式生造的反差句往往不如那句直给的事实句。

**标题定稿后四处同步**（只改一处 = 发出去三个版本）：① docx 的 `<title>`；② wiki 节点标题（`lark-cli drive +update-title --url <wiki URL> --title '<新标题>' --as user`，不改节点时列表里还是旧标题）；③ 文档「图文标题」节；④ 封面主标——且**数字口径要对齐**（标题用 97% 时封面主标也写 97%，正文保留精确的 97.4%，不能让同一张卡出现两个数）。

**同步方向：以文档「图文标题」节为定稿**。用户会直接在那一节手改标题（他写的口语钩子往往比自己拟的更适合发布），此时反向把 docx `<title>` 与他版本对齐，**不要拿自己拟的标题盖他**。**但 wiki 节点标题（选题库列表里的文档名）改动前先问一句**——文档名靠长标题带期刊、标志物、数字来当索引，擅自缩短会让他在列表里找不到稿；把它写成交付末尾的待确认项，不自己改。同步完顺手看一物品类词：`减重药`／`减肥药`／`降糖药` 这类消费属性词会把稿子推进「三品一械」判定线路，发现就提示风险并给一条中性替换（保留钩子、去掉品类词），选择权交回用户、不要自作主张改。

**标题带刊名／平台前缀时先算字数**：「Nature：」「NEJM：」「柳叶刀：」这类前缀连同全角冒号占 7 字，20 字上限里正文只剩 13 字——定完标题先跑 `xhs_check.py` 或 `len(标题.replace(' ',''))` 数一遍，别等到平台拦下来。**更危险的是动词**：概念验证类研究（诊断标志物、早筛、疗法雏形）标题不能写「抽血就能查」「一次就能筛出来」这类承诺句——研究做到的是「证明有信号」，写成「就能查」等于替它宣布进入临床，医生在评论区一问「前瞻队列做了吗」就穿，而且与正文「不足」段（横断面／需前瞻验证）正面矛盾；改成「抽血发现癌前信号」「抽血可测」这类「研究做到了什么」的说法，卖点（顶刊、抽血、癌前）一个不少。用户坚持要承诺句就按他的改，改完在交付里单列一次风险提示，之后不再劝。

**完成判据**：Top1 可直接发；每条候选都能指回公式编号。

### Step 3 · Kimi 写正文

1. `cp <skill_dir>/templates/kimi-prompt.md /tmp/p.md`，填 `{{}}`：事实清单、五段职责、字数、6 个 tag（末两位 `#刀客轻研` `#SciLink`）。
2. `terminal(command="python3 <skill_dir>/scripts/kimi_write.py /tmp/p.md --out /tmp/draft.md", timeout=300)`

**完成判据**：`/tmp/draft.md` 有正文段落 + 最后一行 6 个 tag。

**Kimi 交稿普遍超预算 200–300 字**（实测 prompt 写 820–900、出来 1180；另一次目标 820 出 1317，压满四轮才到 995），预留 2–3 轮压缩，别指望一次过。**纯字数问题自己动手压，别死等 Kimi**：按整段删并（删整句、合并同类句、把「即…即…」这类重复承接删一处），每轮重跑机检拿实测字数，四轮内基本能落地；回灌 Kimi 只留给「整段重写才救得回来的句式问题」，纯压字数回灌往往又长回来。压缩顺序固定，从信息量最低的往下砍：① 数据块里后文段落会复述的那条（如「停药率」在「为什么」段还要用）；② 与 ⚠️ 段重复的发表信息（「论文同期发表于…」）；③ 时序细节（「公司何时首次公布顶线」）；④ 将「三种解释」这类长句段压成短句（保留数字与因果，删修饰）。每轮都重跑机检，不要边压边猜字数。

**批注要求「缩写换中文全称」时，字数会反向膨胀**：`Lp(a)` → `脂蛋白(a)` 每处多 3–4 字符，一篇十几处就是 50–80 字，叠加原有的超预算，会连压 3–4 轮（实测 1116 → 1007 → 998）。接到这类批注时，**先按新写法全量替换再算字数**，不要拿替换前的字数估余量；压不下时优先砍后文会复述的数据条和 ⚠️ 里的重复信息，不要砍批注刚要求补的白话解释。

### Step 3.5 · 装回本账号房式（Kimi 交的是裸稿）

Kimi 按「无 emoji、无小标题、不许劝读者」的禁令写出来是一串裸段落，直接发出去和内容物料库其它条不像。成稿前手工装框，结构固定：

```
{一句主题句：这条讲什么、为什么现在讲}

{背景段：谁 / 何时 / 什么设计 / 什么数据源}

{一句主题引导，例：这六条是一条临床路径——诊断→一线→风险评估→二线→症状→移植后}

▫️ {要点，一条一行，写成完整句而不是冒号+名词堆}

{机制 / 为什么发生 / 怎么被应对，每段一个意思}

⚠️ {口径与截止时间：数据来自哪几家机构、截至哪天、各方统计口径是否一致}

#tag ×6（前 4 个是内容词，末两位固定 #刀客轻研 #SciLink）
```

硬约束：**数据块与正文段不许复述同一批数字**。数据块先把数字列全，正文只写背景、机制、应对、最新进展；写完把「同一数字第二次出现」的整句删掉，否则读起来像一件事说了两遍（实测能削掉 60–80 字且信息不减）。

**Kimi 裸稿会自我重复**：同一条限制（开放标签、随访时长、数据未成熟）常在末段和收尾各写一遍，两句话意思几乎相同。装框时合并成 ⚠️ 里的一处，不要把两句都搬进成稿——用户会把它当成凑字。

### Step 3.6 · 用户点名「六问结构」时的成稿法

用户会直接给出他要的文档结构（例：①什么时间谁发布了什么 ②术语解释 ③以前的传统做法 ④这项研究做出了哪些创新 ⑤意义 ⑥不足之处）。这套「文献综述六问」出现时，**以用户给的结构为准，不要套回 Step 3.5 的房式骨架**（不加 ⚠️ 段、不排 ▫️ 数据块），落地四件事：

1. **六节＝六个自然段的职责与顺序，不是章节标题**（用户纠正过：「按这个结构写，但是没让你分章节」）：`# 正文` 节里直接排六段（每段可含多句，按意思分），段间照常用 `<p>　</p>`，**不许出现 `<h2>`／`<h3>`／「一、二、三、」这类章节标题**——用户说的「结构」指先写什么、后写什么，不是要小标题；附录里「第 N 段 · 英文原文」这类标签同理删掉，改用「引用块＝英文原文、紧接段落＝中文译文」的一句话说明。发布版正文＝这六段原文＋ tag，机检字数按这个口径算。
2. **正文节前加一条 blockquote 说明**：「以下六段即发布版正文，可直接复制（含 tag 共 N 字）」＋ 该稿的口径提醒（推断项、反常数值），不再提「删掉小标题」——本来就没有。
3. **定位声明仍在最前面一处**（2e／2c 不变），不属于任何一节；tag 放在第六节之后另起一行。
4. **六节的事实分工别串岗**：「创新」节装数据（研究类型、样本量、分组、逐项比较的数值与 P），「不足」节装原文自己的限定语（横断面、预测值来自模型、需前瞻连续入组队列），「意义」节只写「在什么层面提供了什么参考」，**不写「改变筛查／带来转机」**。

六问结构天然比房式长（要分别交代传统做法与创新），**起稿就按「一节一段、一段一个意思」写，别在节内再分层**，全篇仍压进 920 字。

### Step 4 · 机检（不许跳）

`terminal(command="python3 <skill_dir>/scripts/xhs_check.py /tmp/draft.md --title \"<标题>\"", timeout=60)`

FAIL 的处理顺序：

1. 字数超 → 回灌 Kimi「压到 880 字以内，优先砍细节不砍事实」。
2. 命中 A 档句式 → 把具体句 + 改法回灌 Kimi 重写整段；**不要手动删两个字凑数**（会写出断句）。
3. tag / 标题不合规 → 直接改，这两项不需要模型判断。

**完成判据**：退出码 0，输出 `→ PASS`。

### Step 5 · `dbs-ai-check` + `dbs-content-risk-check` 复检

- `dbs-ai-check`：按文本顺序逐处看报告，重点看脚本抓不到的两项——**段段收金句**、**整段可删而信息不减**。
- `dbs-content-risk-check`：正文不能有外链（出处放评论区置顶）、无医疗功效表述、无绝对化词、无导流。医学科研选题的 tag 避开 `#医学科普` `#健康科普` 与病名科室词。

**完成判据**：两份报告无未处理项，或已写明为什么保留。

**定稿前走两道外部审（2026-10 用户定的固定顺序，别省）**：① **Kimi 先审（外行视角）**——专抓 headline 术语没白话、数字口径/顺序/分层/发表状态硬伤、缺少收口结论；② **点点后审（合规视角）**——专抓机审风险（选药框架、三件套、绝对化、药企名＋阳性）。两道都过才算定稿；意见回来先出整改方案再动手（Step 9）。

### Step 5b · 用户写了批注时（两轮以上很常见）

1. **先出整改方案，别直接改**：用户批注后的标准提问是「你告诉我你准备怎么改」。回复格式：逐条对应（原文 → 改法），能写出改后句子就直接写，并说明连带影响（字数变化、哪些部分不动）。他回「确认/改吧」再动手。
2. 改完：重跑 `xhs_check.py` → 回读文档 → 逐条 `drive +resolve-comment`，并在本地成稿末尾记「批注处理记录」。
3. 同一篇常被批 2–3 轮，每轮只动被点的部分；标题、封面、图片、出处、DS 初稿节默认不动（除非点名）。

### Step 6 · 事实核对表

正文说法 ↔ 原文出处，一行一条，放交付文件末尾。**表头四列：正文说法 ｜ 出处（原文原句）｜ 状态 ｜ 说明**。

- **状态只有两个值：`实锤`（原文能逐字对上）与 `推断`（流行病学／统计学常识推出来的，原文没有这句）**。有推断项必须双写：表里标 `推断` ＋ 文档说明 blockquote 点名（例：「第 6 节『某病罕见会拉低阳性预测值』为流行病学推断，摘要原文没有这句话」）。用户会拿表逐条问，混在一起的代价比标出来大得多。
- 涉及口径的条目在「说明」列写清（vs 左右谁是哪一组、AUC 反向、样本数是筛选还是随机）。

**完成判据**：不存在「正文有、原文无」的行；每个 `推断` 项都在文档里被点名过。

- 写回飞书：按 `references/feishu-writeback.md`，写完必须 `+fetch` 回读验证。

### Step 8 · 子文档与表格链接（物料库固定口径）

0. **会议／事件专题的文档名要带前缀**：用户口径「ESMO2026｜」这类前缀打在标题最前（全角竖线 `｜`，不是 `|`）。新建时一次写对：`--title 'ESMO2026｜<内容标题>'`；已建好的用 `lark-cli drive +update-title --url <wiki URL> --title 'ESMO2026｜…' --as user`（`--type wiki` 传 node token 也行，node 与 doc 标题会同步）。没有 `wiki +node-rename` 这个命令，别找。

1. **文档建在「资讯内容选题库」下**：`lark-cli wiki +node-create --parent-node-token DTcUwQwEBi1bTWkSdN9c09Kbnnf --obj-type docx --title '<内容标题>'`。
1a. **`+node-create` 的返回是扁平字段，不是 `data.node.xxx`**：token 直接在 `data.node_token` / `data.obj_token`，按嵌套结构解会得到 `None`，看着像创建失败。**拿到 `None` 时先跑一遍 `+node-list` 查重，不要直接重跑**——重跑会再建一个同名空文档（实测建出两份，只能手工删掉一份）。
1. **文档固定结构（用户 2026-10 最终定，顺序不得变）**：

```
<title>ESMO2026｜<内容标题></title>
# 封面与截图      ← 四栏并排：封面（无文案）/封面（带文案）/P2/P3；下方引用块放参考图（小图~420px）
# 封面文案
主标：<专题名，成组专题才有；普通单条不写>
副标：<这一条的具体文案>
# 图文标题
<标题正文>
# 正文
<逐句一段的正文>
# 出处
# 附：原文与译文（英文原文 ＋ 中文译文）
```

   - **封面与截图放最前面**（用户 2026-10 口径：先让审稿人看到图，再读文案），原来放后面的做法作废。
   - **附录固定放「原文与译文」，不再放 DS 初稿**（用户 2026-11-09 新口径：「这些原文的英文和中文译文也需要列到稿件的附录里，反而是那个 ds 初稿已经无所谓了」）。做法：按来源文件的**核心章节**分小标题（英文标题 ／ 中文标题），每节先用 `<blockquote>` 整段放**英文原文**（逐字照拄，不改写、不节选数字），紧接再用普通段落逐段放**中文译文**（一源段对一译段）。开头加一行 blockquote 说明「以下为原文与译文的对照，正文数字均出自此节」。
   - **附录「原文与译文」是每篇必附，不是可选**（用户 2026-11-09：「以后的稿子都要附上这两样」）。不论素材是论文摘要、监管通告、企业新闻稿还是指南全文，都要在文末列出：① 英文原文（逐字照抄，不改写、不节选数字、不合并段落）；② 中文译文（一段对一段，按原文小标题分节）。
   - **附录不是“好东西才写”的附加项**：正文里任何一个数字、人物、限定语，都必须能在附录里找到对应原文；找不到就说明这个说法没有依据，要么回源补上，要么从正文删掉。
   - 仍要写 DS 初稿的情况：仅当用户点名要。`DS建议正文` 列相应留空即可，不要拿正文去填。
   - 参考图一律以引用块 + 小图（宽约 420px）形式放在图 grid 下方，不占大图。
   - **列数按实际出图数定，不留空栏**：四张（含 P3）→ 四栏 `width-ratio="0.25"`；P3 与 P2 内容重复被去重、只交三张 → 三栏 `width-ratio="0.333333"`，并在 blockquote 里写明「P3 与 P2 内容重复，按规则只保留 P2」。
   - 顶部 blockquote 不再放封面文案。标题用户会自己改：回填前先 `docs +fetch` 取当前值，以文档为准。

1b. **元信息用引用块，不混排成正文**：`生图引擎：…`、`说明：原文页 403…` 这类不是给读者看的话，用 `<blockquote>…</blockquote>`。**`# 封面与截图` 节里 grid 下方那条 blockquote 写「图注」，不写封面文案**：按显示顺序一行一行点清（例：`图注：第一行＝插画封面（左无文案／右带文案）；第二行＝来源页截图（P2 页面顶部／P3 关键段刷黄）；第三行＝新闻速读卡 P1–P5`）。封面文案已经有独立一节，重复挂一遍等于两个版本待同步；多个 grid 时更要在图注里标清风哪行是哪组图，否则审稿人无法对号。

1b-2. **「正文」节里不许有任何元信息块，引用块也不行**：字数统计、结构说明、口径提醒（「这个 AUC 低于 0.5 表示…」「这句是推断、原文没有」）这类给审稿人看的话，一律不进正文节。用户 2026-11 直接把正文开头的说明块删掉，并给了口径：**这种东西要么写成批注，要么就不要写**。落地做法：需要标在稿子里的，用 `lark-cli drive +add-comment --doc <docx token> --type docx --block-id <块 id> --content @c.json` 挂到被指的那一句上（块 id 从 `docs +fetch --detail with-ids` 取）；不需要用户当场决定的，写进本地成稿文件的事实核对表，不要留在云文档正文里。

1c. **只出稿、暂不生图时的写法**（用户说「先不生图」）：`# 封面与截图` 这一节不要留空 grid，放两条 blockquote——① `图待生成：本轮按用户要求先只出稿，封面与 P2/P3 截图未生成……`；② `封面建议文案：<文案>`。这样表格字段和后续出图都有落点，文档也不会显得残缺。

1d. **表格批量更新要逐条回读**：一次 `record-batch-update` 带多条记录时，可能只生效一部分且仍返回 `ok: true`（出现过多条里静默漏一条）。写完对每条记录单独 `record-get --field-id 图文建议标题 --field-id 润色正文` 回读，别拿整体 ok 当凭据。
2. **表格「物料文档」列放云文档纯 URL**（`fldy8z10Xu = https://my.feishu.cn/wiki/<node_token>`；用户 2026-10 口径「对，贴云文档链接」）。**不要**把成稿正文写进这一列，也不要写成 `[标题](url)`（text 字段塞 markdown 会读回 None）。`润色正文`（`fldHZF29L7`）放成稿正文文字，两列不要串。
3. `DS建议正文`（`fldqTWRrDy`）仍放 DS 初稿文字；两列分工不要串。
4. **存量记录一并改**：用户说「上一篇稿子贴的是原文也要换成链接」时，把旧稿的 `润色正文` 也改成它的云文档 URL，不要只改新的一条。
5. **整篇换选题（「原来那篇抹掉，换成这篇」）是四件事，少一件就留残影**：① `docs +update --command overwrite` 换正文并改 `<title>`；② `lark-cli drive +update-title --url <wiki URL> --title '<新标题>'` 改 wiki 节点标题——只改正文不改节点，列表里还是旧标题；③ 表格记录同步 `内容标题 / 话题度 / 内容分类 / 原文发布日期 / 来源链接`，并把 `DOI链接` 写成空串（旧稿有 DOI、新稿是企业稿时尤其容易漏，残留在表里就是错数据）；④ 删掉本地旧成稿文件，重写一份新的，别让 `~/Documents/Hermes/小红书成稿/` 里两版并存。
6. **子文档排序**：用户要求「子文档按从新到旧的顺序从上往下排」。实测飞书 wiki 子节点顺序＝创建时间升序（新建追加在末尾），OpenAPI **没有排序参数**：`wiki +move` 只能换父节点；`PATCH nodes/<token> {"position":0}` 回 404；`POST /open-apis/wiki/v2/spaces/<sid>/nodes/<token>/move` 带 `{"position":0}` **返回 `ok: true` 但顺序不变**——接口的 ok 不代表排序生效，别拿它当成功凭据。所以：新建后如实汇报「新文档在末尾，需 UI 拖到最上面」，并提议可选的逆序重建（会换链接、要回填表格，不推荐默认做）。

### Step 9 · 批注返工（先给方案，再动手）

用户会在同一篇稿上**多轮**批注，而且往往是「你告诉我你准备怎么改」——这是**只出方案、不改文档**的指令，不是让我直接开改。固定节奏：

1. `lark-cli drive +list-comments --url <URL> --solved-status all` 读全部未解决批注（`--solved-status all` 才看得到状态），逐条抄成「原文 → 意见」。
2. **回一份整改方案**，每条三段：原文怎么写的 → 改成什么 → **具体改写示例**（直接把新句子写出来，让用户看字感，别只描述思路）。
3. 末尾写「连带影响」：字数会怎么变、机检要不要重跑、标题/封面/图/出处哪块不动、DS 初稿那节改不改。
4. 等用户说「确认」再动手；改完 `xhs_check.py` 跑一遍、`docs +fetch` 回读、再 `drive +resolve-comment` 逐条标已解决。

**用户说「我随手改了一些东西，你先读一遍文档再给方案」时，方案要先有一张「你手改的（我原样保留）」表**，再排批注。完成判定：逐项列出他改了什么（标题、数字写法、段落合并、删句），并明说「不覆盖」。他的手改同时是**下一轮的风格信号**，要跟着学：阿拉伯数字替汉字数（「九成七」→ 97%）、标题加口语钩子（「最新数据！」这类，与禁 📃 开头不矛盾）、把短段合并、删掉多余空行——下篇直接按他的版本写，不要等再改一遍。

**每次返工都要重跑机检**：展开句子（电报体→自然语言）几乎一定撞黑名单（实例：把「换来的瘙痒改善」展开后触发硬造动词「换来」），FAIL 要就地重写那句，不要为了过检删事实。

**改稿不动的东西**：标题、封面文案、已出的图、出处段、`附：原文与译文` 那一节（原文是溯源依据，用户批的是成稿）。真要同步改附录，先问。**例外：批注本身就是点在标题/封面文案上的（如「这个标题很没灵性，应该围绕中国团队重写」），当轮就以批注为准改，并同步表格里的 `图文建议标题`／`封面建议文案`**——不要把「默认不动」误读成「批了也不改」。

**文档 0 条批注时（用户只说「这篇也改一下」「连图带文一起改」，文档是别的分支写的）**：查两遍都是 0 就认定真没有，不要再换 URL 形式反复找（wiki token 与 docx token 各查一次足够）。改为按本 skill 全量自查，交付时报三件事：**改了哪几处 → 每处依据哪条规则 → 原版怎么回退**。用户没点名时，优先改客观违规（剂量数字、P3 重复、封面是程序化绘制而非豆包、元信息混排成正文），标题这类主观项默认不动并说明。

### Step 10 · 自审（用户说「看一下我的文案和封面有什么需要改进的」）

这是 **只出审查意见、不改文档** 的指令。按四组组织，每条都要带「依据的规则 + 具体改写后的句子」：

| 组 | 查什么 |
|---|---|
| **A 必改** | 违反硬规则：元叙述标签（0e）、电报体（0c）、小学生句式（0k）、数字与正文重复（Step 3.5）、数量词与条目数不符（0i） |
| **B 建议改** | 能更好但不违规：续行缩进、方法段过长、团队句位置、研究类型写得不准 |
| **C 封面** | 文案是否平庸/与标题同义（0l、0l-2）、画面元素是否与主题错位、单行文案是否已下移、色板 Δ |
| **D 一致性** | 文档 vs 表格字段是否被手改过、旧稿是否还停在旧规范（▫️ 缩进、文案位置、📌 钩子） |

末尾给一句执行建议（「A 全改 + B 全改 + C2 改画面，C1 你挑文案」），等用户点头再动手。

**用户整篇自己重写后问「你看 OK 不」/「我自己改写了一版，提提建议，不要动我的文档」**：只审不改，按四段交付，别只回一句「挺好的」——
1. **先说改对的地方**（2–4 条，点明具体结构收益，如「三条致病路径挪进定义段，比原版塞在解释段强」）。他重写就是为了摆脱那个「读都读不懂」的版本，先确认他的判断再谈问题。
2. **硬错误逐条列**，每条给「原句 → 错在哪 → 改后句子」。高频四类：**错别字**（「均未达成」写成「均为达成」）、**术语误用**（把事件发生率写成「发病率」——事件发生率是在已患病的人里数事件，发病率是人群中新发病例的比例）、**逻辑反了**（写成「安慰剂组对照数据不足」，实际是用药组 21% 停药、对照只 7%，被稀释的是用药组）、**事实错误**（说「试验没跟踪血液指标」，而试验每年测一次）。事实类先回源核，别凭印象判他对错。
3. **取舍建议**（不是错）：哪些被删掉的信息其实在承担功能（安全性信号、后续进展、落点句），补回去大概多少字。
4. **格式提醒**：全角空格、行首空格、`1. 2.` 有序列表（贴到小红书会被识别成列表自动重排，房式用 `▫️`）。
末尾只问一句「要我按这几处改吗，其它句子不动」——**不主动 overwrite 他的稿子**。

**判「试验到底测了什么」查 ClinicalTrials.gov 登记表，不要凭摘要推**：`curl -s "https://clinicaltrials.gov/api/v2/studies/<NCT>?fields=protocolSection.outcomesModule,protocolSection.designModule"` → 看 `primaryOutcomes` / `secondaryOutcomes` / `otherOutcomes` 三组。登记终点里没有影像学或炎症终点，就说明该试验从设计上没打算回答「斑块有没有缩小」。**「测过基线拿来分层」≠「设成观察终点」**，稿子里要分开写：前者是「只在入组时查过一次、用来分组」，后者才是「跟踪了变化」。用户会追问「所以试验没跟踪吗」，这一问必须用登记表回答，不能靠摘要里的只言片语拼。

**回填前先 diff**：用户会在文档里直接手改标题（例：加上了「疼痛研究｜」前缀）与正文。改写或回填表格前，先 `docs +fetch` 取当前值、与表格字段逐列比对，**以文档里的手改版为准**，不要用本地旧稿覆盖他的编辑。

### Step 11 · 整篇按新规范优化旧稿（用户说「按现在版本的 skill 优化一下这个云文档」）

这不是批注返工（Step 9），也不是只出意见的自审（Step 10）：用户要把一篇**旧稿**按当前规则重做一遍，默认可动文档。固定五步，顺序不能换：

1. **程序体检**（先拿全貌，别凭印象）：`docs +fetch --doc-format markdown` ＋ `--doc-format xml`，五项计数——`<h1>` 列表（应六节且顺序对）、`<br/>`＝0、`　　`＝0、`<p></p>`＝0、`<img>`／`<grid>` 与实际出图数一致；再切 `# 正文`→`# 出处` 算字数。
2. **数字回源审计（最重要，别省）**：把正文每个数字列出来，逐个回原文（新闻稿／摘要／表格）grep 同值同语境。二手报道和 AI 初稿最爱凭空补三类细节——**分时间段／亚组的额外 HR**、**数据截止日期**、**「首个／唯一」定语**；原文查不到的一律删，并在交付里点名「删了哪两个数、为什么」。这一步抓出的问题通常比排版多。
3. **四处标题一致性 ＋ 品类词体检**（见 Step 2）。
4. **补该有而没有的块**：数据块四件套（0b-5）、术语首现白话（0p）、⚠️ 去重（Step 3.5）、附录「原文与译文」（v1.6 后每篇必附）。
5. **落库**：先 `drive +list-comments --solved-status all` —— 0 条批注就 `overwrite`（一次改完结构最省事）；有批注只能 `str_replace`／`block_*`（见 Pitfalls）。回读断言要同时盖住「新增块在」「该删的数字没了」「六节结构在」。

交付分四块报：**事实层删改（含依据）→ 合规层降级 → 结构与排版修正 → 待用户定的主观项**（标题、封面、被删数据要不要补）。

## 文档排版（手机阅读优先）

写飞书 docx 时正文不能一段一大块，按手机屏幕拆行：

1. **段与段之间空一行**：段落之间插一个只含全角空格 `　`（U+3000）的 `<p>`。空 `<p></p>` 虽能存活，但全角空格段在手机端更稳（实测不会被客户端合并）。
2. **普通句子：每一句都是独立的 `<p>`，不缩进、不用 `<br/>`**（小红书粘贴时软换行会丢）。拆分点：先按空行分块，每块内按行拆，行内按 `。！？` 拆句（**`；` 不拆**），每句一个 `<p>`。
2b. **`▫️` 列表条目：各自一个独立 `<p>`、彼此相邻，条间不插 `　` 空行段**。用户的口语是「只换行不空行」，但落地必须拆段落——`<br/>` 软换行在小红书粘贴时会全部丢掉（用户实测回报「复制粘贴到小红书换行又消失了」），而空行是另一个独立段 `<p>　</p>` 造成的。所以：拆成多个 `<p>`（保证换行不丢）＋不插空行段（保证不空行）。整组交给 `scripts/body_xml.py` 即可，不要手写。
   > 这条与第 2 条不矛盾：普通句子每句一个 `<p>`、段间用 `　` 隔；列表条目只是**相邻**，少的就是那个 `　`。两次翻车都出在把“例外”误读成“合成一段用 `<br/>`”——合成后复制到平台换行全丢，比空行更严重。
   > 代价：文档里行间距比原来大、看着更散，但这是为了「复制即发」的保真度付的代价，用户已确认接受。验收：`docs +fetch --doc-format markdown` 里每句/每行之间应有空行（即 `\n\n`），且 `　　` 出现次数＝ 0。
2c. **句子以「。）」结尾会被拆成两段**：`body_xml.py` 按 `。！？` 拆句，句末是「建议。）」时括号右半边会单独成一个 `<p>`（回读是「…建议。」＋「）」两段，复制到平台就是断行）。定位声明这类整句括号，**末尾不写句号**（`（声明：……不构成任何科研决策建议）`）即可避开；别为此改脚本，也别手动删那个 `）` 段了事。
3. 生成 XML 的固定写法：**调脚本，不许手写**——`python3 <skill>/scripts/body_xml.py 正文.md -o body.xml`（`--check` 只验收）。

   > **`-o` 和 `--check` 别一起指望**：两个同时传时脚本只做验收、**不落盘**（stdout 打 `OK: 行首无空格…`，文件却没生成），下一步读 XML 直接 `FileNotFoundError`。分两步跑：先 `… -o out.xml` 生成，再 `… --check` 验收。

   > 为什么固化成脚本（2026-10 实打实翻车一次）：AI 虚假引用篇里，我从会话历史里直接复制了自己早前写的 `body_xml()`——那个版本用 `<br/>` 分行并给续句加 `　　`，于是正文里又出现「句首多两个空格」，用户第二次指出。手写函数必错，脚本是唯一实现；交付前必须跑 `--check`（或回读断言），出现 `　　` 直接判失败、重排再交。

```python
# 脚本内的实现（仅供参考，不要复制去用）
def body_xml(text, spacer="　"):
    """每句/每行一个 <p>：小红书粘贴时不丢换行（软换行 <br/> 会丢）。"""
    blocks = [b.strip() for b in re.split(r"\n\s*\n", text.strip()) if b.strip()]
    out = []
    for bi, b in enumerate(blocks):
        for line in b.split("\n"):
            line = line.strip()
            if not line:
                continue
            if line.startswith("▫️"):       # 每个 ▫️ 是一个独立段落
                out.append("<p>" + html.escape(line) + "</p>")
                continue
            for s in [x.strip() for x in re.split(r'(?<=[。！？])', line) if x.strip()]:
                out.append("<p>" + html.escape(s) + "</p>")   # 注意：；不拆
        if bi != len(blocks) - 1:
            out.append(f"<p>{spacer}</p>")
    return "\n".join(out)
```

> 坑：衹按句子切不按行切，`▫️` 列表会被并成一行（因为它们行尾没句号）。两层都拆才能保住列表形状。
>
> 坑 2（用户连纠三次）：先是用「段首是 ▫️ 则后续全部缩进」，每个 ▫️ 条目都被当成上一条的续行；改成按行判断后又留着「续句缩两个全角空格」；最后为了消空行把整组合成一个 `<p>` 用 `<br/>`，结果用户复制到小红书换行全没了。**最终口径：零缩进；普通句子每句一个 `<p>`；`▫️` 条目各自一个 `<p>` 相邻排列、不插空行段、不用 `<br/>`**（见本节第 2b 条）。验收：回读 XML 无 `　　`、无 `<br/>`、连续 ▫️ 段之间无 `<p>　</p>`。

4. `正文` 与 `附：原文与译文` 两节都用这个函数（附录的英文段落**不插空行段**，保持逐段紧凑）；`出处`、`图文标题` 不用。
5. 回读验收（三项都要过）：① 全文 `　　`＝ 0；② 全文无 `<br/>`（软换行复制到平台会丢）；③ 连续 `▫️` 段落之间不得夹 `<p>　</p>`（`grep -c '<p>　</p>'` 只应出现在普通段落之间）。三项任一不过就重排再交。

## 写作铁律

0. **不写 `📌` 开头钩子**（用户 2026-10 明确口径：「没必要每条文案都加这个」）。正文第一句直接上事实——机构＋时间＋数据。参考旧稿里的 `📌 一行钩子` 一律不要照搬。
0b. **`▫️` 数据块里的每一条必须指向同一个主题**。实测被批：「前两条是疫情进展，第三条 MMR 保护效力跟疫情进展有什么关系」。拆法：数据块只放「同一件事的几个数」，不同维度的数字（疫苗保护效力、政策口径）拿出去写进段落。
0b-2. **数据块必须有「结论线」，不是数字并排**（用户原话：「我觉得这四个结论没有任何相关吧？？？？你到底在总结什么？这里要有明显的现象或者结论」「这个又不是结论，放在这啥意思」）。同一主题不等于有结论线——四条都在讲同一个试验，照样会被打回。逐条过这五关：
  - **递进或对照**：条目之间要有关系（主要终点 → 亚组验证 → 安全性另起），不能是「主要终点、置信区间、亚组、副作用」四个维度平铺。把纯统计量（HR/CI/P）并进它支撑的那条结论里，不单独占一行。
  - **复合终点要列举**：`心血管事件没跟着少` 会被问「什么事件？是发病吗？发什么病？」——写成「心梗、卒中、紧急支架搭桥、心血管死亡这几件事加在一起，没有变少」。MACE、主要终点、复合终点一类名词，首现一律拆成具体的病和事。**但拆完要写成「这几项合起来算一个终点」，不能写成「四个终点」**——复合终点的各组成部分是同一个终点的构成（任一件发生即计一次事件），说成并列的四个独立终点等于把试验设计改掉了，医生扫一眼就会皱眉。同理「四个终点均未达成」是错的说法，正确是「这个复合终点两组没有差别」。
  - **统计量带锚点**：`风险比 1.02` 单独出现等于没说。补一句 `1.00 代表两组完全一样`，读者才知道 1.02 意味着什么；P 值同理，要么给判读（「统计上没有差异」），要么只留 HR 删掉 P。
  - **每条给定性前缀**：`过敏性休克 19 例对 0 例` 会被问「然后呢？这什么结论？」——前面加「安全性上有个信号：」。没有定性前缀的数字条一律不许进数据块。
  - **指代要有先行词**：`单独分析同样没有差别` 会被问「跟谁同样？」——写「结果和整体一样」，把比较对象点出来。
0b-3. **引语要带上下文**：`它没成功` 会被问「在什么方面没成功？」——引号后紧接半句「指的是减少事件上没成功」。研究者原话单独摆着，读者不知道它回答的是哪个问题。**转述研究者对试验参与者说的话时，不许加「建议」两字**（`建议正在参加试验的患者不要因此退出` → `他说，正在参加试验的患者不要因为这些结果退出`）——加「建议」就从「转述当事人」变成「作者给读者开医嘱」，机审口径直接踩 2b。
0b-4. **阴性／零效果稿必须保留安全性信号**：把「过敏性休克 19 例对 0 例」「两成多人因不良反应停药」这类删掉，读者读完只剩「这药没用」；留着才是「没用，而且有代价」，信息量和讨论度都高一个量级，也是这类稿最容易被转出去的点。删安全性数据的唯一理由是字数超限，且要优先砍别处（后文会复述的数据条、发表状态、时序细节）。
0b-5. **试验／会议稿的数据块按四件套铺满，缺一件就是硬伤**：① **主要终点**（率或中位值 ＋ 风险比 ＋ 95% 置信区间 ＋ 是否达统计学显著）；② **次要终点／关键亚组**（远处转移、ORR 之类）；③ **总生存**——即使尚未成熟也要给出 HR 与 CI（`总生存尚未成熟，风险比 0.77，95% 置信区间 0.45 到 1.31`），只写「仍在随访」等于把读者最关心的那个问题悬着；④ **安全性**（≥3 级不良事件两组发生率 ＋ 最常见的 2–3 项反应，见 0b-4）。实测残稿的三种典型缺口就是：只给 HR 不给 CI、OS 只写「未成熟」不给数、整篇一条安全性都没有。
0c. **禁电报体**（用户原话：「不要为了少写字而少写字」「神经一样的六条推荐，推荐什么了」）。列表每条写成自然语言的完整句：什么人／什么情况／做什么／能得到什么。错：`▫️ AMA 阴性但临床怀疑 PBC：加查 sp100 与 gp210 抗体`；对：`如果患者临床很像 PBC，但抗线粒体抗体（AMA）查出来是阴性，指南建议再查 sp100 和 gp210 两种抗体，一部分患者因此不用做肝活检`。
0d. **列表前面必须有一句主题引导**：告诉读者这几条是什么、按什么逻辑排（例：这六条是一条临床路径——诊断→一线→风险评估→二线→症状→移植后）。裸列表直接甩 = 读者不知道在看什么。
0e. **禁元叙述标签**：「两条术语白话：」「下面解释两个术语」这种交代写法的句子一律删（用户原话「脱裤子放屁」），术语首现就地跟解释。
0f. **比喻写完整、说人话**：写「可以类比为这个病的『指纹』」，不许压成「像这病的『指纹』」；惜字如金到丢人味 = 返工。**但常识词不加比喻**（见铁律 4b）——写之前先问一句：这个词医生真的需要解释吗。
0g. **外部推荐里的「对照臂」和限定语不许压缩**：把指南的 `recommend using UDCA compared with no treatment` 压成「用 UDCA 而不是不治疗」，读者会以为临床上真有个「不治疗」方案（用户直接反问「原先的治疗方案到底是怎么建议的」）。写法分三档，按顺序试：① **首选整句删掉对照语**，只留结论——「指南把熊去氧胆酸（UDCA）列为初诊患者的一线选择」；② 对照必须在文中交代时，用原文自己的措辞，**不许自造「对照组 / 比较臂」这类读者看不懂的同位词**（生造出来的是「这句话啥意思？读起来莫名其妙」）；③ 原文没定义的（对照里到底观不观察、对不对症处理）不许替它补。
0h. **一组并列项的标签用同一句式**：六条建议统一叫「诊断阶段 / 一线治疗 / 风险评估 / 二线用药 / 症状处理 / 移植之后」，不许混进「诊断这一段」这种口语变体（用户原话「改为『诊断阶段』不就行了？」）。写完把这一组标签横向扫一眼再交。
0i. **并列项先按「结论方向」分组，再落到类型**：写「四类疼痛」却把急性与术后合并列成三条，会被抓「说四种却列三条」。正确顺序：先分两组说方向（炎症越重、疼痛也越重 / 炎症越重、疼痛反而越轻），再往组里填疼痛类型，特例单独起段。这样读者先拿到规律，再看分类。数量词（四类/三种/六条）写完必须数一遍实际条目数。
0j. **转折处用「则／却」，但不做机械替换**（用户原话：「我不是要你把『就』全部换成『则』，而是要你在一些转折的地方用『则』『却』这些字」）。只在逻辑真的拐弯的句子用：方向**却**随状态而变 / 长期结局**却**更差 / 到了慢性阶段**则**可能失控 / 方向**则**可能相反。其余「就」保持口语本色。
0k. **句式别写成小学生作文**：`对临床的直接含义是 X`、`这种轻不是好消息`、`看起来像…在承担修复任务` 这类主谓宾平面句要改成人话，例：`因此临床上需要根据不同分期选择相应的抗炎手段`。写完每段读一遍，拗口或稚气的那句重写。
0l. **封面文案不能平庸**：`X和Y 关系会反转` 这种平铺直叙会被打回（「这个文案太普通了，真的是 dbs 写的吗？」）。封面必须带立场/反差/数字，按 `dbs-xhs-title` 给 3–5 个带公式编号的候选让用户挑，Top1 先出图。
0l-2. **封面文案不得与标题同义**：两者分工是「标题让人对号入座，封面让人愣一下」。标题是「炎症越重，未必越痛」时，封面就不能写「炎症越高疼痛未必越重」，要换成「同样的炎症 两种相反的痛」这类反差句——同义重写等于浪费一个位置，用户会直接换掉。改封面前先把新文案与标题并排读一遍。
0m. **团队/机构只在真有名气时点一句**（用户口径：「比较著名的你就提一下，不著名就算了」）：首段一句话说清“哪家机构 + 谁领头”就够，例：「研究团队来自麦吉尔大学 Alan Edwards 疼痛研究中心，末位作者 Luda Diatchenko 是加拿大卓越研究主席」。不堆头衔、不写自我判断式形容词（「国际最集中团队之一」这类需删）。头衔必须可核（官网/机构页），核不到就不写。作者与单位另存到文档「出处」节，别塞进正文。
0n. **首句要有润滑，不能写成主谓宾电报句**（用户原话：「太干了，缺乏一些过渡措辞润滑」）：结论句必须带连接成分——`只需…就能…` / `把…拉到…` / `…却没有赢` / `没想到…`。反例：「进入维持阶段后加一个双抗，中位总生存从12.7个月延长到21.1个月。」正例：「进入维持阶段后，只需加一个双抗，就能把中位总生存从12.7个月延长到21.1个月。」
0o. **中文语序：主语做动作**（用户原话：「主语发布了谓语，不要写成xxx在xx公布这种被动物体放在前面的写法」）。反例：「3期XXX研究在欧洲肿瘤内科学会（ESMO）2026年会公布」；正例：「XXX研究团队在欧洲肿瘤内科学会（ESMO）2026年会上公布了这项3期试验的结果，论文同期发表在《…》」。主语是团队/作者，动词是公布了/报告了。
0p. **试验术语一律落地，而且必须落在首现处**：用户两轮批过同一件事——「这里才解释…前面就该备注了」、「又知道备注了，为什么备注不放在第一次出现的地方」。规则：**任何缩写/术语的第一次出现就带括号注释**，后面不再重复注释、只用缩写或「该药」。要落地的包括：`arm/臂` → `组`；`亚组` 前文没交代就改成「把患者按转移部位分组后…」；非劣效（＝要证明「不比标准差」而不是「更好」）、界值、数据成熟度、BICR（第三方影像团队判读）、ctDNA、pMMR、CRS、高表达。**双向都要严（2026-10 TroFuse 篇因这个被连批四条）**：① 解释必须贴在词第一次出现的位置，隔段后置＝没解释；② 反过来，词在附近没出现过却单独冒出一句解释（悬空解释）也要删，挪到该词首现处——两句都要看，不是只查“后面有没有解释”。
0p-5. **只解释主角词，且解释必须真落在前文**（用户删过一次三处术语解释，理由是「这篇文章的主角就是它，只解释它就行了。再说了你解释的其它东西也没有出现在前文」）：**副角缩写只补中文全称**（`高级别浆液性癌（HGSC）`），不补整句解释；用户手改删掉的解释**不要再加回去**。反过来，他点名要解释某个词时，括号写两截——**它是什么 ＋ 它为什么不够用**（`CA125（沿用多年的血清标志物，炎症、子宫内膜异位也会让它升高，早期癌却常不高）`），只写「是什么」等于没回答他问的那半句。
0p-2. **括号里的检测参数也得白话**：`免疫组化3+且≥90%肿瘤细胞`、`FISH≥10拷贝` 这类不是解释而是黑话，要写成「免疫组化3+且≥90%肿瘤细胞（即染色最深、几乎全部肿瘤细胞都染上）」「FISH≥10拷贝（即每个细胞里该基因拷贝数≥10）」。
0p-3. **百分比不许裸露**：`数据成熟度53%` 这种写进 ▫️ 块会被问「53% 突然冒出来、没有前言后语」。做法：数据块里只写读者能读的限定语（`HR 0.68，随访尚未达预设事件数`），百分比的含义放到段末一句白话或 ⚠️ 里。
0p-4. **受众含无科研基础的医生（用户明确），headline 术语也要白话**：标题／封面数字对应的核心术语——无进展生存、总生存、HR（风险比）、阳性、几线治疗——即使不是缩写、医生都懂，也要在首现处给一句白话。外行拿标题数字当入口，headline 不解释就只是个数字；「阳性」还会被读成化验单阳性。审稿人（Kimi 外行视角）专抓这个。
0q. **同一个东西只用一个称谓**：先说 DLL3 又改口「双抗」会被问「生怕别人知道你的主语到底是谁」——同一对象统一叫一个名字，或以「它」承接。比喻被否（如「门牌」）就换直说，不要换个比喻再试。
2d. **「具体癌种＋具体药名＋具体疗效数字」三件套是机审首要雷区**（用户 2026-10 拿小红书 AI 审意见回来，判定这是目前风险最高的一类）：三件套全齐时容易被判「医疗功效宣称」。降级三招，缺一不可：
  - **句式**：首句改成客观陈述——「试验组中位总生存为21.1个月，对照组为12.7个月」；**禁用强功效句**：`延长到 / 提高到 / 降低风险 / 只需…就能… / 多活 N 个月`。
  - **药名**：研究药只保留一次且写成「一种双特异性抗体（Tarlatamab）」；对照药只用类别（「免疫检查点抑制剂」），不点具体名。
  - **导向句**：`支持成为新标准 / 指导临床决策 / 直接改变实践` → `为后续治疗策略的探索提供了参考`。
2e. **免责/定位声明只出现一次，放在正文最开头、并用括号包起来**（用户 2026-11 定稿口径，取代原先“结尾一处”）：正文第一段就是 `（声明：本文为科研资讯解读，不构成任何医疗建议，具体诊疗请咨询专业医师。）`，后面整篇不再重复（结尾也不写）。开头前置的理由是：读者第一屏就看到，机审也比结尾更容易抓到。措辞可随题材调：非医学题材用「科研规范解读」版（见 2u）、药品/疗效类用「不构成用药推荐」版（见 2b-3）。首段末的「以下为数据转述…」和数据块引导句里的括号免责照样删——全文只有开头这一处。
2f. **封面不能写功效承诺**：`多活8个月`、`生存期翻倍` 这类把风险从正文搬到图上，等于白降级。封面只写反差或方向（例：「维持期 多了一个选项」），具体数字留正文。
0r. **看着像常识的临床词也要给判断依据**：`进展`、`耐药`、`缓解`、`可评估` 这些词医生熟、但读者不知道具体指什么。用户会直接问「就一个『进展』，怎么进展的？」。首现就地补一句标准口径：`治疗后肿瘤再次长大（影像上病灶增大或出现新病灶，医学上叫疾病进展）`；后文再用「进展」就不用重复。
0s. **写中文全称前先核权威指南，并回填依据**：用户会问「你确定一下是不是这个」。做法：用国家卫健委诊疗指南 / CSCO 指南核对（例：EGFR＝表皮生长因子受体（epidermal growth factor receptor），《原发性肺癌诊疗指南》与 CSCO 肺癌指南均如此写），核对结果与依据写进文档「出处」节；不确定就只写英文缩写，不硬编中文名。
2g. **「全球首个」「首次」「获益」「改善」一律不写（用户 2026-10 口径，比小红书 AI 的建议更保守）**：即使事实成立，「全球首个……总生存获益」叠加会被判夸大宣传/功效宣称。价值感改由**中国团队牵头 + 规模**承载（例：「由上海市胸科医院陆舜团队牵头，在 29 个国家的 230 家中心开展」）；`获益` → `数据方向一致`；`改善` 尽量落地成具体数字。标题/封面确需用「首个／近30年首个」这类强表述时：**必须有官方出处 + 转述主体**（「据研究团队介绍／据官方发布／据官方新闻稿」），且转述主体优先用「研究团队／官方发布」，少用具体药企名（点点 2026-10：药企名＋阳性结果机审更敏感）；特别求稳就把绝对化留在正文、封面标题只写中性词。
2i. **「选药 / 建议 / 质疑」框架是机审最高危（比三件套还危险）**：标题带「选哪个」「该做什么」「是浪费时间么」、正文写「谁好谁差」「正面PK」「摆在一起比」、反复用「新药」压对照组，机审会判为处方推荐／药品对比宣传或诊疗建议。这类选题一律拉回「数据解读」转述口径：
  - 标题去掉「选哪个 / 该做什么 / 是浪费时间么」，用「头对头研究数据公布 / 结果解读 / 围术期研究数据公布」这类转述；
  - 删掉「谁好谁差一眼见分晓」；结论段改成客观陈述「试验组在…上的数值均高于对照组，结果供参考」，并补背景限定（开放标签、对照组组成）；
  - 「新药」统一改「试验组药物」或直接写药名，不再反复强调新旧；
  - 「正面PK／摆在一起比」换成中性的「头对头／直接对比」。
2h. **病程词用「发生进展」而非「长大/叫疾病进展」**：用户口径是写「治疗后发生进展（影像上病灶增大或出现新病灶）」，动词短语更自然、也更像临床表达。
2j. **试验结果报道必须有收口结论段**：骨架固定「旧困境 → 新试验 → 数据 → 注意点 → 所以这意味着什么」，缺收口 = 读者要自己拼结论（Kimi 审核原话「文章从头到尾没有说出结论」）。⚠️ 之后直接进入收口段（不再有结尾声明），加一句「这项研究为<人群>补上了<某条路径/选项>；至于<悬而未决的终点>，还需更长随访或直接对照来回答」——把开头「过去只能直接切/直接手术」的旧困境和数据接成闭环。
2k. **数字自带结论，⚠️ 引用前文要有**：主要终点数字必须写 HR + P 值/是否达显著（否则「最容易被截图断章」，如 `HR 0.57，P=0.0002`）；⚠️ 段引用的任何数字（如三药组的 HR）前文数据块必须出现过，否则读者无法核对——要么补进数据块，要么删掉这条。
2l. **开头对现状的定性必须与 ⚠️ 里的「现行方案／标准」自洽**（2026-10 KEYNOTE-C93 被审出）：开头写「一线通常直接上化疗」、⚠️ 又写「化疗联合免疫是现行方案」，读者两头糊涂。改法：开头加时间限定「过去」，把旧做法框在过去，与现行方案区分开。
2m. **数值接近的疗效终点必须给一句解读**（2026-10 KEYNOTE-C93：ORR 64.1% vs 62.1% 几乎一样、PFS 却差 30 个月，悬着像笔误）：点透差异来自「缓解持续更久、而非缩瘤更多」，和曲线／生存数据的解读串成同一层意思。**诊断类稿里 AUC 低于 0.5 是「反向区分」、不是笔误**（例：CA125 在良性附件包块组 AUC 0.31，意思是用它鉴别时良性组反而更高）：字数够就补半句「低于 0.5 表示方向反了」，字数不够就**只在文档「正文」节的说明 blockquote 里记一笔口径**并在交付消息提醒——反常数值不能静默放过，医生读到时必问。
2n. **同一句里的并列限定语别用两个逗号堆叠**：`患者，一线治疗，按1:1随机` → `患者（均为一线治疗）按1:1随机`。
2o. **封面／标题里的绝对化词也会被机审 OCR 扫**（点点 2026-10：不只扫正文，封面大字和标题里的「首个／近30年首个」同样扫）。标题和封面文案要和正文一起走合规口径，不能“正文降级了、封面还在喊首个”。
2p. **数据块的数字要回源核对口径，不能只对数值**（2026-10 三篇连续被 Kimi 抓出 5 处硬伤，全是“数值对、口径/顺序错”）：加了「前=组A、后=组B」标注后，**每一个 `vs` 数字的左右顺序都要回源核对**——来源常按「标准组在前」报，照抄到「试验组在前」的标注下就整体反了（AE 和 PFS 都反过）。核对五件事：① vs 左右谁是组A；② 分层（`共随机 X 例` 要分清「筛选／随机／亚组」三层，如 267+265=532≠594，594 是筛选总数）；③ 不良事件标「全因」还是「治疗相关」（摘要常给全因 69%，别拿二手报道的“治疗相关 54%”硬贴）；④ 置信区间/界值口径（非劣效界值 vs 实际 CI、90% vs 95%）；⑤ 发表状态（「全文尚未开放检索」不能与「已在线发表于 Lancet＋PubMed 已收录」并存）。核对依据优先取摘要原文／官方稿，二手报道只作交叉。
2q. **点点的合规结论是最终权威，可直接执行**（用户 2026-10：「点点是小红书官方AI，它说行，那就是行」）：点点的合规建议不必再等确认、不必再来回问，直接照改；Kimi 的审稿意见是参考（内容／外行视角），凡与点点在合规口径上有冲突，以点点为准。
2r. **标题/封面文案要带「态度方向」，不能只转述数据**（用户 2026-10 定稿 MOIO 标题「免疫治疗拉长间隔 死亡信号升高须警惕」时明确：读完要有“这是好消息还是值得警惕”的抓手）。每条稿先定性，标题或封面至少一处用方向词点出：
  - **好消息**：事实词「阳性 / 首个 / 显著」（禁「获益 / 多活 / 翻倍」）；
  - **警惕**：事实+提醒词「升高 / 偏高 / 须警惕 / 反而更高」（禁诊疗建议「别减针 / 有风险」——「须警惕」点点认可可用）；
  - **双刃**：反差句式「赢了X，没赢Y」（如 OS 显著、PFS 未达标）。
  方向词只作提醒、不作推荐。

2s. **比例/发生率类的数字，三件事必做**（2026-10 AI 虚假引用篇被审出）：
  - **带时间限定**：报道里的 `1/277` 往往只是最新一段窗口（本篇是 2026 年前七周），不是审计全期（全期约 1/890）。首句写成「2026 年前七周发表、被 X 收录的论文里，**每** 277 篇就有 1 篇……」——`每 N 篇有 1 篇` 是比例，不是「N 篇里有 1 篇」的总数，用户会直接问「是 277 篇，还是每 277 篇？」。
  - **换算成百分比（一律用百分比，不写分式）**：用户 2026-10 口径「以后关于比例、概率等情况，尽量都用百分比，不要用原文这种形式」。公式 `100/N`：1/2828=0.035%、1/458=0.22%、1/277=0.36%。写成 `0.035%（2023）→ 0.22%（2025）→ 0.36%（2026 年前七周）`，**不要在后面再附 `原比例 1/2828 → 1/458 → 1/277`**（会被问「这俩不一个意思吗」）。正文、DS 初稿、出处节统一百分比；只有核对说明为溯源可保留原式。
  - **倍率必须与手算对账**：报道写「两年涨 12 倍」而 1/2828→1/277 实为 10.2 倍——不一致就**不写倍数**，只给百分比，否则被心算读者抓。

2s-2. **建模估算类素材（GBD／疾病负担／预测模型）单独一套口径**：这类既不是队列也不是试验，四件固定——
  - 研究类型写「基于 GBD 20xx 的建模系统分析（二次分析）」，**不写「观察性研究」**；⚠️ 首句点明「模型估算、带不确定区间」。
  - **只写率的变化，不推绝对数变化**：摘要没给两个年份的绝对数对照时，就不能写「死亡人数涨了/降了多少」——那是自己外推。
  - **自己换算出来的数字必须在 ⚠️ 里注明「按摘要数字换算」**（例：中国占东亚死亡 = 254,463／261,368 = 97%），且换算要跑一遍算术，不要口算。
  - 首现给白话：ASMR（年龄标化率＝把各国人口年龄结构拉平再比）、EAPC（估算年度变化百分比）、DALY（伤残调整寿命年）、分解分析（把死亡数变化拆成老龄化／人口增长／流行病学变化）。
  - 收口写「作者结论称…」，不写「应加强筛查」这类建议（同 2b）。
  - **负担占比必须带两个东西：分母 + 标化率对照**。「中国占亚洲 59.8%」「占东亚 97.4%」这类份额由**人口规模**驱动，单独摆出来会被一句「那不废话，中国人多」打穿（用户必问，且问得对）。做法：① 份额一律写清分母（「占该地区」「占亚洲」），跨段出现两个不同分母时尤其要写，否则读者以为其中一个算错；② 正文或交付说明里给出 **每 10 万人的年龄标化率与邻近国家横向对照**——这类数字摘要常常不给，要去正文 Table 1 取（`ASIR/ASMR/ASDR per 100,000` 行），有了它才能回答「剔掉人口因素后是不是真的高」；③ 若原文确实做了分解分析，用它收口（老龄化／人口增长驱动绝对数，而不是发病率飙升）。
  - **占比类数字一律阿拉伯，不写「九成七」这类汉字数**（用户会直接改成 97%）。需要更精确时正文写一位小数（97.4%）并写明分子分母，标题保留整数（标题卡 20 字上限，小数点后再也塞不下）；换算出的精确值只在正文/⚠️ 用，别再把汉字数改回去。
  - **受众是「把病看明白就得了」的临床医生，不是做统计的人——负担类稿必须「结论先行 + 拆掉统计壳」**（用户原话：谁刷个图文还仔仔细细去分析数据）。四件固定：① **第二段就给结论**（「97.4% 在中国，但按每 10 万人算和邻国差不多，占比高主要因为人多」），不要让读者自己从三个数字里推；② **所有 `95% UI` / `95% CI` 括号从正文删干**，统一在 ⚠️ 写一句「数字来自模型估算，均带不确定区间，这里只写点估计」——一篇稿原带 8 处括号，删完省两百字且好读一个量级；③ **白话在前、术语在后**：先讲「死亡人数＝得病风险 × 人口数量」「老年人多的地方病例天然多」，最后才出现「年龄标化率」这个词；④ **可以不用 `▫️` 数据块**——负担类稿改成叙述段落更顺（五条数字摆成列表反而逼读者对数字），这是对房式列表惯例的合法例外。

2t. **相关≠因果，媒体用 coincided with 时要归因**：`拐点与 AI 写作工具普及的时间正好对上` 是陈述事实，会误导；改成 `研究团队指出，拐点与 AI 写作工具普及的时间重合`——关联性结论一律把主语放回研究团队。

3. **三档黑名单**见 `references/ai-slop-blacklist.md`：硬造动词、`真正…的是`、`比…多一…`、`不是…而是…` 高密度、套话、读者指令。
4. **术语/缩写的呈现顺序按“哪个更常用”定**（用户 2026-10 口径）：英文缩写更常用（PPAR、PBC、UDCA、HR、AUC、RCT）→ **英文在前、中文全称进括号**（`PPAR 类药物（过氧化物酶体增殖物激活受体激动剂）`）；中文更常用（糖化血红蛋白、肾小球滤过率）→ 中文在前、缩写进括号。不要用“也就是…”把两个写法串成一句。
4b. **常识词不配比喻**：`标志性抗体`、`一线用药`、`肝硬度` 这类本身含义已经在字面上的词，**不要再加“可以类比为…”**（用户原话：「这是废话，标志性抗体就是识别用的」）。比喻只给真的外行看不懂的概念（如全血 RNA 测序 = 看细胞此刻在干什么活）。
5. **tag 六个六位配比**（2026-10 用户口径）：热点大词 / 精准核心词 / 受众词 / 垂类词 + **末两位固定品牌词 `#刀客轻研`、产品词 `#SciLink`**；同义大词不同时打。只给 5 个会被 `xhs_check.py` 判 FAIL。
6. **字数**按「含标点、含空格、不含换行」的实测值报给用户，不许估。

## Pitfalls

- **`str_replace` 删句子会残留空 `<p></p>`**：用 `--content ""` 删掉一行（例如删掉多余的术语解释行）后，文档里会多出一个空段落，看起来像双空行。改完 `docs +fetch --doc-format xml` 查 `<p></p>` 计数，非 0 就现拉一份当前 XML、`replace('<p></p>','')` 后 overwrite 一次（此时批注已 resolve，overwrite 安全）。
- **用户手改会留下带空格的空行段，`body_xml.py --check` 查不出来**：`<p> </p>`（半角）或 `<p> 　</p>`（半角＋全角）在 markdown 回读里就是一行空白，缩略图看不出，但违反零空格铁律、粘贴到小红书会带缩进。审计既有文档时用 `docs +fetch --doc-format xml` 扫 `re.findall(r'<p>[ \u3000]*</p>', c)`，再按内容区分：只含 `　` 的是合法空行段，含半角空格的一律有问题 → 拿到段 id 用 `block_replace --block-id <id> --content '<p>　</p>'` 逐段改回。
- **写「率」必须点名是哪个率**：`南亚是唯一在升的亚区`、`三个「率」都在降` 这类写法会被批注追问「什么东西在升？？」。一律落到具体名词：`年龄标化死亡率`、`发病`（每年降 3.42%）、`疾病带来的健康损失`；无法一句话说清时补半句限定（`把年龄结构拉平后，每 10 万人里的死亡人数每年升 1.8%`）。
- **用户用征询口气问方案（「你觉得…会不会好一点」「先说说你的想法」）＝只出方案、不改稿**：回复按「结论（支持/不支持 + 一句理由）→ 为什么好 → 风险 + 对应补丁 → 我的排序建议 → 待确认点」组织，每条意见都要能落到具体改法。用户回「OK」再动手，且动手时把先前提出的补丁一并落实（只做主干改动、把补丁漏掉 = 下一轮被打回）。
- **中文引号一律用「」不用""**（用户 2026-10 明确：所有要加双引号的地方都用「」，保持格式一致；已写死进 skill）。
- **`block_insert_after` 的中文内容一定要用 `@file` 传**：在 shell 里把中文 `json.dumps(...).replace('"',"'")` 拼进 `--content`，会被当成字面量 `\u25ab\ufe0f` 写进文档（实测整行变成乱码转义）。正确做法：写 `/tmp/x.xml`，`--content @/tmp/x.xml`；写完 `docs +fetch` 回读看有没有 `\u`。
- **给图片块加评论**（注明生图参考图）：`drive +add-comment --doc <token> --type docx --block-id <img块ID> --content @comment.json`；elements 只支持 `text`/`mention_user`/`link`（写 `text_run` 会报 unsupported type）。图片块 ID 从 `docs +fetch --detail with-ids` 取。
- **`docs +update --content @file` 会把「同名旧文件」当成新内容静默写进去**：回写多轮时如果文件名与记录 ID 的对应关系乱了（例：三条新稿的 XML 仍叫 `moio.xml` / `clarity.xml`，而正文实际在 `reczz….xml` 里），接口照样回 `ok:true`，文档却还是旧版本。做法：① 文件统一用 **record_id** 命名，不用语义化简称；② 每次写完 `docs +fetch` 回读，用一句**只属于新版的标志句**（如「并没有带来预想的收益」）做断言；③ 列表类文档再查 `　　▫️` 出现次数＝ 0。
- **每次 overwrite 前重新 `docs +fetch`，禁止拿会话早前导出的 XML/JSON 当底稿**：多轮返工时我把脱敏之前的旧 XML 重新上传，把刚删掉的药名又写回了文档（当时只改了图，回读只查图数就以为成功）。规则：① 任何一次 overwrite 前现拉一份当前内容，“上一轮的底稿”一律作废；② 回读断言要同时盖住本轮每一项修改（药名 0、周期 0、图片数、`　　` 0），不能只验证最后改的那一项；③ 手上留一份 ndjson 快照，误写字段/回滚时用得上；④ **断言要盖住「本轮新增的东西」**——本轮新增了节（如论文卡 grid）就先数一遍覆盖前的 `imgs` 与节标题，覆盖后要求 `imgs ≥ 覆盖前`、新增节标题出现 1 次，否则用旧快照覆盖时新节会整体消失（图数从 7 掉回 5，肉眼翻文档才发现）。
- **Moonshot 端点 `429 engine_overloaded_error` 会连成一片**（实测 2026-10：`api.moonshot.cn` 连续 4 次退避重试全失败，5 条稿 6 分钟只出 1 条）。不要把重试次数调高或循环等待：换通道——`api.kimi.com/coding/v1`（key 取 `~/Documents/Hermes/APIs/kimicode API.rtf`，model `k3-256k`，`temperature` 只能=1，`max_tokens` 给 6000）实测同时段稳定；再不行才退 GLM coding 端点。写稿 prompt 可以直接复用，不用改模板。
- **Kimi k3 系列是思考模型**：不关 thinking 会把 token 全烧在 reasoning 上，`content` 返回空字符串。`kimi_write.py` 默认带 `thinking={"type":"disabled"}`。
- **`kimi-k3` 只接受 temperature=1**，传 0.85 直接 400。脚本默认不传 temperature。
- **`kimi-code` CLI 的 OAuth 会失效**（`The provided authorization grant is invalid`），别修，直接用 Moonshot API Key。
- **空格算字**：正文里「2026 年 9 月」的空格平台也计数，别用去掉空格的 len 低估。
- **`block_replace` 会让被替换块的批注失效**：用户标注意见时，先本地存稿、把批注逐条落实，再整体替换。
- **`docs +update --command overwrite` 的真正硬约束是「文档有未解决批注时禁用」，不是「有配图就禁用」**：XML 里用 `<img path="@./x.png" caption="…"/>` 重新声明全部图片时，整篇覆盖能把旧图换成新图（实测：四图文档覆盖成三图，回读图数、顺序、附图说明全对，旧 file_token 全部换新）。批注则会整批消失且不可恢复。所以：**无批注 → 可以 overwrite 重建（含配图，最省事，`--doc-format xml` 一次带排版）；有任何未解决批注 → 只能 `str_replace` / `block_*`**。写完一律 `docs +fetch` 回读图片数量与一句只属于新版的标志句，不看接口的 `ok`。
- **正文排版别退回 `<br/>` 软换行 + 续行缩进的老模板**：老版本 `body_xml()`（`"<p>"+"<br/>".join(...)`、`▫️` 续行加 `　　`）会从会话历史里被直接复制复用，结果是文档里行间距看着正常、**复制到小红书全部挤成一段**，且行首多出两个全角空格。**根因（2026-10 AI 虚假引用篇实打实翻车）**：我调了本会话早前写的 body_xml，而不是 skill 里的当前版——因为当时只把写法写进文档、没固化成脚本。现在唯一入口是 `scripts/body_xml.py`；任何“从上下文里找个生成函数用”的行为都算违规。交付前必须跑 `--check` + 回读断言 `　　`＝ 0。
- **「疫情同步推进」这类动词是 AI 味重灾区**：疫情、病例不能「推进」（用户原话「哪枱这种说法的」）；过渡句用「再看看其它州：」这种白得不能再白的写法。“好在接种量也在上升，”比“接种量也在上升。”带信息。
- **用户写批注后的两件事**：①批注要用 `lark-cli drive +list-comments --url <URL> --solved-status all` 读（`docs +fetch` 现在**不再**回 `reference_map.comments`，fetch 里找不到批注不等于没批注）；②改完用 `drive +resolve-comment --url <文档 URL> --comment-id <id>` 逐条标已解决——**只给 `--comment-id` 会报 `specify --url or --token`**（也可用 `--token <docx token> --type docx`）。批注锚点在 XML 里是行内 `<span comment-refs="cN">…</span>`：用 `str_replace --pattern "原句"` 就地替换这段文字后 resolve 仍能成功，**默认不要用 overwrite**（整篇覆盖会把锚点一起删掉、批注批量失效且不可恢复）；改前先 `docs +fetch` 取 XML，定位是哪一段被批注、哪段是用户手改的。
  - **例外：批注要求段落级重排时，走「先全 resolve 再 overwrite」**。批注里出现「这段应该放到开头第二句」「这四条没有相关，重新组织」这类意见时，`str_replace` 只能改字不能搬段，硬凑会把正文改乱。此时：① 本地改好整篇；② `xhs_check.py` 跑到 PASS；③ **逐条 `drive +resolve-comment` 把 13 条全部标已解决**（偶发单条 500，重试一次即过，别换 URL 或跳过）；④ 再 `docs +update --command overwrite --doc-format xml`；⑤ 回读断言要同时盖住「用户手改的句子还在」「新结构生效」「旧句已删」三项。代价是批注记录消失，所以**交付时必须给一张逐条对照表**（批注原文 → 改后句子）替代文档里的批注。
  - **这条路的两种安全做法（都别凭记忆重写整篇）**：① 「切片 overwrite」——现拉当前 XML，只把 `# 正文` 那一节（`<h1>正文</h1>` 到下一个 `<h1>`）换成新生成的正文，前面的 `<title>`／封面／图文标题与后面的 `# 出处`／`# 附` **原样拼接**，这样用户手改过的其它节物理上不可能被覆盖；② **正文按用户手改后的段落划分逐段生成 `<p>`，不要用 `body_xml` 重新拆句**——他常把几个短句合成一段长段、删掉段间空行，重新拆句等于动了他的排版。为什么需要这条路：一个长段落被拆成多个 `<p>` 后，`str_replace` 整段替换会把新文字塞回单个 `<p>`，多句挤成一段（贴到平台又是一大块），只能走整节替换。
  - **批注先分三类再动笔**：① **保命型**（「这句是我加的，你不要删掉」）——不属改写意见，原样保留并 resolve；② **补白话型**（一句批注只有「意味着什么」几个字）——补的是这串数据的含义，不是数据本身；③ **改写型**（「这个意义显得不够大白话」）——就地换成读者能懂的话。分不清就按字面意思改，别把保命型当改写型处理。
- **`润色正文` 列放云文档纯 URL，不放正文文字**（用户 2026-10 口径）。DS 稿仍进 `DS建议正文`，两者不要串。
- **原文页 403／404 时先分辨是「站点拦机器人」还是「链接真坏了」**：政府站与出版社站对非浏览器 UA 常直接回 404（页面本身完好），据此向用户报「表里链接失效」是错报。判定前必须用真浏览器 `browser_navigate` 打开一次，能出正文就说明链接有效，只是 curl 被拦；确认真坏才动数据。错报要说出来更正，不要静默改口。**政府站的典型组合是「正文页回 412 反爬页（几百字符）＋ 同页附件 PDF 走 `/files/*.pdf` 静态路径 curl 直接 200」**：正文用浏览器读、附件用 curl 下，两条路分开走，别因为正文 412 就认定整个选题拿不到原件。取不到页面时 P2 走 `scilink-pic/scripts/shot_offline.py`（curl HTML → 本地 headless 渲染 → 裁 3:4），并在文档里注明「原文页 403，P2 采用官方新闻页」。
- **附录已改为「原文与译文」（2026-11-09），不是 DS 初稿**：那类文档现在结构是「正文（润色稿）＋ 附：原文与译文（英文原文＋中文译文）」。英文必须**逐字照抄原文**（不改写、不合并段落），译文一段对一段；按原文自己的章节分小标题（如 What did FDA find? ／ FDA 查到了什么）。`DS建议正文` 列默认留空（用户说 DS 初稿无所谓了），不要再为了填列去补写初稿。
- **指南/清单类稿件最容易一口气踩三个坑**：①把六条推荐当清单子甩出去不给主题引导；②每条用电报体（冒号＋名词），为了控字数把解释砍光；③把原文的对照语（compared with no treatment）压成「而不是不治疗」这类临床上不存在的方案。写完先问三句：这几条是什么关系？每条读者能看懂吗？每个「而不是」能回原文对上吗？
- **字数不是第一优先级**：平台上限 1000，但用户真正反感的是「为了少写字而少写字」。指南类目标 850–950 字，压缩对象是无信息量的修饰（有多高 / 这件事 / 一份），不是解释与比喻。
- **写回后必须列表回读验证，不信接口的 ok**：改完节点位置/记录字段，用 `wiki +node-list --space-id <space_id> --parent-node-token <父> --page-all`（**`--space-id` 必填**，只给 `--parent-node-token` 会静默返回 0 条，看着像“这个父节点下没有任何子文档”；返回里是 `data.nodes`，不是 `items`；**`--page-all` 也必加**——默认 page-size 50，第 51 条以后的节点根本不出现，且 `meta` 只回 `{'count': 50}` 不提示还有下一页，把刚建/刚搬的文档误判成「不在这里」；58 个子文档时要 `--page-all --page-limit 5` 才看得到末尾那条）或 `base +record-get` 回读实际值。凡是「API 说成功但列表没变」的地方，以回读为准；无法回读验证的变更不要向用户报完成。
- **`xhs_check.py` 的两条非问题别追**：`缩写首现未带中文名` 是 INFO，中文全称就写在同行括号里（`MMR（麻疹、腮腺炎、风疹联合疫苗）`）时属误报，不要为它重写句子；`emoji 分类标记` 的 WARN 也来自本账号房式允许的 `⚠️` 口径行。只看 FAIL，WARN 逐条判断后可以在交付说明里写明保留理由。
- **规范更新后旧稿要回归对齐**：本 skill 是活规则（禁用 📌、▫️ 续行缩进、单行文案下移、段间空行都是后来加的）。写完新稿后把同目录最近几篇当成一批看，**上一批可能还停在旧规范**，审查时当成必提项，别让同一个账号两种排版。
- **研究类型别含混过关**：只写「观察性研究」会漏掉「二次分析 / 多队列再分析」这类关键信息；写前先定类型、写进 ⚠️ 首句，用户会直接问「这是综述还是啥」。
