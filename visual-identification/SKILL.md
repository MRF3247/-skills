# 画面识图与核验（先用本模型自己的眼睛，脚本通道作备用）

用途：任何「这张图 / 这段动图里到底是什么」的任务——素材命名、归档描述、核实素材是否名实相符、读图上文字、批量识图。产出的描述会进素材库 README / 稿件 / 交付说明，所以**准确度 > 好看**。

相关技能：GIF/表情包入库全流程见 `gif-meme-collection`；视频素材出图与排版审核见 `video-asset-pipeline`（其「视觉审核」节）。本技能只管「看清楚 + 怎么表述」。

## 看图通道优先级（按顺序试，别和它较劲）

1. **`vision_analyze` 工具（首选）**：把图直接载进本模型自己的上下文，由本模型判读——不经第三方模型转述，误读最少。**它一次只吃一张图**，所以动作时间轴不要逐帧调多次，用第 2 条的拼图法一次看完整条序列。
2. **拼图 + `vision_analyze`（看动作时间轴的标准做法）**：`scripts/gif_montage.py <gif> <out.png> [最多格数=6] [格高=220]` 均匀抽帧拼成一张横向长图、每格左上角标「序号 (f帧号)」，一次调用看完整条动作序列。
   - ⚠️ **超宽图会被大幅缩小**（工具提示里的「downscaled from WxH to WxH，坐标乘 N」就是它）：长图宽过 ~3000px 细节基本丢光。宁多分几张——长 GIF 拆成 8~10 格/张，必要时分 2~3 张看；短 GIF（≤10 帧）干脆全抽。
3. **`minimax_see.py "<问题>" <图...>`**（备用脚本通道；MiniMax-M3，key `MINIMAX_CN_API_KEY` 在 `~/.hermes/.env`；支持同消息多图，输出含 `<think>` 已由脚本剥离）。
4. **`kimi_see.py` / `kimi_multi.py`**（旧通道，仍可用）：
   ```bash
   # 单图（首帧 / 静态图 / 截图）
   /Users/Jin/Documents/Hermes/venvs/huashu/bin/python3 \
     /Users/Jin/Documents/Hermes/kimi_see.py <图片路径> "<问题>"
   # 多图时间轴（动图 / 视频抽帧；一条消息塞多图）
   /Users/Jin/Documents/Hermes/venvs/huashu/bin/python3 \
     /Users/Jin/Documents/Hermes/scripts/kimi_multi.py "<问题>" f_1.png f_2.png f_3.png
   ```
   - 端点 `api.kimi.com/coding`（Anthropic 式 content 数组），key 在 `~/Documents/Hermes/APIs/kimicode API.rtf`。
   - **脚本通道报错先分类，别盲重试**：返回 `403 access_terminated_error` / `monthly usage limit` 是计费周期额度用尽，重试无用——直接换回第 1~3 条通道继续干活，换通道不影响结论精度。
   - **解释器必须带 PIL**：默认 `python3` 没有；用 huashu venv 的 python3（上面写的那个路径）。跑任何 kimi 看图脚本都用它。
   - 脚本路径分两处，别拼错：`kimi_see.py` 在 `~/Documents/Hermes/` 根目录；`kimi_multi.py` 在 `~/Documents/Hermes/scripts/`（本技能 `scripts/kimi_multi.py` 是真源副本，丢了从这里取）。
**脚本通道（第 3~4 条）的排查口径**：

- **返回空文本时先按这两条排查，别急着判定通道坏**（本机通道实测的两个成因，改完即可拿到回答）：
  1. `max_tokens` 给小了——thinking 模型把预算耗在 thinking 块上，`content` 里只有 `"type":"thinking"`、没有 text 块，打印出来就是空。看 `usage.output_tokens_details.thinking_tokens` 与 `stop_reason` 即可确认；把 `max_tokens` 提到 1500~2500 重发。
  2. 图太大——长边 >2000px、或 PNG >400KB 的截图容易返回空。先缩到长边约 1200~1400px、存 JPEG q85 再送。
  两条都试过仍空，才考虑换图/换问法/换帧。
- **要改通道细节就改 `kimi_see.py` / `kimi_multi.py` 本身**，别在临时脚本里另起一套 base64 直连：脚本里已有的尺寸与参数处理一漏就撞上上面那两条空响应，排查成本远高于读一次脚本。

## 流程

1. **先看全貌**：单帧/单图问一句面向事实的问题——「画面主体是什么（人/动物/物件）？在做什么？有没有文字？不要推测，一句中文描述。」
2. **动图/动态素材必须多帧核验**，不许只审首帧：
   ```bash
   ffmpeg -i a.gif 2>&1 | grep -E "Duration|Stream #0"        # 先看时长与 fps 估总帧数
   ffmpeg -y -i a.gif -vf "select='eq(n,0)+eq(n,8)+eq(n,16)+eq(n,24)+eq(n,32)+eq(n,40)'" \
     -vsync vfr -frames:v 6 a_%d.png
   ```
   帧号按实际帧数取：3s@15fps≈50 帧用 0,8,16,24,32,40；1.3s 用 0,4,8,12,16。`-frames:v` 少出 1 张 = 末帧号超出，正常，不必重跑。
   抽完**合成一张带序号的拼图再自己看**（`scripts/gif_montage.py`，见上）：一次调用就能判完整条动作序列，比逐帧多次问模型省时间，也不会漏掉中段的切场景（实测有素材中段从「桌前用电脑」切到「站着举爪」，只看首尾帧必定漏）。
   问题模板：「这6张图按时间顺序取自同一段动图（a_1最早，a_6最晚）。只描述看到的事实：主体是谁？各阶段发生了什么动作？画面里的文字/标志是什么？最后停在什么状态？2-3句中文，不要推测。」
3. **存疑就定点追问**，一次一个维度，比重新问全貌快：位置类（「水线划过他身体哪个部位」）、道具类（「杆子末端在水面上方还是水里，有没有网或钩」）、文字类（「衣服上的字逐字念出来」）、道具真实性（「蛋上有没有插牙签/支撑物」）。
   判「有没有点头 / 有没有整体位移」这类**细微动作**时，直问「头动了吗」会被标题带偏（模型顺着标题答）——改用**参照物锚定**：抽 9-11 帧，把画面里的静止物明确指给它当尺子，问「主体的眼睛/鼻子相对右上角那行文字的高低位置各帧有没有变化，若有指出最低/最高在第几帧」。同一段动图换这个口径追问，三轮得到一致结论才算定论。
4. **交叉核对来源页**：能回查的出处当事实用——页面标题、Series/Episode（如 The Simpsons S16E21）、账号名、上传时间。抓不到页面就用 web_search / web_extract 取原页文本；GIPHY 页抽不到标题/频道时最省事的是 oembed（返回原题与作者，比抽页稳）：
   ```bash
   curl -sL --max-time 40 "https://giphy.com/services/oembed/?url=https%3A%2F%2Fgiphy.com%2Fgifs%2F<ID>"
   ```
   `author_name` 只有 "GIPHY" ＝ 原页没有具体上传频道，登记里写「原页未标注上传频道/出处，未能回查」，不编来源。三条纪律：
   - **原页正文常混着「Related GIFs」推荐位的说明**：网页抽取会把关联素材的文字并进正文（实测某页正文写的是另一支「黄鹦鹉看可乐爆炸、蘑菇云」动画，而本条画面里没有人、没有饮料、没有蘑菇云）。描述与画面不符时先怀疑串位，一律以自己的抽帧为准，绝不把推荐位内容写成本条描述。
   - **标题/标签里的情节只能标成外部信息**：原帖标题写了画面里没有的东西（标题 `Squirrel` 而画面只有狗转头），写进描述并注明出处即可，名字仍按画面取；页面无标题时登记就写「无原题」+ 频道与标签，不要拿推荐位里的标题冒充原题。
   - **页面上的大数字要先确认口径**：频道页会显示账号累计播放量，未必是本条；要引用就注明「取自频道页，可能是累计量」。
5. **落定命名/描述**，写进目标 README 或交付说明。

## 表述纪律（硬规则）

- **只写画面可见事实**：动作、位置、数量、文字、颜色、构图照写。
- **不写因果、不写意图、不写身份**：模型爱把并置读成因果（「泳者被水浪冲得翻身」→ 只能写「身影被水花搅乱」）；认不出的人**不许编名字**（「男子玻璃后平静凝视」而不是「Liam」），卡通角色/名人有出处确认了才写俗名。这条同样管**主体类别与道具身份**：放大复核能得到的判据（皮肤过于均匀、发际有胶状粘贴感 → 更像仿真娃娃；有毛蓬松、看不出手指 → 更像猫爪）**只能得出「更像 X」，不足以写进名字或登记**——名字只写可确认的动作（「掀开蕾丝帽露头顶」「猫爪破洞偷硬币」），不确定项进备注，并把「要不要按某身份改名」抛给用户定。平台标签也不能当身份证据（原页标签写着 doll/alien/disguise，同样不等于画面里就是娃娃）。
- **上传者/平台写的说明文字与标签都不是画面证据**：原始页标签（如 whip / slave / memes）、原页的 alt / 一句话描述（如 `Celebrity gif. … giving an uncomfortable grin and nod in agreement`）都不得用来给动作下结论，只能当检索线索与出处。实测冲突：原页写「nod in agreement」并打 nod/agree 标签的名人动图，三轮多帧核验（含参照物锚定）都查不到头部上下位移，实际只有挑眉/眯眼/咧嘴。**冲突时按画面命名**，把分歧原样写进登记备注（不圆场、不按标签改名），并在汇报里把「保持画面名 / 改成通行梗名 / 改中性名」三个选项抛给用户定。
- **画面内文字两次识读互相矛盾 → 一律不采信、不转写**：包装小字、外文说明、边角水印这类内容在不同轮次会读出不同东西（同一块纸板一次说能认出网址片段、另一次说「未见可靠网址」）——这时的结论就是「读不可靠」：登记里写「多次识读结果不一致，未采信」，最多把放大图一并交给用户自己看，绝不把某一次的转写当事实落进台账。
- **情绪词可以进文件名但要标明是判断**：库内命名风格允许「无奈扶额」这类判断式短名，但描述里要写清依据（眉眼下垂、抿嘴、扶额）并说明「这是对表情的判断」。
- **一个动作有两种合理读法时，名字取中性的那个，两种读法都写进备注**：实测加菲猫举爪＝既可读「招手」、也可按原页标签（no thanks / stop / not today）读「不必了」——名字写「举爪摆手」，台账标「⚠️ 手势两义，按用途取用前先看片」，把判断权交回用户。
- **认角色靠特征枚举 + 发布方佐证，不靠整体感觉**：放大首帧后逐项报特征（毛色、条纹/花色、眼形、鼻嘴形），再看发布账号的目录与出处页是否支持该角色（实测橘色＋头背黑色排线条纹＋大椭圆眼皮＋粉黄嘴部，发布方是播过该动画的官方账号 → 才写「加菲猫」）。特征列不全就别写俗名，退回中性描述。
- **命名规格**：中文描述性名，≤12 字，结构=主体+动作/梗点（「黑猫敲代码」「鸡蛋蒸汽悬浮」「泳池挥杆搅水」）；同名冲突加特征区分（「虎斑猫震惊」）。入库前 `ls GIF动图 | grep -i <关键词>` 查同名。
- **同一角色沿用库里既有中文名**：动名之前先 `grep -i <关键词> README.md` 看库里是否已有同角色/同主题条目，已有「科米特蛙弹钢琴」就写「科米特蛙…」，别自创「科米蛙」——同一角色在库里名字不统一就会被拆散、检索不到。
- **单帧辨认不稳的品牌 logo 不进台账**（如连帽衫上的运动品牌图标）：写错品牌比缺一项更糟，宁可不写。

## 坑（实测）

- **prompt 里带「图1到图4按顺序命名」会让模型对单张图幻觉编造多段描述**（一张图被编出 4 个名字）→ 多图时间轴必须给「按时间顺序的同一段动图」语境；批量命名要逐张调用。
- **单帧误读是常态，不是异常**：首帧单图曾读出「鸡蛋底部插着两根细签」（实为完整鸡蛋悬在蒸汽上）、「气球吊着红色背包」（实为穿背带的狗，背脊+背带被读成背包）。**问「这是什么」必须带首尾帧**——画面只见局部时模型会连类别都读错（动物→物件），抽帧复核的成本远低于改名返工。命名与描述一律按核验后的事实写。
- **模型会用解说式语言编因果**（「把她冲得翻身」「他明显在催促」）——读到这类句子先降级成可见描述再落笔。
- **判动作的决定性证据只有「多帧 + 参照物视觉核验」；像素测量只能当旁证**：GIF 调色板抖动噪声布满全帧——相邻帧差分口径完全无效（实测差异区竖直跨度 350-368px／画面高 372px），全帧暗区质心也会被身体/背景稀释（实测 2.5px，既可能真零位移、也可能被摊平）。要报幅度就换**目标化探针**：探测区选**颜色可区分的部位**（人脸=肤色块、动物头=深色斑块），阈值逐幅调（实测同一张小图暗阈值 80 零匹配、100~140 才有信号），照实写 px 与占比（「脸部肤色块横向极差 3.55px／350px≈1%」「猫头暗部 4~8px／246px≈2~3%」），**措辞停在「趋近静帧 / 轻摇」，绝不外推成「它在摇头」**。**两个静态口径仍成立**：① 整段质心极差 <1px ＝「这条几乎没动」的有效旁证，直接写进近静止的剪辑警告；② 几何一致性（见下条）。探针脚本与阈值细节：`asset-intake-verification` 的 `scripts/gif_motion_probe.py` + `references/verification-recipes.md`。
- **但静态生成图的几何/一致性，要用像素测量定论**：上一条只针对 GIF 动作判定（压缩噪声会摊平位移）。对静态渲染图（SVG/网页出图、图标、对比图、卡片），逐格 bbox、前景像素量、四角 alpha 是硬证据——模型说「其中一个明显小一圈 / 位置跑偏 / 颜色不一样」先量再驳，相等就把测量结果写进汇报（实测五格 bbox 全等 728×870，模型仍在说「最右边那个头明显小一圈」）。
- **核细节前先放大裁切，别送整张缩略图**（裁切+放大直接用 `scripts/zoom_crop.py`，支持 `--box L,T,R,B` 比例与 `--scale`；别每轮手写 PIL，也便于把同一个主体在不同帧裁成同一尺寸对比）：数「几个角 / 几个字 / 有没有差异」这类细节，半尺寸预览会让模型读错——实测同一张图在缩略图下 4 角星与 6 角星都被读成五角星，把元素逐个裁出来放大拼成对照图（长边约 1200px）再问，同一批立刻数对。细节类结论只在放大图上取，缩略图结论只能当线索。
- **极小/极短动图判细微摆动，同样靠裁+放大**：<200px 或只有 4~12 帧的循环，全帧读不出动作。先问模型「主体在画面哪个位置、约占宽高各百分之几」拿到裁剪框（如 500×325 里「头在右上偏中、约占宽 30% 高 40%」→ 裁 290,30–460,180），把主体裁出再 3× LANCZOS 放大逐帧送——实测全帧 3.68px/宽 169px（≈2%）的横向位移，放大后模型能指出「第 4 帧最偏画面右侧」；不放大就只能得到「没动」的错结论。
- 可疑信号：命名与图面不搭、太抽象、含具体人物身份或动作推测（「翻车」「赶图纸」「签字」「Liam」）→ 必须抽帧复核。
- **不要第一轮就收工**：小批（<12 张）全部核，成批按可疑信号抽查，改过名字的要重核。

## 交付口径

汇报识图/入库结果时给证据表，不要只用一句话总结：**目标绝对路径 / 大小 / md5（源与目标相等才算没传坏）/ 索引或 README 行号 / 库内总数**，并说明有无同名副本、有无散落文件。用户会来复核存放位置，主动给证据比等他问一轮省事。

登记条目（README 行）要素，缺一不可：**原题 · 出处（账号/原帖与板块）· 画面上的水印 · 实拍还是 AI 或数字绘制 · 「多帧时间轴核验」字样 · 适合场景**。角标/水印要转写就**只裁那个角落放大 4 倍**再从放大图读（`scripts/zoom_crop.py`），并在台账注明辨识度（如「首个账号名辨识度有限」）——全图问模型读角标小字必错。水印与 AI 生成属性必须显式写出——有第三方水印（如 `4GIFs.com`）或 AI 生成的素材能不能上片是用户自己定的，前提是登记里写了。

再加两条**剪辑向警告**（用户会拿这些条目直接决定能不能用，漏了他得回头问）：① **近静止/极短循环**（<0.5s、4~12 帧）写明帧数与时长 +「当动态素材用会像静帧」；② **低分辨率/小体积**写明像素尺寸与 KB +「剪进正片会糊，只适合小尺寸贴图/角标」。

**写日期前先跑 `date`**：长会话跨零点后容易按惯性沿用前一天的日期（下午开的会话，次日上午仍在写前一天的日期），每批登记前确认当天日期。

## 台账核对（入库收尾 / 被问「库对不对」时）

- 跑 `scripts/check_library_integrity.py [素材库根目录]`（默认 `~/Documents/素材/表情包`）：双向比对 README 条目 ↔ 实体文件，列出「有条目无文件」「有文件无条目」「README 内重复条目」。脚本只解析 `GIF动图/` 的条目格式（`ENTRY_DIR` 常量），README 里其他子目录（音效/、静态表情包/）不在比对范围——要扩先改常量再跑。
- **中文文件名比对前两侧都 `unicodedata.normalize('NFC', s)`**：macOS 磁盘上的中文名多是 NFD 分解式，README 文本是 NFC，直接集合相减会把**同一个文件**虚报成两条错位；同时过滤 `.DS_Store` 等非目标后缀（不滤会虚增一项）。先排除这条，再怀疑真的缺文件。
- **发现错位只报告，不自行配对改名**：名字像 ≠ 同一张。要实锤就用完整签名 URL 拉源文件比 md5（短链会超时），否则把两份清单列给用户等确认。
- 只读核对，不动别人的库：报告里给行号（`L<n>`）方便用户回查。
- **入库前按 ID 去重，命中后要做字节实锤**：`grep -c <GIF_ID> README.md` 命中不算完——把用户这次的签名 URL 重新下一份，与库内文件比 md5：一致就回「该 ID 已于 <日期> 入库为 <名字>，未重复入库」并给出两组 md5（不重复入库、不改台账）；不一致＝同名不同源，正常入库并加特征区分。比对各库内文件只用 `md5 -q` / `ls` 读，不要改动它去凑比对。
