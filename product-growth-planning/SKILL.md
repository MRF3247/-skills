# 产品增长与冷启动方案策划（0 到 1）

触发：用户/老板要求「帮我想想增长方案」「从 0 起步怎么做」「向核心用户推广的落地方案」「竞品怎么做的增长」「build in public 方案」。2026-08 实测（SciLink 冷启动方案，老板交办）。

## 核心流程

1. **先盘点资源约束（第一性，决定方案形态）**：用户基数（0 用户？有付费用户？）、团队人力（几个运营/专业人才）、人脉资源（能否触达目标人群）、预算、时间窗口。**方案假设必须基于真实基数**——0 用户起步时，「从现有付费用户里筛种子用户」不成立，第一性问题变成「第一批人从哪来」。
2. **收集输入源**（并行）：
   - 飞书文档：`lark-cli docs +fetch --doc <URL> --doc-format markdown`（先 skill_view lark-doc 看 fetch 规范）
   - 微信文章：web_extract 会误拦 mp.weixin.qq.com（返回 Blocked: internal network）→ **curl 直连**（~3.5MB HTML：标题 `<h1>`、公众号 `id="js_name"`、发布时间 `var publish_time = "秒"`、正文 `id="js_content"` strip 标签 + html.unescape）——详见 xiaohongshu-content-scraping skill「微信文章收录」节
   - 同事已有策略文档：先搜知识库（grep 关键词如「风口/季度/需求」），避免重复调研、拿现成数据（如平台搜索指数/季节性）
   - 竞品检索：web_search 按「竞品名 + 增长/用户/打法」多轮并行
3. **需求风口分析**：季节性/事件驱动的需求窗口（如职称申报季 8-9 月、毕业季 4-5 月、基金季 Q1）。找三样证据：①事件驱动（申报/评审时间线）；②平台搜索数据（指数峰值月份）；③全年节奏中的承接位。结论落成「窗口 + 预算集中 + 内容截流」动作。
4. **竞品增长案例拆解**：每个竞品固定结构 = 怎么起来的（发展脉络）→ 核心打法（精细步骤，1.2.3.…）→ 结果（可量化）→ 对我们的启示。不写泛泛的「它做得很好」，要写「它第 1 步做了什么、第 2 步做了什么」。已验证案例库见 references/product-growth-cases.md。
5. **方案设计**（按资源形态选型）：
   - 0 用户 + 有人脉 + 少人力 → **Build in Public**：把「产品从 0 到 1 的真实构建」变成内容资产，三个内容引擎（①产品进度周更[负责人:产品/技术,每周≤30min] ②用户共创故事[每两周] ③专业审稿人把关[每周 1-2h，做把关+背书不陪跑]）；人脉=首批共创者（内测资格+身份，反馈变内容素材）；获客双通道（人脉 1v1 邀请 + 官宣内容自然报名）；内测转化路径 = 申请内测→审核→发放免费额度（3 个月）→到期转付费。
   - 有用户基础 → 顾问团/大使机制：从高活跃用户筛种子（给身份/舞台/可写进 CV 的头衔 > 现金），参与即传播（丁香医生模式），科室/师门裂变。
6. **交付**：用户/老板要可交付物时**生成 Word 文档**（docx-js，见下节），文档结构 = 背景与前提（含资源约束）→ 策略主轴 → 风口 → 机制 → 日历 → 里程碑指标 → 风险红线 → 竞品参考 → 北极星指标。

## Build in Public 要点（0 声量冷启动）

- **叙事前提必须匹配产品状态**：产品已上线 → 叙事是「已上线 + 招募首批共创者/公开构建用户从 0 到 1」，**不能说成「我们准备从 0 做一款产品」**（用户 2026-08-10 纠正：「官宣听起来像是还没开始做一样，我们的产品已经上线了」）
- 三个内容引擎的选题示例：进度（「为什么先做 X 模块」「XX 被审稿人打回 3 次的教训」）；共创者故事（「一位主治医生的第一周体验」）；审稿人点评（「医学审稿人怎么看 AI 写的讨论部分」——专业背书是竞品没有的稀缺形态）
- 红线：公开过程/决策不公开代码核心；合规话术（医学产品禁「代写/包过/降AI率」）；区分「已上线/开发中/规划中」不夸大——build in public 的信任一旦透支就全完了；共创者预期管理（告知早期版本不完整）

## Word 文档交付（docx-js，macOS 实测）

- 用 npm `docx` 包写 node 脚本生成（`npm install docx` 于工作目录），Packer.toBuffer + fs.writeFileSync
- 中文文档：默认字体设 `'PingFang SC'`；标题用 HeadingLevel（大纲/目录可识别）；表格：`columnWidths` 和每个 cell 的 `width` 都要设（WidthType.DXA），宽度和=表宽；表头 shading 用 `ShadingType.CLEAR`（SOLID 渲染成黑）；**加粗前缀别和正文重复**（LI 函数里 boldPrefix 与 text 各放一半，否则输出「通道A：通道A：内容」式重复——2026-08-10 实测踩坑）
- **macOS 无 LibreOffice 时验证**：docx 是 zip → `zipfile` 读 `word/document.xml`，strip 标签后断言关键文本存在/无重复 + 数 `<w:tbl>` 数量核对表格数；不需要渲染 PDF。生成脚本与验证脚本分开（生成脚本可留 scripts/ 复用，验证临时跑完删）

## 坑（实测）

- 方案里「种子用户来源」写错会整体翻车：0 用户时别写「从付费用户筛选」，先确认团队有没有人脉/地推可触达的第一批人
- 单专业人才（如 1 名医学审稿人）不能陪跑：把角色重定义为「把关+背书」（每周固定 1-2 小时审要发布的内容），不做一对一服务
- 老板要「少投入人力」时优先「内容代替运营」的方案形态（build in public/共创机制），不要设计需要客服/陪跑/社群运营人力的方案
- 竞品案例只写「它对我们的启示」会空洞，必须写「它的第 1/2/3 步」——搜索时优先找带发展脉络/步骤的文章
