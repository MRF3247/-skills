# 产品需求文档（运营 / 内容侧 → 产品）

运营、内容、增长团队向产品提需求，以及评审产品/研发写回来的需求与原型，都用这一套。核心立场：**需求的价值由提出方举证，产品只负责判断怎么做**。

## When to Use

- 用户要给团队定「提需求要用什么格式」，或直接要一个需求模板。
- 用户发来产品/研发写的需求文档、原型链接，问「有什么可参考之处 / 好不好」。
- 一条具体需求要落成文档、写进飞书后再发给产品。

不适用：产品定价与回本测算（见 product-unit-economics）、内容选题与起号（见 video-content-strategy）。

先确认承接格式：问清「这条需求最后落在哪、对方后台有几个字段」。需求系统常见只有名称 / 描述 / 链接三字段，那就直接给「一之二」压缩版，别先甩完整字段表——复杂模板会被当场退回重写。

## 一、完整字段表（没有固定系统、或需求要进评审会时用）

| 字段 | 必填 | 怎么写 |
|-|-|-|
| 需求标题 | 是 | 动词开头：支持 / 增加 / 优化 / 修复 + 对象。一句话说清改什么 |
| 需求编号 | 是 | 1.1 / 2.3 这类，便于别处引用「见 2.3」 |
| 提出人 / 日期 | 是 | 谁提的 + 日期 |
| 需求类型 | 是 | 功能新增 / 体验优化 / 数据埋点 / Bug / 内容配置 |
| 背景与证据 | 是 | 现状 → 卡在哪一步 → 截图 / 评论原话 / 后台数据链接 |
| 目标用户与场景 | 是 | 谁（具体人群）+ 在做哪件事时遇到 |
| 期望结果 | 是 | 用户视角一句话：他能顺利做完什么 |
| 具体要什么 | 是 | 逐条 3–6 条可勾选动作，不写「体验更好」这类空话 |
| 规则与阈值 | 视需求 | 门槛写成数字 + 边界情况怎么处理 |
| 用户看到的原文 | 视需求 | 提示语、按钮、报错文案直接给成品 |
| 不要什么 | 否 | 划边界，防止做偏或做太大 |
| 验收标准 | 是 | 可测判定，含时间 / 数量 / 顺序等可核对指标 |
| 优先级 | 是 | 只三档：P0 阻塞发布 / P1 本月 / P2 有空再做 |
| 期望时间 | 否 | 最晚何时要 + 为什么是这个时间 |
| 不做的后果 | 否 | 影响多少用户、影响哪条链路 |
| 附件与参考 | 否 | 截图、竞品链接、样例文件 |
| 状态 | 产品填 | 待评审 / 已排期 / 开发中 / 已上线 / 不做（含原因） |

三条硬规则：先讲问题再讲方案；必须带证据；必须可验收。优先级只允许三档，防止所有人都写「紧急」。

## 一之二、需求系统只有「名称 / 描述 / 链接」三字段时的压缩版

对方的需求管理后台只收三个字段时，别搬完整字段表，压成三段：

- **名称**：动词 + 对象 + 范围，20 字内；禁用「优化体验」「加个功能」。
- **描述**：固定标签五段、5 行内写完——【现状】【证据】【要什么】【验收】【优先级】。模板用 `<pre lang="text">` 给可复制成品。
- **链接**：一屏原型（带 screen 参数）/ 红框截图 / 长规则 / 竞品参考；一条需求一个链接，不放目录页。

其余字段（不要什么、多端影响、提示语原文、状态）不删，移到链接指向的文档里，描述只留摘要。判断标准：5 行还写不完，说明需求本身没想清楚。

## 二、评审产品/研发写回来的需求：5 个加分项

1. **需求挂界面**：每条需求贴在具体那一屏、那个控件旁（原型标注），开发不用猜改哪里。
2. **阈值写成数字**：「分组数 > 1」「每组 > 50 条」「超过 10 组只取前 10 个」——开发能写代码，测试能写用例，没有「我以为」的空间。
3. **异常与降级路径写清**，连提示语原文一起给（不写「有问题就提示」）。
4. **文案给成品**：整段可复制的提示 / 遮罩 / 报错文本，省一轮来回。
5. **多端影响单列一条**：一个改动影响哪几个端（平台 / Agent / 小程序）全部列出，防漏端。

## 三、评审同样的文档：4 个常见缺口

1. 全篇没有「为什么做」——没有用户证据、没有目标，导致无人能判优先级。这是提出方必须补的。
2. 没有优先级、时间、验收标准——做完无法判定对错。
3. 状态靠批注零散体现，做完了不留痕。
4. 内容只在原型工具里（需登录、受浏览器限制、不可检索、不能拷出引用）。

评审输出固定三段：**可参考的做法 → 缺口 → 合并后的方案**。不要只列缺点，先认可对方做法，用户要的是能拿来用的增量。

## 四、写进飞书文档

- 新增内容用 `lark-cli docs +update --doc <url_or_token> --as user --command append --content "$(cat /tmp/x.xml)"`：先把 XML 写进临时文件再 `"$(cat ...)"` 传入，避免引号与换行被 shell 吃掉。
- 改掉已写好的整段（不是追加）用 `--command block_replace --start-block-id <首块ID> --end-block-id -1`（`-1` = 到文末），块 ID 先 `+fetch --detail with-ids` 取；**不要用 `overwrite`**，它会丢评论和不能回放的资源。
- 表格用 `<table><colgroup><col width="140"/>…</colgroup><thead>…`；表头 `background-color="light-gray"`。
- `<callout>` 子块只支持 `p/ol/ul/checkbox`，不要塞表格或图片。
- `<ol>` 写 `seq` 会报 `degrade_code=5002`（服务端 schema 不认该属性），有序列表默认就自动编号，直接省掉。
- 写完必须 `docs +fetch --doc-format markdown` 回读验证：表格列数、列表层级、加粗是否都渲染出来。
