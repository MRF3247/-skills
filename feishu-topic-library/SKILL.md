# 飞书选题库 / 痛点库：文档 → 多维表格 + 云文档

## When to Use

- 用户给一篇「产品内容选题库 / 选题库」云文档 + 一个多维表格链接，要求「把选题分门别类装进多维表格」
- 要求把文档里的选题拆成一篇篇云文档，链接回填到表里
- 要求重构已有选题库表结构（换主字段、合并列、拆行、重打标签）

**与 `feishu-content-material-library` 的分工**：那个管「日更资讯卡片写入内容物料库」；本技能管「选题池本身的结构：从文档建库、拆云文档、按痛点重构」。两者共用同一个 Base（`PCm9b6saQaJ8gmsqAxTcqWHtnVj`，刀客轻研选题库）。

## 对象坐标

| 角色 | 表 | table_id |
|---|---|---|
| 资讯内容选题库（内容号@刀客轻研SciLink + 公众号） | 每日资讯选题 | `tblfAf9h81t9oVq9` |
| 产品内容选题库（小红书 + 服务号，推广性质） | 痛点驱动选题池 | `tblW0VnKXJaPlids` |

Base 的 wiki 节点就是用户发来的 `my.feishu.cn/wiki/...` 链接，先 `lark-cli base +url-resolve --url '<url>' --as user` 拿 `base_token`，别猜。

**产品能力源文档**：`https://my.feishu.cn/wiki/CAzqwRKK4iwKuokJo5zcihOxnWe`（SciLink 功能大全，70 项能力 + 明确「做不到」清单）。写业务对接点、判对接度、策划产品向选题都先查它，别凭印象编功能。

## 用户口径（这些是他明确改过的，别再走回老样子）

1. **云文档只放内容，不放元信息。** 归属章节、用户处境、研究类型、痛点分析、业务对接点这类「多维表格里已经有的」字段，**一律不要出现在云文档正文里**。建文档时只写标题 + 文案步骤 + 配图。用户会直接在文档里批注「这部分都删掉，在多维表格里有了」。顶部那张元信息小表也算——建的时候干脆别写。
2. **文档命名 `N.标题`。** N 取它在**原文档所属章节内的位置序号**（不是重排后的 1..n），所以中间会有跳号（没文案配图的小节不建文档，号就空着）。不要前缀「四、场景案例 ·」这类章节名。改名用 `lark-cli drive +update-title --url <url> --title '<N.标题>'`。
3. **拆分粒度：只给真有内容（文案+配图）的选题建文档。** 只有标题的选题留在表里不带文档链接；先报数量让用户选粒度（「全部建 / 只建带文案配图的 / 全部但轻量」），别默认全建。
4. **表格是痛点驱动的：痛点场景必须是第一列、冻结。** 后面的工作都从痛点出发，选题标题是痛点的派生物。
5. **标签要按内容重做，不要沿用混装的旧标签。** 旧表里「数据收集、处理」同时装着研究设计和统计分析，「机器学习」和「预测模型」重复——发现这种重叠就换一套干净的分类，并给**全表每一行**重打，不留空。
6. **多轮迭代是常态。** 用户会连着几轮改结构（删列 → 合并列 → 拆行 → 换主字段）。每轮落地后汇报三件事：行数变化、标签分布、**需要他拍板的占位/重复**（原文缺字段的占位行、一个源头拆成多行后重复的选题列）。

## 建库流程

### 1. 解析源文档

```bash
lark-cli docs +fetch --doc '<wiki 或 docx URL>' --doc-format markdown --as user > src_doc.json
```

`markdown` 格式会把文档里的表格输出成**内嵌 HTML `<table>`**，图片是 `<img … src="<img_token>"/>`。用 Python 按 `<table>` / `<tr>` / `<td>` 切，再按 `# ` / `## ` 切章节。

单元格里的多条目要用 **`<li>` 嵌套树**拆，不能只按 `<br/>` 切：`<ol>/<ul>` 里的每一项要靠 `</li>` 断句，否则会串成一条（「纳排标准定不清…随访起点和终点不统一…」粘成一句）。解析函数见 `references/doc-to-base-split-recipes.md`。

### 2. 设计字段（一次 `+table-create --fields`）

列序即创建顺序，**主字段必须是你想放第一列的那个字段**（见下方「主字段不可换」）。一个够用的起点：

`痛点场景`(text, 主字段) → `痛点分类`(select) → `研究类型`(select) → `选题标题`(text, 多条用「；」) → `业务对接点`(text) → `参考稿件`(text) → `选题文档`(text)

### 3. 写记录

`{"create_records":[{字段名:[值]}]}`，**10–15 条一批**，每批失败单独定位。写入前必须跑一遍 select 值白名单校验（见下方坑 #1）。写完 `+record-list --format ndjson` 读回数行数、查重。

### 4. 拆云文档（只对选定的那批）

```bash
lark-cli drive +create-folder --name '产品内容选题库·选题文档' --as user   # 先建一个专属文件夹
lark-cli docs +create --doc-format xml --content @xml/case00.xml \
  --parent-token <folder_token> --as user
```

XML 里图片直接写 **`<img src="<原文档的 img_token>"/>`**——这是「复制原始图片」，不用先 `+media-download` 再 `+media-insert`，一步保住原图和顺序。模板见 `references/doc-to-base-split-recipes.md`。

### 5. 回填链接

`+record-batch-update` 写 `选题文档` 列（纯 URL，不套 markdown）。

### 6. 验收

逐篇 `docs +fetch --doc-format markdown` 数 `![` 的出现次数，和源文档该小节的图片数逐一比对；再 `+record-list` 确认「总数 / 有文档数 / 标签无空值」。

## 重构已有表：先想清楚代价

主字段不可换（见坑 #3），但**字段顺序可以调**（坑 #4：`+view-set-visible-fields`）。所以「换第一列」仍需改主字段名 + 重建记录；单纯调列序不用重建。重构流程：

1. `+field-update` 把**原主字段改名**成目标第一列（不改 type），它的值由后续重建记录写入。
2. 删掉所有其它字段，按目标列序一次 `+field-create` 重建。
3. 删掉全部记录，按新结构重新解析源文档 + 重新插入。
4. 重新回填文档链接。

因为记录本来就要重建，字段删除不损失任何东西——**这是唯一零额外成本做列序的时机**，别在保留数据的前提下硬排。

合并两列再加一行一痛点拆行时注意：同一个源头（比如某个研究类型下的 6 条痛点）共用的那一组选题，拆开后每行都会挂同一串选题。**要重复还是留空，先跟用户确认**；默认保留（不丢信息），并在汇报里点明「这几行选题是重复的」。

拆行时还要防「同一句话的两个版本」：用户疑问（口语全句）和痛点分析（短标签）常常是同一件事的两种说法，两个都拆会得到两行近似重复。**取口语全句那一版**，短标签版本丢掉。

## 补痛点场景：先查覆盖密度，再补具体场景

用户问「全流程还有没有能补的痛点」时，不要凭印象列，按**科研全流程 14 个阶段**数一遍现有条数，缺口一目了然（实测容易空的是：科研绘图、投稿返修、国自然基金、发表后与职称、团队协作、数据**收集**阶段、合规与 AI 使用）。

14 个阶段：认知动机 → 文献检索阅读 → 选题开题 → 研究设计（纳排/样本量/伦理/注册）→ 数据收集 → 数据清洗编码 → 统计分析 → 机器学习预测模型 → 科研绘图 → 论文写作 → 投稿返修 → 国自然基金 → 发表后与职称成果 → 团队协作与外部依赖（＋合规与 AI 使用横切所有阶段）。

写新痛点时**必须是具体场景，不是分类**：「科研绘图」不合格，「SPSS 出的图被退，期刊要 300dpi TIFF，截图只有 96dpi」才是合格的一条。带具体数字、具体工具、具体系统报错、具体对话（「统计师问你要做什么分析」）。

清单交用户时按阶段分表，每条给出**痛点分类 + 研究类型**两个建议标签，并用 ★ 标出「真实卡点且产品能接」的。等用户拍板后整批插入，插入前照样跑 select 白名单校验。

顺手做一次**存量分类体检**：原文档「大类选题」那章的分类很粗，按选题内容归错列很常见（样本量/纳排→研究设计、统计方法/步骤→统计分析、怎么写论文→论文写作）。发现错位一并报给用户，改不改让他定。

## 一选题一行（A+）的三个坑

用户不想建子表、选「就在现表里拆成一选题一行」时，拆完必须做两件事：

1. **去重。** 原表里同一组选题会挂在同组的多条痛点下（例如「回顾性队列」的 6 条痛点都挂同样的 5 个选题）。拆行后这组选题在每条痛点上各出现一次，会变成 173 行重复——表的三分之一是冗余。处理：每个重复选题只留在语义最匹配的那一条痛点上，其余删掉。
2. **补回空痛点。** 去重删行时，那些“只有重复选题、没有专属选题”的痛点会被删到零行，**从表里直接消失**（实测丢了 21 个）。删完必须用删前快照比对痛点集合，把缺失的痛点补回成「有痛点、选题标题空」的行。否则痛点库会静默缩水。

另外，拆分后选题标题不再需要「1. 2.」编号（一行一条）；分组视图用 `+view-set-group` 按痛点场景分组，视觉上还能保持“一块一块”的旧形态。

## 按产品能力表填业务对接点 + 对接度

用户给一份产品功能清单文档、要求「填业务对接点 + 加一列对接度」时：

1. 先把功能文档读完，建一份**功能清单缩写表**（功能编号 + 一句能力 + **明确写下的做不到**）。平台自述的「没有的能力」跟有的能力一样重要——它决定对接度是 1 还是 2。
2. 逐行写对接度，**最终交付形态是彩色单选标签，不是数字列**——用户靠颜色分流（绿＝可直接做，红＝再等）。选项名把数字带上方便排序（`5 直接可用` `4 稍改可用` `3 需人工主导` `2 只能给框架` `1 产品接不住`），配色 `Gray`→`Green Standard`/`Green Lighter`/`Yellow Light`/`Orange Light`/`Red Standard`。内部先算数字再回填标签，别直接拍颜色。
3. 业务对接点要**点名具体功能**（带功能编号），写清「能做什么 + 边界在哪」；只写「数据分析」这种废话毫无价值。
4. 发现功能表里有能力但痛点库没覆盖的，**新增痛点行**（一条能力对一条真实场景），不要只在旧行里塞。同理：能力明确做不到的那些痛点，对接度给 1 并写清「平台上没有这个能力」，这是有价值的结论，不要美化。
5. 写完汇报**对接度分布**和**对接度=1 的清单**——那批是产品空位，往往比补 30 条新痛点更有决策价值。

## 工具坑（都是这一路踩出来的）

1. **select 值不在 options 里 → 整批 `800030005 not_found`，且报文不带字段名和行号。** 写前用 `+field-list` 的 `options[].name` 建白名单逐条校验；同一概念在源文档里常写成多种字面值（「只有科室病例／只有病例数据／只有科室病历」），必须统一到 options 里那一个。定位失败批的办法：单条提交，逐个字段删掉再试，去掉哪个字段就成功，那个字段就是元凶。
2. **写失败的批次不代表一条没进去。** 分批循环中途失败时，已成功批和失败批都可能有残留，直接重跑会生成重复行。每轮结束 `+record-list --format ndjson` 数实际行数、按业务主键查重，再决定补哪几条。
3. **主字段（第一列）不可更换。** 没有「把某字段设为第一列」的接口，主字段永远最左、自动冻结。要换第一列只能改原主字段的名字和内容。
4. **字段显示顺序可以调，别瞎重建。** `+field-list` 的顺序**不是**展示顺序（重建后主字段甚至会排在末尾）；展示顺序看 `+view-get-visible-fields`。要调整就用 `+view-set-visible-fields --view-id <vew> --json '{"visible_fields":[...]}'` 传完整有序字段名列表（它也控制隐藏）。只有主字段（第一列、自动冻结）不能换，换它仍要改主字段名+重建记录。
5. **`lark-cli` 会在 JSON 后面追加 `_notice` 块**（版本提示）。直接 `json.load(stdout)` 会抛 `Expecting value`，要用 `2>/dev/null` 并在解析前切掉尾部，或只取第一个完整 JSON 对象。
6. **`docs +update --command str_replace --pattern X` 只在单个 block 内匹配。** 表格单元格在 markdown 里显示成 `| 病例对照 |`，但真实 block 文本只有 `病例对照`——带竖线的 pattern 永远匹配不到。单元格改值用 `block_replace --block-id <cell 内 p 的 id>`，id 从 `+fetch --detail with-ids --scope keyword` 取。
7. **`+update` 返回 `ok:false` 但带 `revision_id` ＝ 没匹配到 pattern，不是失败。** 别据此重试，先 `+fetch` 看实际文本。
8. **删一段连续块用 `block_delete --start-block-id <首> --end-block-id <尾>`。** 首尾是同级兄弟块（表格和它后面的几个 h1/p 一起删就传表格 id 到最后一个 p 的 id）。
9. **markdown 格式读回时图片是 `![](url)` 不是 `<img`。** 数 `<img` 会得 0，误判「图没进去」；数 `![`。
10. **`docs +fetch` 里被批注过的块会带 `comment-refs`**，用户用评论圈出「这几块删掉」时，`drive +list-comments` 的 `quote` 就是待删范围；删完再 `+resolve-comment` 把批注标为解决。
