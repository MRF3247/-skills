# 外部导出表 → 多维表格（建模 + 灌数 + 对拍）

## When to Use

- 用户贴一张平台导出的 Excel/CSV（或附件）并说「按这个结构建一张表 / 把数据存进多维表格」。
- 用户给一个空的多维表格链接，要求设计字段结构并灌入历史数据。
- 用户给一份飞书文档（选题库/清单/盘点表），要求「分门别类装进多维表格」，常附带「单条拆成云文档、链接放回表里」→ 走 §14。
- 不适用：只是往已有结构的表里补几条记录（直接用 `lark-base` 的 record 命令）；本地 Excel 的读写加工（用 `xlsx`）。

场景说明：源表常是多块并排的宽表 + 一张空白多维表格，要求「按这个 Excel 的结构设计表，把全部数据存进去」。
命令语法以 `lark-base` skill 为准（`+url-resolve` / `+field-create` / `+record-batch-create` / `+view-set-*`）；本 skill 管**怎么建模、怎么写、怎么验**。

## 1. 先读源表，判断行粒度

- 老式 `.xls`（BIFF）用 `xlrd`、`.xlsx` 用 `openpyxl`；系统 python 常无 pandas/xlrd/openpyxl，建临时 venv 一次装齐（`python3 -m venv v && ./v/bin/pip install openpyxl xlrd`），不改系统环境。`openpyxl.load_workbook(..., data_only=True)` 读公式缓存值；报 `Workbook contains no default style` 是源文件没写样式，忽略即可。
- 平台导出包常是「一张账号总体/汇总 sheet + 每指标一张趋势 sheet」：`wb.sheetnames` 先按前缀分组（`账号总体*` 是汇总，`*趋势` 是日粒度），逐个打印 sheet 名、行数、首行，确认哪张是汇总、哪张是日趋势，别假设 sheet 顺序。
- **先认平台，再认字段**：`曝光 / 封面点击率 / 平均观看时长 / 完播率 / 主页访客 / 主页转粉率 / 发布图文|视频` 这套组合是小红书创作者中心导出；视频号是「播放量」口径，B站 是「播放/粉丝」口径，公众号导出的渠道表长成「日期×渠道×阅读人数」。别凭源表字段名（例：附件字段叫 `SciLink近30天`）推断平台或账号——字段名是用户随手起的，平台看指标口径；拿不准就在交付里写一句「按 X 平台口径入库」，让用户一句话就能纠正。
- 多块并排的表先按列区间切 block（如 cols 1-3 / 5-9 / 11-15），逐块打印表头+行数，确认每块粒度：日×渠道 / 日 / 篇×渠道 常常同时存在。
- `20261015` 这类紧凑日期先拆成 `2026-10-15`；`0.0` 浮点先整数化（`int(v) if v==int(v)`）。
- 单位挂在值里（`23%`、`17秒`、`1569秒`）要在解析层剥掉：`%` 除以 100 转小数、`秒` 直接取数值；汇总 sheet 的百分比是「5.0 表示 5%」的原始数，按 0–100 口径存，别再除一次。
- 环比行按基础名回溯：指标名常带 `(%)`/`(s)` 后缀（`封面点击率(%)`），而环比行叫 `封面点击率环比(%)`。**先剥后缀再拼 `base+环比(%)` / `base+环比`**，直接拼 `k+"环比(%)"` 会匹配不到、环比列静默为 None——这种漏匹配不会报错，只能靠人工看输出发现。

## 2. 建模：先判断「一张表够不够」

源表粒度决定表数。「日趋势」+「账号总体/汇总」两种粒度**仍装一张表**：总体走 `记录类型=30天总体` 的行，用 `指标/数值/单位/环比(%)` 四列承载，日行这几列留空、总体行日期留空，再用记录类型过滤的视图互相隔离。只有**不同平台/账号**才拆表——一表一账号（见 §11 表命名）。

用户只给一张空表、且数据是单一粒度时，默认**不要**擅自拆成多张表：

1. 加单选字段 `记录类型`，取值=各 block 的语义名（如 `渠道日趋势` / `账号日指标` / `内容来源`）。
2. 所有 block 的列并成一张宽表，不属于该型的列留空——空单元格没有成本，比拆表好查。
3. 每个记录类型建一个 grid 视图：`+view-set-filter` 单选 intersects、`+view-set-sort` 主时间列 desc（来源型按阅读量 desc）、`+view-set-visible-fields` 只留相关列；原视图改名「全部数据」。
4. 字段名照源表/用户的叫法，不自创黑话；易误解的口径写进字段 `description`（例：「占比=该渠道内占比，不是占全站」）。

主字段：空表自带的 `文本` 主字段**改名复用**，不要再新建主键列——主字段必须是 text：

```bash
lark-cli base +field-update --base-token $B --table-id $T --field-id <主字段id> \
  --json '{"name":"记录名称","type":"text","description":"日期 · 维度"}' --yes --as user
```

记录名称拼 `日期 · 维度`（来源型再加 `· 标题 · 渠道`），跨类型也能读懂、能排序。

### 平台导出包：一张表（日趋势宽表 + 总体行）

**用户不要别人替他统计**——原话「我不需要你统计，我后面会对所有数据进行统一统计」。所以平台导出包（「账号总体XX数据 + 各指标趋势」各一张 sheet）按下面装：

- **一张表**：主字段 `记录名称` + `记录类型`(单选：`日趋势` / `30天总体`) + `日期`(datetime) + `周起始日`(datetime) + `月`(text `YYYY-MM`)，之后每个日趋势 sheet 一列。零值日期照录（账号没发内容那几天源表就是 0，不是缺数据，别删行）。
- 源表「账号总体」sheet 的值**不另建指标卡表**，而是同表里 `记录类型=30天总体` 的行：`指标` / `数值` / `单位` / `环比(%)` 四列有值，`记录名称`=`30天总体·曝光`。30 日 + 18 指标 = 48 行即「完整备份」，这就是用户要的形态。
- 拆成「表1 日明细 + 表2 近30天汇总指标卡」的做法已被用户当场删表否决，**别再拆**；只有用户明确说「要一张指标汇总表」才建表2（混合单位共用一个 number 字段、单位单列，百分比按 0–100 存并标 `%`，不设 `percentage:true`）。
- 汇总 sheet 里的 `XX环比(%)` 行**不单独成行**，折进对应指标的 `环比(%)` 列，指标行数=去环比后的指标数。
- 每个数字都留出处：`数据来源` text 字段写清源附件字段名 + 文件名 + sheet 名，日后对不上账才追得回。
- 解析+对拍脚本模板：`~/Documents/Hermes/scripts/xhs_30d_backup.py`（openpyxl 按 sheet 前缀分流 → 日趋势/总体两份 payload → 打印日趋势合计 vs 总体值逐项对拍）；早期两表版留在 `scripts/scilink_30d_import.py` 可参考。同目录 `.venv_xl` 已装 openpyxl+xlrd。脚本第一个参数是导出目录（`scripts/.venv_xl/bin/python scripts/xhs_30d_backup.py dl_dkr`）：同一套解析服务所有同构账号，换账号只换目录和附件 `file_token`，不要给每张表复制一份脚本。
- 对拍（§7）照做：日趋势合计必须与源表总体值全等，这是验数据、不是替用户做统计，交付时把数字写出来。

## 3. 字段 JSON 实测坑

- select option 的 `hue` 有白名单：`Blue` `Green` `Purple` `Gray` `Orange` `Red` 可用；`DarkGreen` `Cyan` 报 `validation_error 800010205`。选项多就复用可用色，别为配色反复试错。
- 百分比：`{"type":"number","style":{"type":"plain","precision":2,"percentage":true}}`，值传 0–1 小数（不是 0–100）。
- 计数：`precision:0`，需要时加 `thousands_separator:true`。
- 日期：`{"type":"datetime","style":{"format":"yyyy-MM-dd"}}`；写入值 `2026-09-26T00:00:00+08:00`。

## 4. `+field-create` 传数组会「部分成功」

返回 `ok:false` + `Request validation failed with N issues` 不代表全部没建。**重试前先 `+field-list --jq '[.data.fields[] | .name]'`**：已落地的字段再用同名数组重试只会得到重名 validation_error，把真根因盖住。

定位真实失败项：把字段**逐个单独** `+field-create` 跑一遍，谁失败就是谁的 payload 有问题；select 再对每个 hue 单独试。修好后删掉探测用的临时字段。

## 5. 白名单不只管 `--json @file`

大 payload 写文件到 cwd，执行完 `rm -f` 清掉。`+record-batch-create/update` 的 `--json` **不认 `@./x.json`**（报 `positional arguments are not supported`），要传 `--json "$(cat x.json)"`；`+table-create --fields @./fields.json` 才是 `@` 写法。写到 scratch 目录都会被拒（`outside the built-in allowlist`）。

同一条白名单也管**附件下载落地路径**：`+record-download-attachment --output` 指向 scratch 目录会报 `unsafe output path: --file ... outside the built-in allowlist`（提示里写成 `--file`，实际是 `--output`）。`mkdir -p ./dl` 下载到 cwd 再解析即可；多个附件时 `--output` 必须是已存在的目录。

**源文件在附件里时（用户只给一条 `my.feishu.cn/record/…` 链接）**：`+url-resolve` 返回 `input_type=record_share_url` + `base_token` / `table_id` / `record_id` → `+record-get` 打印各 attachment 字段的 `file_token` / `name` / `size` → `+record-download-attachment --file-token … --output ./dl/x.xls`。一个记录里常挂多份不同账号的导出（公众号/服务号/各平台各若干），**按文件名和大小确认拿哪一份**，别假设第一个就是用户要的。

**每轮导入前重新读这条附件记录，不要复用上一轮记住的「某字段=某账号数据」结论**。用户会在会话中途给同一 base 加附件字段、把旧字段改名、甚至把一组附件拆成两组（例：`SciLink近30天` 拆成 `刀客轻研SciLink近30天` + `刀客轻研近30天`，两组各一套同名的 4 个 xlsx、属两个不同账号）。字段名只是用户随手写的标签，唯一可信的是**当前** `+record-list` 打出来的字段名 + 附件 `file_token` / `size`：两组导出文件名完全一样（`近30日涨粉数据.xlsx` …），只能靠 file_token 和 size 区分。拿错源 → 整张表灌错账号 → 清空重灌，代价远高于多读一次。

## 6. 批量灌数

- 空白表建表时会自带几条空记录（用户没填过的那种）：灌数前先 `+record-list --format ndjson` 取 `record_id` 全部删掉，否则表里永远多出几行全空数据。
- 脚本生成 `{"create_records":[...]}`，按 200 条一批切文件，同一表**串行**提交（并行可能触发并发冲突）。
- **整批 `not_found 800030005` 先怀疑「某个 select 值不在 options 里」，不要先怀疑条数或表 id。** 这条错误文案完全看不出真因（明明表在、字段也在）；近义词差异最常见（`只有科室病例` vs 选项里的 `只有科室病历`、`病例对照` vs `病例对照研究`）。写入前用脚本把每条记录的每个 select 值跟你建字段时的 options 集合做一次断言，比事后二分快得多：`assert set(vals) <= options[k]`。
- **定位脏值的二分法**：去掉一个字段能写进去，就说明那个字段的值非法——比逐条试快。注意这个探测会**真的写入一条残缺记录**，探完必须删。
- **测试写入会造重复记录，交付前必须按主字段查重**：探测/重试/分批混跑后，`+record-list --format ndjson` 拉全表 → 按主字段（如选题标题）计数 → 重复的删到只剩一条、残缺的（归属列/select 列全空）也删，最后核「记录数 == 预期数」。写入接口 ok 不代表表里干净。
- `+table-list` 的 `records_count` 有延迟，判总数以 `+record-list --format ndjson` 的行数为准。
- 清空行：`+record-delete` 要 `--yes`，`--record-id` 必须取自 `record-list` 的 ndjson——**不要按规律拼 ID**，猜错的 ID 会让整条命令失败。

## 7. 验收：与源表对拍合计

灌完把全表拉 ndjson（`+record-list --format ndjson --output ./v.ndjson`），用 Python 按口径合计与源表逐项比对：某渠道合计阅读数、各来源合计、每日互动指标总和；行数也要对上（各 block 行数之和 = 表内记录数）。数字全等才算完成，交付时写出对拍数字（多少行、合计多少）。

## 8. 周更型数据表（用户按周更新）

平台导出多为滚动 30 天窗口、同一批数据会重复出现，用户会按周追加。加一层「周」字段会让后续所有汇总不用再算：

- 加 `周起始日`（datetime，`yyyy-MM-dd`），值=自然周（周一~周日）的周一日期；描述里写清口径。对已有记录用 `+record-batch-update`（200/批）按 `日期` 回填。
- **周/月视图 ≠ 汇总表**：用户说「加周汇总和月汇总」「每张表一个周视图、一个月视图」时，只加两个字段 `周起始日`(datetime) + `月`(text `YYYY-MM`) 并各建一个分组视图，**不要另建汇总表**再把数字灌一遍——同一份数据存两处，改一处就和另一处对不上。「我不需要你统计」否决的是自作主张的指标卡汇总表；分组视图是用户自己要的看数形态，不算越界。
- 分组视图三件套：`+view-set-filter` —— 有 `记录类型` 的表**必须** filter 到 `日趋势`（否则总体行会掉进一个空分组，看着像脏数据）；`+view-set-group`（周：`{"group_config":[{"field":"周起始日","desc":true}]}`；月：字段换 `月`）；`+view-set-sort` 日期 asc；`+view-set-visible-fields` 去掉与本维度无关的列。
- 不要一口气建「周汇总/周渠道/周互动」一堆预设视图——用户点名要哪个才建哪个。
- 交付时把**分组实测数字**一起写出来（周/月 × 曝光/观看/净涨粉/发布/互动），用户一眼能核视图对不对；同时提醒**首尾周/月不完整**：滚动 30 天窗口的起止常落在半周、半月，这类合计不能和完整周/月直接比。
- 写一个可反复跑的导入脚本（模板见 `~/Documents/Hermes/scripts/wx_weekly_import.py`）：解析 → 算周起始日 → **按主字段「记录名称」去重** → 200/批串行写入 → 打印与 Excel 的合计对拍。滚动窗口重叠时同一文件再跑一次应输出「待新增 0 行」，这是验证去重是否生效的最快办法（不产生任何写入）。
- 脚本要带 `--table "表名或tbl id"`（内部 `+table-list` 按 name 现查 id）：同一套解析逻辑要服务公众号表、服务号表等**同构**表，表名固定写死在脚本里，第二张表就得复制一份脚本。
- 脚本内所有 `--output` artifact 一律加 `--overwrite`：上一次残留的 `.manifest.json` 会让 `+record-list` 直接失败退出，而脚本若 `json.loads(stdout)` 就会抛成「输出无法解析」的误导性 traceback——真因在 stdout 里，参数解析函数出错时先打印 stdout/stderr 原文。
- 首次导入后务必跑一遍「同文件重导」测试，确认幂等，否则用户第二周导出会把整月数据再灌一遍。
- **源块缺列要在解析层回填，别指望下游补**：微信 `tendency.xls` 的「账号日指标」块只有 分享/跳转原文/收藏/篇数，**阅读只在「渠道日趋势·渠道=全部」块里**，所以日指标行的 `阅读人数` 会整列空着（表里有字段、没值）。导入时按同日「全部」渠道回填 `阅读人数`，已入库的历史行用 `+record-batch-update` 按日期回填；不回填就会出现「周合计对、按日取数全漏」的假象。
- **跨账号 helper 汇总表必须脚本重算，不要手写灌一次**：模板 `~/Documents/Hermes/scripts/weekly_rollup.py`（读全部源表 → 长格式周汇总 → 按主字段「记录名称」幂等 upsert → 打印每周合计对拍）。脚本按「源表里到底有没有这个字段」自适应：某平台将来补采了新列（赞/在看/关注），重跑即自动并入统一口径，不用改代码。手写灌的表第二周就得手改，且口改一处另一处对不上。
- `.xls` 用 xlrd：给脚本配一个脚本目录下的 `.venv`，脚本头部 `except ImportError: os.execv(VENV_PY, [VENV_PY]+sys.argv)` 自愈，避免依赖系统 python。

## 9. 仪表盘（用户说「做成看板/仪表盘，我先看看」）

表建好后用户常紧接着要可视化。顺序固定：`+dashboard-create` 拿 `dashboard_id` → 逐组件**串行** `+dashboard-block-create` → `+dashboard-block-get-data` 逐个读回核对 → `+dashboard-arrange` 整盘编排。

- **建图前先盘点「指标到底落在哪一行」**：一表多 `记录类型`/`渠道` 时，按 `记录类型 × 渠道` 枚举条数再展开看值（如某类型的阅读列全为 null，真阅读在另一类型的「全部」渠道行）。拿错行会得到一整个图的 0，而接口全程不报错。

- 组件编排默认一套：顶部 4 张 `statistics` 指标卡（总量/发文/分享/收藏）→ 通栏 `text` 写口径与北极星指标 → `column` 周趋势 + `column` 周维度拆解 + `combo` 多指标 → `ranking` TOP10 内容。
- **多账号同图必先建 helper 汇总表**：一张图只绑一张表，四个账号的线画不进一张图。按用户要的图形选：
  - **每账号一条线**：长格式周汇总表（周/周起始日/账号/各指标，一周一账号一行）+ 两个 `group_by`（横轴=周，系列=账号）；某平台缺该指标时留 null 不填 0，组件名如实标「（小红书×2）」。
  - **大盘主线 + 每期分账号小柱**：另建**宽表**（一周一行，`大盘` + 各账号各一列），喂 `combo`，`series` 里**各账号排前面、大盘排最后**——飞书 combo 默认第一个指标画柱、其余画线，`series` 顺序就是柱/线开关（写反会得到「大盘一根大柱 + 四账号四条线」）。
  - 长表和宽表都由同一个重算脚本刷（宽表=长表按周聚合），不要手灌；图形写反时改 `series` 顺序即可，不用换组件类型。
- **改版旧看板优先复用旧块**：`type` 不能改但同族图可原地换用途；`--position` 精确排 12 列栅格，让「大盘」真的在最上面；顶层 `data_config` 按 key 合并。
- **大盘口径写进组件名与 text**：缺指标的账号不要静默混算；「本周」= 最新**完整**周（周一一早改版时本周刚开始），卡片筛选「周」= 最新周标签，这条周更维护动作要写进交付。
- **导出里没有的指标不要到别的表里翻**：公众号 `tendency.xls` 只有 阅读人数/分享人数/微信收藏人数/跳转原文/发表篇数/内容来源，**不含「赞」「在看」「新增关注」**。用户说「公众号也有点赞，只是不在同一列」时，先说清源表确实没采到（附字段清单），再给补采路径，不要自己编一个来源、更不要填 0 混进合计。
  - **已验证的补采闭环**：微信后台「数据概况」页切「最近 7 天」截图只有 阅读 / 赞 / 分享 / 在看 / 留言 五个数（没有关注数，关注在「用户分析 → 用户增长」）。用户把图挂到附件字段后 `+record-get` 拿 `file_token` → `+record-download-attachment` 下载 → 先整图 `vision_analyze` 定位，再用 `region` 裁到指标行逐个数核对（数字小、最易读错）→ 用「阅读/分享」与表内同周合计对拍，确认截图覆盖的周窗口 → 写进脚本目录的 `rollup_manual.json` 由重算脚本合并。
  - **重算脚本对人工补录字段必须「没算出来就跳过该 key」，绝不写 null**：源表缺该列时写 null 会把你上一轮截图补的数清空；`口径备注`/`数据来源` 要追加截图来源，别让表里仍写着「未采集」。
- **跨平台大盘是「人数 + 次数」混算**：公众号导出全是「人数」（去重），小红书是「次数」；合计只用于看趋势，当精确总量会失真——卡片名或口径 text 里标一句。各指标字段与口径对照见 [weekly-metrics-and-analysis.md](references/weekly-metrics-and-analysis.md)。
- 交付时把**数据缺口点名**（哪个平台缺哪个指标、榜单因源表缺行只有几条），并给分级改进建议清单（先补采 → 再比率卡 → 再环比/结论块），让用户挑下一步。
- **先读回再交付**：`+dashboard-block-get-data` 返回图表实际算出的数字，必须与对拍值一致才算完成；创建接口 ok 只代表配置写进去了。
- 用户说「先看看」= 交最小可用版 + 一句「哪里不顺告诉我改哪块」，不要一次堆满自定义布局。
- **用户说「我改了一下看板」时先只读不改**：`+dashboard-block-list --page-size 100` 拿块清单（含 `position`）+ 逐块 `+dashboard-block-get` 读 `data_config`，先用清单复述他改了什么（改名 / 删了哪几个块 / 布局挪动），再动手。他删掉的块往往是不想要的——不要自动建回、不要把他挪的布局再改一遍。
- **可复制的 `data_config` 模板**（含 combo 柱/线顺序、宽表「大盘主线+分账号柱」、人工补录 JSON 格式）、字数口径陷阱、读回脚本片段见 [dashboard-blocks.md](references/dashboard-blocks.md)。

## 10. 数据怎么分析（用户问「该做哪些分析/能得出什么结论」）

不要只复述指标，按「描述→结构→内容集中度→互动质量→节奏→归因」分层给结论，每层都带算出来的真实数字，并主动列出「这份数据做不了什么」（缺粉丝数/送达数就算不出打开率与转化）。周粒度口径、北极星指标、爆款剥离法见 [weekly-metrics-and-analysis.md](references/weekly-metrics-and-analysis.md)。

## 11. 交付与收尾

- 删 cwd 临时 payload / `.ndjson` / `.manifest.json`。
- `+table-list` 复核：Base 里可能有用户**同时新建**的其他表，不要动、不要顺手改，交付里明确说「没动那张表」。
- 交付内容：字段清单（表格逐条列全）、为什么这样装（一张表 + 记录类型 + 分类型视图）、对拍结果。用户关心「数据对不对得上」，先给这个结论。
- **表名跟用户的「平台：账号」体系**（`公众号：刀客轻研` / `服务号：刀客轻研` / `小红书：刀客轻研`）：新建表前先 `+table-list` 看现有命名，别自创 `xxx数据`。用户会在会话中途改名、新建、删表，交付前重新 `+table-list`，按**当前**表名说话，不要用自己建表时的旧名。
- **同构新表一次建齐**：追加一个账号/平台表时用 `+table-create --name "平台：账号" --fields @./fields.json`（`--fields` 数组**第一项即主字段**，直接写 `记录名称` text），比「建空表→改主字段→删空行→逐个补字段」少四步且不会漏字段；之后直接跑 `--table "新表名"` 导入并补建同类视图。
- **同一批附件被要求再灌一张新表**（例：已灌「小红书：刀客轻研SciLink」，又让建「小红书：刀客轻研」）：照做，但交付时必须点明「两表数据同源、会重复」，并给选项（清空旧表 / 删旧表 / 确认是不同账号），**不要擅自删数据**。
- **确认拿错源就整体重灌，别逐行改**：`+record-list --format ndjson` 取全部 `record_id` → 一条 `+record-delete --yes` 带多个 `--record-id` 清空 → 重新 `--json @payload` 灌入 → 再对拍。逐行 update 会把两套账号的数据混在一起，对拍时更难分清。
- 同构多表时 `数据来源` 统一写成「**账号附件字段名** · 文件名 / sheet 名」（例 `刀客轻研近30天 · 近30日涨粉数据.xlsx`）：跨表合并统计时能一眼看出这行是谁的数。
- 分析类回答先给一句结论再分层展开；每个判断标清是**实锤（数据直接支持）**还是**推断（需注明假设）**；比值类指标必须写明分子分母口径（「人数比≠转化率」）。

## 12. 视图落地的两个实测边界

- **view_id 现抄现用**：只从 `+view-list` 的返回里复制 id，不要从 URL 或 `+url-resolve` 结果里手打。这些 id 只有一字之差（`vew…`/`vev…`、`0`/`O`），敲错一个是 `not_found 800030501` + `method_id` 排查链接，报错文本里完全看不出是 id 错位，会白查一圈权限。
- **没有字段求和/统计类命令**：`lark-cli base` 的 `+view-set-*` 只有 filter/sort/group/visible-fields/card/timebar。分组视图只能给到「分组 + 可见字段 + 排序」，组内列求和要在 UI 里手动点列统计；交付时说一句「分组已设，组内合计点列头统计」，不要去找不存在的 `+view-set-stat`。

## 13. 用后台截图补录周数据（用户说「看截图，不要看 Excel」）

周汇总表里每个账号一行、`周` 为空，数据源是另一张「基础数据」表按周挂的**后台截图**。固定四步：

1. `+record-list --format ndjson` 读基础数据表，按 `周` 找到本期记录，抄出对应账号列的 `file_token`（image.png），`+record-download-attachment --file-token … --output ./w44_imgs/x.png` 下到 cwd（`--output` 不能指 scratch）。
2. 先整图 `vision_analyze` 让它把**所有**指标标签+数值+统计周期读全，再对易错的个位数用 `region` 裁小核对。
3. 用**已经填好的另一条账号行**反推字段映射（数字逐项对上才算规则成立），再写空的那一行。
4. `+record-batch-update` 改 `账号` 定位到的 `record_id` 那一格，**不要 `+record-batch-create`**——汇总表的账号行是预建好的空行，新建会让同一账号出现两条同周记录；写完 `+record-get` 读回核验。

必守口径：

- **`粉丝数` = 总粉丝数（存量），不是净涨粉**。小红书「笔记数据总览」只有「净涨粉 / 新增关注 / 取消关注」（流量），存量粉丝要另找来源。
- **数值对得上 ≠ 语义对得上**：已填行的 `粉丝数` 恰好等于截图「净涨粉」时，别据此认定映射成立——存量字段默认按总量理解，拿不准就问用户一句，不要用近似指标顶替入库。
- 截图里读不到总粉丝数时**主动报缺口并给选项**（每周你直接给数 / 再挂一张「粉丝数据」页截图），不要静默填净涨粉或留空当完成。
- 用户说「不要看 Excel」就只用 image.png：同一列里常混着同名 xlsx（`近30日观看数据.xlsx` 等），不要拿它交叉验证、也不要改用当源。
- 周标签取截图的统计周期换算（`10-19 至 10-25` 近7日 → `w44`），写之前确认周期是全周还是滚动截断。

平台截图 → 表字段的完整对照表见 [weekly-metrics-and-analysis.md](references/weekly-metrics-and-analysis.md)。

## 14. 一篇飞书文档 → 分类入库（+ 每条生成云文档回填链接）

用户给一份「选题库 / 需求库 / 盘点」类飞书文档，要求「分门别类装进多维表格」，并常附带「单条拆成一个云文档，把链接放回表里」。流程固定六步。

1. **先拉文档，按章切块统计，不要直接开建表**：`docs +fetch --doc <url> --doc-format markdown` 落 JSON，用 `re.split(r'\n(?=# )', content)` 按章拆。每章先数「真正有内容的条目」再设计字段——同一篇文档里常常「三个表很饱满 + 一个表全是空占位 + 一个章节带图带文案」，字段和拆分粒度都取决于这个盘点。
2. **抽取时两个必须处理的细节**：
   - `<li>` 转文本**必须按 `</li>` 断行**。只按 `<br/>` 切会把一整列痛点串成一句（「…关键变量没记录随访起点和终点不统一…」），落到表里没人看得出来。
   - `<del>`（原文划除）是编辑决策，**不能静默丢掉**：转成文本时加重前缀如 `（已划除）“…”`，否则下游会把已被否决的条目当待办。
   - 嵌套列表区分层级：`<li>` 深度 1 = 一个选题，深度 2 = 该选题的子要点；按深度拆行，别把子要点也建成记录。
3. **字段设计按「章节 + 两个分类维度 + 内容 + 出处 + 产物」**：主字段（选题标题）→ `归属章节`（select，一章一个值）→ 各章的痛点/处境维度各一个 select（无值的行留空，不要塞空格或「无」）→ `场景` / `痛点分析` / `业务对接点` / `参考稿件` → `选题文档`（text，放云文档 URL）→ `素材状态`（select：有文案+配图 / 仅标题）。`素材状态` 让用户一眼看出哪些还没内容。
4. **原文术语不统一时在入库层归一，并在交付里说明**：同一概念常写成「病例/病历」「病例对照/病例对照研究」。归一值是**建 options 时就要定死的那一套**，同时把文档里出现的变体映射过去（见 §6 的 800030005）；否则整批写入失败。归一必须两边一致——表格和拆出去的云文档都用同一套词。
5. **拆云文档前先问粒度，别一把建到底**：一条记录一个文档时，纯标题的条目会变成大量空壳文档。先盘点「N 条仅标题 / M 条有文案+配图」摆给用户选（全建空模板卡 / 只建有内容的 / 全建轻量），拿到了再动手。
6. **建文档 + 回填链接**：`drive +create-folder --name <库名·文档>` 建一个文件夹收口 → 每条 `docs +create --doc-format xml --content @./case.xml --parent-token <folder_token>` → 从返回的 `data.document.url` 回填到 `选题文档` 字段（`+record-batch-update`，按主字段匹配 `record_id`）。图文条目用 `<img src="<原图 token>"/>` 直接内嵌原图，不用下载重传。

**验收**：逐篇 `docs +fetch --doc-format markdown` 数 `![` 的个数与源文档该节图片数逐个对平（总数也要平），并确认归一后的术语没有残留；再 `+record-list --format ndjson` 核「总数 == 预期」「带链接数 == 实际建的文档数」。
